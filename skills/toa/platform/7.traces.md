# Follow a Request through the Application

Approving an order takes two seconds and nobody knows where they go: in `store.orders`, in the
call to `billing.wallets`, in the database, or in the mail provider. A *trace* answers that. It is
the record of one request as *spans*: one per step, each with its duration and its place among
the others.

Spans for operations, calls, events and storage commands are made for you. You add spans around
steps of your own, and say in the [Context](../shipping/1.context.md) where traces go.

## See spans on the console

Add `telemetry` to the Context: name the `console` exporter and lower the log level to `trace`
for the local environment:

```yaml
# context.toa.yaml
telemetry:
  logs:
    level@local: trace
  traces:
    exporters@local:
      console: ~
```

Restart the application, call an operation — `store.catalog.convert` is the one
[Add a span](#add-a-span) writes — and read what the components wrote:

```shell
$ npm run restart
$ npx toa call store.catalog.convert "{ input: { amount: 1000, currency: 'EUR' } }"
$ pm2 logs app
```

Each span is written when it completes, as a log entry of `TRACE` severity whose message is the
span's name:

```json
{
  "time": "2026-01-01T12:00:00.000Z",
  "severity": "TRACE",
  "message": "fetch rate",
  "attributes": { "currency": "EUR" },
  "context": { "namespace": "store", "component": "catalog", "operation": "convert" },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "parent_id": "53995c3f42cd8ad8",
  "duration": 12.4
}
```

| Field | |
| --- | --- |
| `trace_id` | 32 hex characters, shared by all spans and log entries of the trace. |
| `span_id` | 16 hex characters. |
| `parent_id` | The `span_id` of the enclosing span, when there is one. |
| `duration` | Milliseconds. |
| `kind` | `server`, `client`, `producer` or `consumer`; absent for an internal span, which is what `context.span` creates. |
| `status` | `error` when the span failed; absent otherwise. |

These are log entries of the lowest severity, so they appear only when the log level is `trace`.

## What is traced without any code

| What happens | Spans |
| --- | --- |
| An operation is invoked | one span for the invocation |
| A component calls another | a `client` span at the caller and a `server` span at the callee; the difference of their durations is the time spent in transport |
| An event is published | a `producer` span |
| A receiver handles an event | a `consumer` span per receiver, linked through the event |
| A storage command | a `client` span named `<command> <collection>` |
| A [stash](4.stash.md) command | a `client` span named `<command> stash` |
| A [`context.fetch`](../logic/11.external.md) call | a span for the call and one per attempt |
| An HTTP request to the gateway | a span for the request |

A request that arrives with a [W3C Trace Context](https://www.w3.org/TR/trace-context/)
(`traceparent`) continues that trace; otherwise a new trace starts.

Receivers handle an event after the operation that caused it has returned, so their spans may end
later than the operation's span.

A span is marked as failed (`status: error`) when an exception was thrown, when an operation
answered with an exception, and when an HTTP request ended in a `5xx`. A returned error is not a
failure and leaves no mark.

Storage commands issued outside a recorded trace, such as index management at startup, are not
recorded.

## Add a span

`context.span` runs a function and records how long it took. The catalog converts a price with a
currency rate it asks an external service for:

```yaml
# components/store.catalog/manifest.toa.yaml
name: catalog
namespace: store

operations:
  convert:
    input:
      type: object
      properties:
        amount: { type: integer }
        currency: { type: string }
      required: [amount, currency]
```

```typescript
// components/store.catalog/operations/convert.ts
import type { Context, ConvertInput } from '../types/index.d.ts'

export async function computation (input: ConvertInput, context: Context) {
  const rate = await context.span('fetch rate', () => lookup(input.currency))

  return Math.round(input.amount * rate)
}
```

`lookup` stands for the request to the rate service.

```text
context.span<T>(name: string, task: () => T | Promise<T>): Promise<T>
context.span<T>(name: string, attributes: object, task: () => T | Promise<T>): Promise<T>
```

- `name` is the span's name. Keep it constant, as with log messages; put what varies into
  attributes.
- `attributes` is optional and is recorded with the span as given.
- `task` is the function to run. Its result is returned as it is. If it throws, the span is
  marked as failed and the exception is thrown on.

`context.span` always returns a promise, also for a synchronous task.

### Attributes

```typescript
const rate = await context.span('fetch rate', { currency: input.currency }, () =>
  lookup(input.currency))
```

The rules for [log attributes](6.logs.md#write-good-entries) apply: identifiers and enumerable
values, no personal data, no secrets.

### Nesting

Spans created inside a task are children of its span, and log entries written inside it carry
its `span_id`:

```typescript
export async function computation (input: ConvertInput, context: Context) {
  return context.span('convert', { currency: input.currency }, async () => {
    const rate = await context.span('fetch rate', () => lookup(input.currency))

    context.logs.info('Rate received', { rate })

    return Math.round(input.amount * rate)
  })
}
```

### When to add one

Calls to other components, storage, the stash and outside HTTP are already spans. Add one around
what cannot be seen from outside your code: a computation that may be slow, or a call made with a
client library of your own.

A span's duration is recorded whether or not the trace is sampled, so a duration needs no
[metric](8.metrics.md) of its own.

## Send traces to a backend

Trace ids are always there, in every [log entry](6.logs.md). Spans are recorded somewhere once
the Context names an exporter:

```yaml
# context.toa.yaml
telemetry:
  traces:
    exporters:
      otlp:
        endpoint: http://tempo:4318
```

| Exporter | |
| --- | --- |
| `otlp` | Sends spans in batches to an OTLP/HTTP endpoint: Grafana Tempo, an OpenTelemetry Collector and the like. `/v1/traces` is appended to `endpoint`. |
| `console` | Writes each span as a log entry of `TRACE` severity. Takes no options: `console: ~`. |

Only the exporters named are used. To have both, name both:

```yaml
telemetry:
  traces:
    exporters:
      console: ~
      otlp:
        endpoint: http://tempo:4318
```

The other options of `otlp` (`timeout`, `cooldown`, `headers`) and what happens when the backend
is away are in [Send Telemetry to Grafana](9.exporting-telemetry.md#the-otlp-exporter).

Over OTLP, a span's `service.name` is the component that produced it, such as `store.orders`, or
`exposition` for the gateway's request spans, also when several components share a process.
There is no per-process service name to configure.

## Record fewer traces

Recording every trace of a busy application is expensive. Two settings limit what is recorded:

```yaml
# context.toa.yaml
telemetry:
  traces:
    sample: 0.1
    rate: 5
```

| Key | Default | |
| --- | --- | --- |
| `sample` | `1` | The probability, `0` to `1`, that a trace is recorded. `0` records none, `1` all. |
| `rate` | unlimited | The most traces recorded per second, per process. May be fractional: `0.5` is one trace in two seconds. |

`sample` keeps the recorded volume proportional to traffic; `rate` is a cap against spikes. With
both set, a trace is recorded when it passes the `sample` draw *and* the rate is not exceeded.

A value out of range stops the deployment:

```text
telemetry.traces.sample must be a number within [0, 1]
telemetry.traces.rate must be a positive number
```

What to expect with sampling on:

- A trace is recorded whole or not at all; there are no traces with components missing. Nothing
  needs to be configured for sampling in a collector.
- Operations of an unsampled trace run the same, and **their log entries still carry its
  `trace_id`**. A log record may therefore name a trace the trace backend never received.
- Metrics are unaffected: every operation is counted and timed whatever happens to its trace.

More on the subject is in the model article
[Telemetry](https://toa.io/model/platform/telemetry/#traces).

## See where startup time goes

Set `TOA_BOOT_TRACE=1`. `toa compose` and `toa serve` then produce a trace of the boot: loading
manifests, creating components, connecting each connector.

```shell
$ TOA_BOOT_TRACE=1 npx toa compose ./components/*
```

It is off by default.
