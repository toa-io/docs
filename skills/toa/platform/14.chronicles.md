# Keep a Log of What Happens and Query It

The shop wants to know what sells, what customers search for and where they leave the storefront,
and wants to ask in words rather than build a dashboard. *Chronicles* keep a log of the
application in [ClickHouse](https://clickhouse.com): the changes of the components that name them,
facts an operation sends, and what browsers send. An agent reads it over the gateway's
[MCP](../api/15.tools.md).

## Turn it on

ClickHouse reads the log off the broker the application already runs. Add it to
`docker-compose.yaml`, with a user that may create what the log needs:

```yaml
# docker-compose.yaml
services:
  clickhouse:
    image: clickhouse/clickhouse-server:26.8.34.13
    ports:
      - "8123:8123"
    environment:
      CLICKHOUSE_USER: developer
      CLICKHOUSE_PASSWORD: secret
      CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT: 1
    volumes:
      - ./clickhouse.xml:/etc/clickhouse-server/users.d/developer.xml:ro
```

```xml
<!-- clickhouse.xml -->
<clickhouse>
  <users>
    <developer>
      <named_collection_control>1</named_collection_control>
    </developer>
  </users>
</clickhouse>
```

Then the [Context](../shipping/1.context.md) says where the broker and ClickHouse are. ClickHouse
reaches the broker over the compose network, by another address than the components do:

```yaml
# context.toa.yaml
chronicles:
  broker: amqp://localhost:5672
  clickhouse:
    url: http://localhost:8123/store # the path names the database
    broker: amqp://rabbitmq:5672
chronicles@production:
  broker: amqp://rabbitmq.example.com
  clickhouse: https://clickhouse.example.com:8443/store
  retention: 730 # days a row is kept; absent, kept
```

The log is served by a service of its own, `chronicles`. Add it to what `sys` serves:

```javascript
// ecosystem.config.js
{ ...common, name: 'sys', args: 'serve configuration exposition introspection chronicles' },
```

```shell
$ npm run env
$ docker compose up -d
$ npm run restart
```

`npm run env` writes the credentials of the broker and of ClickHouse into `.env`. In a deployment
they are [secrets](../shipping/6.secrets.md): the ClickHouse user, and `reader`, the password of the
user queries run as, which the service creates.

```shell
$ npx toa conceal chronicles-broker username=store password=...
$ npx toa conceal chronicles-clickhouse username=store password=... reader=...
```

## Log the changes of a component

A component names the [events](../logic/7.events.md) whose payloads are its changes in the log:

```yaml
# components/store.orders/manifest.toa.yaml
chronicles: [created, snapshot]
```

`created` is one every component has; `snapshot` is an event of its own, which nothing has to
consume. Its payload is what the log is given of every change — the order without what identifies
the customer:

```typescript
// components/store.orders/events/snapshot.ts
import type { Event } from '../types/index.d.ts'

export function payload (event: Event) {
  const { email, address, ...order } = event.state

  return order
}
```

What an event's payload leaves out does not reach ClickHouse, so this is where personal data is
kept out. A change is logged once it is committed, whether or not ClickHouse is up at the time,
and once however often it is delivered.

## Send a fact

A search changes nothing, and is still worth knowing:

```typescript
// components/store.search/operations/find.ts
import type { Context, FindInput } from '../types/index.d.ts'

export async function computation (input: FindInput, context: Context) {
  const results = await query(input.text, context)

  await context.chronicles.send('searched', { text: input.text, results: results.length })

  return results
}
```

```yaml
# components/store.search/manifest.toa.yaml
chronicles: []
```

`send` resolves once the broker has the fact, and nothing sends it again: what must not be lost is
a change of state instead.

## Take events from the storefront

```yaml
# context.toa.yaml
chronicles:
  ingest: true
```

The storefront posts batches of what happened, at most 100 at a time:

```javascript
navigator.sendBeacon('https://api.store.example/chronicles/ingest/', JSON.stringify([
  { id: crypto.randomUUID(), name: 'page.left', time: Date.now(), payload: { path: location.pathname } }
]))
```

```http
202 Accepted

accepted: 1
```

An event is `{ id, name, time, payload }`: its own id, which a retry sends again; dotted
lowercase segments; milliseconds by the browser's clock; an object of at most 16 KiB. It is logged
under `client.<name>`. The route takes no credentials and is throttled per address, which takes
[`exposition.ip`](../api/17.running.md#client-address) to name the address. Anyone can send anything, so a user in a
payload is what the browser said.

## Read the log

Every row is in `events`:

| Column      |                                                                              |
| ----------- | ---------------------------------------------------------------------------- |
| `label`     | `store.orders.created`, `store.search.searched`, `client.page.left`           |
| `component` | the component that logged it                                                 |
| `time`      | when it happened                                                             |
| `entity`    | the id of the order that changed; `NULL` for a fact and for the storefront    |
| `version`   | the order's version                                                          |
| `payload`   | what the event, the fact or the browser carried                              |

`states` holds the latest payload of every order under every label: under `snapshot`, the order
as it stands.

```sql
SELECT toDate(time) AS day, count() FROM events FINAL
WHERE label = 'store.orders.created' GROUP BY day ORDER BY day

SELECT payload.status, count() FROM states FINAL
WHERE label = 'store.orders.snapshot' GROUP BY 1
```

Read both with `FINAL`, which collapses what was delivered twice. Nothing arrives in order: order
by `time`, or by `version` within one order.

## Let an agent ask

Publish the gateway's [tools](../api/15.tools.md), and the log is four of them:

```yaml
# context.toa.yaml
exposition:
  mcp:
    name: Store
```

| Tool                                  | Does                                                          |
| ------------------------------------- | ------------------------------------------------------------- |
| `chronicles.query.GET`                | the labels, their counts and times, their payloads' fields, the views |
| `chronicles.query.POST`               | one `SELECT`                                                  |
| `chronicles.query.views._name.PUT`    | defines a view, and with `refresh` a table recomputed on that cycle |
| `chronicles.query.views._name.DELETE` | drops a view                                                  |

Reading takes the role `system:chronicles:query`, and views `system:chronicles:views`; grant
`system:chronicles` for both. See [Give Staff Wider Access](../access/7.roles.md#grant-a-role).

A query reads the store's database and nothing else, for at most 30 seconds and 10,000 rows, and
cannot write. A view is a `SELECT` a query could run; with `refresh`, in seconds and at least an
hour, it is computed on that cycle and read as a table. A store has at most 50 views.

### Try it

```http
POST /chronicles/query/ HTTP/1.1
host: api.store.example
authorization: Basic cm9vdDpzZWNyZXQjMTIzNA==
accept: application/yaml
content-type: application/yaml

sql: SELECT label, count() AS n FROM events FINAL GROUP BY label
```

```http
201 Created

columns:
  - name: label
    type: LowCardinality(String)
  - name: n
    type: UInt64
rows:
  - [store.orders.created, 12]
truncated: false
```

## When ClickHouse refuses what it was sent

What ClickHouse fails to write stays on the broker, in the queue `chronicles.dead`. Once the cause
is fixed, move the messages back to the queue `chronicles` with the management UI's _Move
messages_ or a [shovel](https://www.rabbitmq.com/docs/shovel).
