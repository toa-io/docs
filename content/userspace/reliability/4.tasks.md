# Tasks

A task is a call nobody waits for. The caller hands it over and carries on; the operation runs
later, in whichever process of the target component is free. The model's
[Tasks](../../model/reliability/4.tasks.md) explains when a task is the right tool and when an
event is.

## Making one

Add `task: true` to the request:

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, entry, context) {
  // … debit the account, as before

  entry.status = 'approved'

  await context.remote.store.notifications.send({
    input: { customer: entry.customer, order: entry.id },
    task: true
  })

  return entry
}
```

`store.notifications` is a component whose effect `send` emails the customer. Without
`task: true`, `approve` would wait for the email and fail if the mail service were away. With it,
the call answers as soon as the task is stored, and `approve` goes on.

Nothing is declared for it. The operation called is an ordinary operation; being run as a task
is a property of the call, and the same operation can be called both ways.

`query` works as in any call:

```javascript
await context.remote.store.orders.archive({ query: { id }, task: true })
```

A component can give a task to itself, with `context.local`. That is a common way to answer now
and do the slow part afterwards:

```javascript
// components/store.orders/operations/cancel.js
export async function transition (input, entry, context) {
  entry.status = 'cancelled'

  await context.local.refund({ query: { id: entry.id }, task: true })

  return entry
}
```

## What the call answers

`null`, once the task is safely stored:

```javascript
const reply = await context.remote.store.notifications.send({ input, task: true })
// reply === null
```

It says nothing about the result, because there is none yet. If the caller needs the outcome, it
gets it as it would get any other fact about another component: by reading state later, or by
receiving an event.

A call that *throws* is a task that may or may not have been taken. Letting the exception through
is right; if your own operation is then retried, the task may be handed over a second time, which
the operation has to tolerate anyway.

## What you can count on

**A task that was accepted will run.**

- **It is stored before the call answers.** A caller that stops the instant after has nothing
  left to do.
- **It outlives what it waits for.** A component that is down, being deployed or not yet started
  is given its tasks when it comes back. Nothing expires while it waits.
- **A failure does not lose it.** An exception has it tried again, with growing pauses; one that
  keeps failing is [parked](1.delivery.md#parked-messages) for a person, with what it was and why
  it stopped.

## What that asks of the operation

A task is handled [where nobody is waiting](1.delivery.md#when-nobody-waits), and all of that
applies.

**It may run more than once.** The guarantee is that it runs, not that it runs once. Write the
operation so that handling the same task twice leaves the same state, declare it
[`once`](3.idempotency.md), or, for an effect that reaches outside, put it under
[continuity](5.continuity.md).

**A refusal ends it, and nobody reads it.** A returned error stops the task and is not tried
again. If the refusal has to be visible, the operation writes it:

```javascript
// components/store.orders/operations/refund.js
export async function transition (input, entry, context) {
  const reply = await context.remote.store.accounts.credit({
    query: { id: entry.customer },
    input: { amount: entry.total }
  })

  if (reply instanceof Error) {
    entry.refund = 'failed' // somebody reads this; nobody reads the returned error
    return entry
  }

  entry.refund = 'done'

  return entry
}
```

**It has no deadline.** Nothing ends a task early, and it may run long after it was made — after
a deployment, after an outage. Work that can stop being worth doing has to tell from the state
it reads: a `refund` for an order that is no longer cancelled does nothing.

## What cannot be a task

Each of these is refused where the call is made, with an exception:

| call                                         | why                                            |
| -------------------------------------------- | ---------------------------------------------- |
| with `timeout` or `signal`                   | nobody waits, so there is nothing to give up   |
| to a stateful operation                      | it is served by one named process              |
| to an operation that takes a stream as input | the stream exists only while its caller writes |
| to an unsafe operation, in a readonly chain  | handing over a write is a write                |

A stateful operation is called on one process by name, while a task is taken by whichever process
is free. Readonly chains are described in
[Call Chains](6.call-chains.md#chains-that-may-only-read).

A task that names an operation the target component does not have — a caller deployed ahead of
it — is accepted, and parked at once when the component takes it.

## Tasks share a component

Every task a component is given waits in one line, whichever of its operations it is for, and
the processes of that component take them in turn. A backlog of one operation's tasks delays
another's, and an operation that takes minutes is felt by every task of its component.

Where that matters, move the slow operation to a component of its own. That is the same boundary
that decides what is deployed and scaled together.

## Summary

| you want                                   | you write                                         |
| ------------------------------------------ | ------------------------------------------------- |
| hand work to another component             | a `context.remote` call with `task: true`         |
| hand work to your own component            | a `context.local` call with `task: true`          |
| know it was accepted                       | the call answered `null`                          |
| know how it ended                          | read state, or receive an event                   |
| survive a repeat                           | a change that repeats safely, `once`, or continuity |
