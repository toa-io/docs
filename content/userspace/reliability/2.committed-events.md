# Committed Events

When an operation of `store.orders` commits, its [events](../components/6.events.md) are
published. This article is about how sure that is: **a state change and the events of that change
are stored together, so an event is never lost and never published for a change that did not
happen.** The model's [Committed Events](../../model/reliability/2.outbox.md) explains why that
matters.

## What you declare

Nothing in the component. The operation commits, and publication follows:

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, entry, context) {
  // …
  entry.status = 'approved'

  return entry // the order and its `approved` event are stored in one write
}
```

The operation does not wait for the broker. If the broker is slow or away, `approve` still
answers, and the event is published when the broker returns.

Two things have to be true of the deployment for the guarantee to hold.

### A storage that commits both at once

MongoDB running as a replica set or a sharded cluster. On a standalone `mongod` events are still
published right after the commit, but a process that stops between the two loses the event; the
component says at startup that it is running this way.

### Somewhere for replicas to agree

If the process that committed a change stops before publishing it, another replica of the
component publishes it instead. For that the replicas need the platform's shared decisions,
which run on Redis:

```yaml
# context.toa.yaml
atomicity:
  redis: redis://redis.example.com
```

Without [`atomicity`](../services/6.shared-decisions.md#setting-it-up), events are published as they
are committed and nothing recovers one that was left behind. A replica that cannot reach Redis
recovers nothing until it can.

## Which events are published

An event is published only where something consumes it. Inside the application that is a
receiver in another component — the runtime sees those itself. An event consumed *outside* the
application has to be named in the Context:

```yaml
# context.toa.yaml
events:
  - store.orders.approved # a warehouse system outside this application listens
```

An event nobody consumes is not published and costs nothing; a component none of whose events
are consumed keeps no record of its changes at all.

On a local run — `toa compose`, `toa mono`, a composition booted in a test — every event is
published.

## What a subscriber can rely on

These are the rules a [receiver](../components/7.receivers.md), or an outside consumer, is
written against.

**At least once.** An event may arrive twice: the publisher can stop after sending it and before
noting that it did, and the broker redelivers on its own account. Make the operation a receiver
invokes [tolerate a repeat](1.delivery.md#what-an-operation-must-tolerate), or declare it
[`once`](3.idempotency.md).

**No order.** Two changes to one order may be announced in either order, and an event recovered
after a failure can arrive long after later ones. Never assume the event you are handling is the
newest.

**A version on every event.** The state an event describes carries `VERSION`, which only grows.
A lower version than the last one you applied is stale; an equal one is a duplicate:

```javascript
if (entry.applied >= input.version) return entry
```

**One destination does not hold up another.** Events go to the broker, and the same change may also
feed [realtime](../gateway/13.realtime.md) streams or another [region](../running/10.regions.md).
Each is delivered on its own: one that is down delays only itself, and nothing that already arrived
is sent again because of it.

**How late.** Normally an event follows its commit immediately. One that has to be recovered
arrives after three to four cycles — 15 to 20 seconds with the default settings.

## The event

What a condition or a payload function is given is the stored change:

| property   | what it is                                                       |
| ---------- | ---------------------------------------------------------------- |
| `origin`   | the entity before the change; `null` if it did not exist         |
| `state`    | the entity after the change, with `VERSION`                      |
| `trailers` | what the operation wrote into `TRAILERS`                         |
| `input`    | the operation's input                                            |

Because the functions run on what was stored, a recovered event is evaluated on exactly the same
facts as a prompt one. Keep them pure: a payload function that reads a clock or a counter gives
a recovered event a different payload.

An event of an assignment has an `origin` too, and no `trailers`.

### Trailers

A trailer is a fact about *this change* that is not part of the entity: how much was debited,
why, on whose behalf. A transition writes it into `TRAILERS` and it is committed with the change:

```javascript
// components/store.accounts/operations/debit.js
export async function transition (input, entry) {
  if (entry.balance < input.amount) return new Error('INSUFFICIENT_FUNDS')

  entry.balance -= input.amount
  entry.TRAILERS.amount = input.amount
  entry.TRAILERS.reason = input.reason

  return entry
}
```

```javascript
// components/store.accounts/events/debited.js
export const condition = (event) => event.trailers.amount !== undefined

export const payload = (event) => ({
  account: event.state.id,
  amount: event.trailers.amount,
  reason: event.trailers.reason,
  balance: event.state.balance,
  key: `${event.state.id}:${event.state.VERSION}`
})
```

The `key` is worth copying: an entity's id together with its `VERSION` names one write, once and
for all. A subscriber that keeps a ledger line per debit stores the line under that key, and a
repeated event writes the same line again instead of a second one.

**Trailer values must be serializable.** They are stored, so a function, a stream or a class
instance does not survive.

`TRAILERS` is never stored on the entity, never answered and cannot be declared in the entity
schema.

### What can go wrong

**A condition or payload function that throws blocks every event of that change.** They are
published together, so none of them goes out, and the attempt is repeated every cycle until the
function stops throwing. Deploy the fix and the events follow.

**A very large entity.** A stored change holds the entity before, the entity after and the input,
so a 1 MB entity makes a record of about 2 MB against MongoDB's limit of 16 MB per document.

## Settings

```yaml
# context.toa.yaml
outbox:
  interval: 5000   # milliseconds between checks for events left behind
  batch: 200       # how many of them one read brings back
  retention: 86400 # seconds a published change is kept before it expires
```

All three are optional.

- `interval`, at least `100`, decides how fast a rare failure heals, not how fast events flow:
  recovery takes three to four intervals.
- `batch`, at least `1`, bounds one read and not the work: a full read is followed by another.
- `retention`, `0` or more: published changes stay this long as a change log you can read.

For development, three environment variables:

| variable              | effect                                                               |
| --------------------- | -------------------------------------------------------------------- |
| `TOA_OUTBOX_DEFER=1`  | nothing is published right after the commit, only by recovery        |
| `TOA_OUTBOX_INTERVAL` | the interval, in milliseconds                                        |
| `TOA_OUTBOX_BATCH`    | the batch                                                            |

`TOA_OUTBOX_DEFER` is announced at startup. With it every event arrives late, which is a way to
see how subscribers cope.

## Operating

The changes of a component are kept beside its entities, in a collection named after it with
`_outbox` appended. It is a change log and a list of what is stuck at once:

```javascript
// what has not been published, oldest first
db.store_orders_outbox.find({ published: false }).sort({ _id: 1 })
```

In a healthy system this finds nothing, or a few documents a moment old. Each one holds the
`event` described above and, in `outstanding`, the destinations it has not reached.

An unpublished change is never dropped and never expires: there is no attempt limit. If the list
grows, something it publishes to is down, or a payload function is throwing.

Each replica recovers its own share of changes, and there are 128 shares, so **a component runs
at most 128 replicas**.
