# Continuity

A [task](4.tasks.md), or an operation a receiver invokes, is tried again when it throws, and
every attempt runs the operation from the top. For an effect that is a sequence of steps reaching
outside the component, that means the steps that already succeeded are made again.

An effect declared under `continuity` picks up where it failed instead. The concept is in the
model's [Continuity](../../model/reliability/5.continuity.md).

## Declaring it

`store.fulfilment` is a component that ships an approved order: it reserves the stock, books a
courier through the courier's API, and notifies the customer.

```yaml
# components/store.fulfilment/manifest.toa.yaml
namespace: store
name: fulfilment

operations:
  ship:
    type: effect
    input:
      type: object
      properties:
        order: { type: string }
      required: [order]

continuity:
  ship: 604800 # seconds an unfinished run can still be resumed
```

```javascript
// components/store.fulfilment/operations/ship.js
export async function effect (input, context) {
  const order = await context.remote.store.orders.observe({ query: { id: input.order } })

  await context.remote.store.catalog.reserve({ input: { items: order.items } })

  const response = await context.fetch('courier', {
    method: 'POST',
    body: JSON.stringify({ order: order.id })
  })

  const booking = await response.json()

  await context.remote.store.notifications.send({
    input: { customer: order.customer, tracking: booking.tracking }
  })
}
```

The operation is written as any other; nothing in it is about resuming. If `send` throws, the
next attempt is given the order `observe` answered, the reply of `reserve` and the response the
courier gave — without any of them being asked again — and only `send` is made.

`continuity` is a section of the manifest, beside `operations`. Each key names an effect of the
component; the value is how long, in seconds, a run that has not finished can still be picked up.

- **There is no default.** How late a parked task can be put back is yours to know.
- **The minimum is `600`.**
- A manifest that states less, names an operation the component does not have, or names one that
  is not an effect is refused: `'transit' is not an effect`.

## Calling it

Only where nobody waits. As a task:

```javascript
await context.remote.store.fulfilment.ship({ input: { order: entry.id }, task: true })
```

or from a receiver:

```yaml
# components/store.fulfilment/manifest.toa.yaml
receivers:
  store.orders.approved: ship
```

Each task, and each event, is one *run*. Its attempts share what was kept; two runs share nothing.

**A call that waits for the answer is refused** with an exception, and so is a
[pulse](../flow/1.pulses.md) that names the operation. A waiting caller decides for itself whether
to ask again, so there is no later attempt to resume.

## Steps

A step is something the operation asks of its context. What a step answered is kept, and given
back on a later attempt instead of being asked again.

| asked through `context`                     | a step |
| ------------------------------------------- | ------ |
| `remote` and `local` calls                  | yes    |
| `fetch`                                     | yes — status, headers and body, given back as a `Response` |
| `stash`                                     | yes    |
| `id()`, `now()`, `random()`                 | yes    |
| `logs`, `span`, `metrics`, `configuration`  | no — the same on every attempt |
| `state`, `atom`                             | no     |

**A step is recognized by what it asks, not by when.** Two attempts that make the same request
are making the same step. So concurrent branches are fine:

```javascript
await Promise.all([
  reserve(context, 'warehouse-a').then((r) => label(context, r)),
  reserve(context, 'warehouse-b').then((r) => label(context, r))
])
```

Each branch is given its own answers on the next attempt, in whatever order they complete.

### Take time, randomness and ids from the context

Because a step is recognized by its arguments, an argument that differs between attempts makes a
new step, and the step is made again:

```javascript
// a new timestamp every attempt: the call is made again every attempt
await context.remote.store.invoices.issue({ input: { at: Date.now() } })

// the same timestamp on every attempt: the call is made once
await context.remote.store.invoices.issue({ input: { at: context.now() } })
```

| instead of                          | take                 | answers                           |
| ----------------------------------- | -------------------- | --------------------------------- |
| `Date.now()`                        | `context.now()`      | milliseconds since the epoch      |
| `Math.random()`                     | `context.random()`   | a number in `[0, 1)`              |
| `crypto.randomUUID()` and the like  | `context.id()`       | a new id, made as an entity's is  |

Their answers are kept like any other step, so a run sees one moment, one random value and one
new id however many attempts it takes. They exist on [every operation
context](../components/8.context.md); taking them from there by habit costs nothing.

The same goes for anything else an argument is built from. If the effect reads its own entity,
the entity is read again on every attempt, and a step whose arguments come from it is made again
if it moved.

### Keep nothing in the process

The next attempt is taken by whichever replica is free — after a restart or a deployment, by a
process that has never seen the run. What the context answered is given back wherever that is.
What the operation kept in its own process is not:

```javascript
// counts in whichever process the attempt runs in, and not across attempts
context.state.sent = (context.state.sent ?? 0) + 1

// kept with the run, and given back wherever the next attempt runs
const sent = await context.remote.store.notifications.send({ input })
```

A module variable, a cache in memory, a file on the local disk and `context.state` are all
whatever the process of the next attempt holds. Anything a later attempt depends on comes from a
step, or from state the operation writes and reads back.

## What you can count on

**What answered is not asked again**, within one run: after an exception, after the process died,
after a deployment, and after a parked task is put back within the window.

**A finished run delivered again makes nothing.** It is given everything back.

**A call keeps its identity.** A call made from the effect carries the same identity on every
attempt, so a callee that declares [`once`](3.idempotency.md) refuses a repeat of it.

**Two copies of a run agree.** If a run is delivered twice at the same moment, both go on with
the answer the first of them kept. `context.id()`, `context.now()` and `context.random()` are the
exception: each copy has its own value until one is kept, so a step one copy builds from it may
be made by the other as well.

**An answer is the same every time.** What a step answers is given as it will be given back,
on the attempt that made it too, so the operation reads the same thing on every attempt.

## What you still handle

**A step that took effect may be made again.** If the process dies after a step took effect and
before its answer was kept, the next attempt makes it again.

- A call to another component arrives with the same identity. Declare the callee `once`, and the
  repeat is refused there.
- A `fetch` to a third party is sent again. Make it safe to repeat, or pass a key the third
  party deduplicates on — `context.id()` gives one that is the same on every attempt:

```javascript
const key = context.id()

await context.fetch('courier', {
  method: 'POST',
  headers: { 'idempotency-key': key },
  body: JSON.stringify({ order: order.id })
})
```

**Among identical steps, which branch gets which answer is not fixed.** Two concurrent calls
with the same arguments are the same request, and each is given one of the two answers — possibly
the other one than the first time. A later step built from the answer *and* something of the
branch's own then has new arguments and is made again. Calling `context.id()` in two concurrent
branches is the common case; take the ids before branching.

**What cannot be kept is refused.**

- A step that answers with a stream throws `Unrecordable`, and the run is parked at once.
- An answer is kept as one document of at most 16 MB. A larger one fails to be kept, and the
  step throws.

**A run that used up its attempts is parked**, like any other message — see
[parked messages](1.delivery.md#parked-messages). Put back within its window, it picks up where
it stopped. Put back later, it starts from the beginning.

**An error still ends the run.** Continuity changes what a retry repeats, not what is retried: a
returned error is final, as for any task.

## Deployment

The runs are kept by a component the runtime brings along, `continuity.journal`, in MongoDB. An
application whose components declare `continuity` gets it deployed as a service of its own; there
is nothing to add to the Context for that.

Its database is given like any component's. A Context whose `mongodb` names one address for
everything has nothing to add; one that names addresses per namespace names this one too:

```yaml
# context.toa.yaml
mongodb:
  store: mongodb://store.mongo.example.com
  continuity: mongodb://mongo.example.com
```

While that database is away, runs wait and pick up when it is back.

## Checklist

- The operation is an `effect`, named under `continuity` with a window of at least `600`.
- It is called with `task: true` or from a receiver, never waited for.
- Every value that would differ between attempts comes from `context`.
- Nothing a later attempt needs lives in the process.
- Callees that change state declare `once`; requests to third parties carry a key.
- No step answers with a stream.
