# Call Chains

Every call and every event carries the path that led to it: the *chain*. You never write one or
read one. The runtime uses it to refuse two things no single component can check for itself — a
call that has gone round in a circle, and a write made under a request that may only read. The
model's [Call Chains](../../model/reliability/6.chains.md) explains the idea.

## Cycles

Suppose `store.accounts` keeps the number of a customer's open orders, updated by a receiver on
order changes, and somebody later adds a receiver in `store.orders` that refreshes an order
whenever its customer's account changes:

```yaml
# components/store.accounts/manifest.toa.yaml
receivers:
  store.orders.updated: recount
```

```yaml
# components/store.orders/manifest.toa.yaml
receivers:
  store.accounts.updated: refresh
```

Each declaration is reasonable alone. Together an order update changes the account, which
changes the order, which changes the account. Every operation on the way succeeds, so nothing
would ever stop it.

The runtime does:

```
LoopException: 'store.orders.refresh' is hop 3 of this chain
  trail: exposition > store.orders.refresh > ~store.orders.updated >
         store.accounts.recount > ~store.accounts.updated > store.orders.refresh
```

### What is refused

| a call is refused when                     | default |
| ------------------------------------------ | ------- |
| it would enter the same hop this many times on one chain | `3` |
| its chain has grown to this many hops      | `32`    |

The refusal happens **before the operation runs**: nothing is read, committed or published by
the refused call. What ran before it stays as it was — in the example each component has been
written twice by the time the third visit is refused.

Both limits count one path, not a period of time:

- An operation that calls the same endpoint fifty times, in a loop or concurrently, has made
  fifty chains of one hop. None is a circle.
- Work that repeats on a schedule is not a circle: every firing of a [pulse](../flow/1.pulses.md)
  starts its own chain.

### Reading the chain

Read it from the left. The repeated hop is the circle.

| hop          | written                    |
| ------------ | -------------------------- |
| an operation | `store.orders.refresh`     |
| an event     | `~store.orders.updated`    |
| a service    | `exposition` (the gateway) |

What you change is almost never the operation. **A circle is closed by a subscription** — a
receiver that writes back to the component whose event it listens to — so the `~` hops are where
to look. Every component has `created`, `updated`, `deleted` and `sync` events whether it
declares them or not, so a receiver on somebody's `sync` or `updated` is enough to make one.

The usual fixes: listen to a narrower event with a
[condition](../components/6.events.md), so that the write a receiver makes does not publish the
event that triggers it; or stop writing when there is nothing to change — a transition that sets
[`DISCARD`](../components/3.errors.md) commits nothing and publishes nothing.

### Where you meet it

- **In a call you made.** Thrown at the `await`, like any other exception, with the chain in
  its `trail`. Let it through. Over HTTP it is a `500`: the client did nothing wrong, the wiring
  did.
- **In an event or a [task](4.tasks.md).** Nobody is waiting, and a circle is the same on the next
  attempt, so the message is [parked at once](1.delivery.md#parked-messages) with the chain as its
  reason. This is the usual case, since circles are mostly closed by events.

### A delay is a hop

A call made later with `context.delay` is made by the chain that asked for it. An operation that
re-arms itself — delaying a call to its own endpoint — is therefore a circle, however slow. Say
that the next run is a fresh start with `unchained`:

```javascript
await context.delay(endpoint, request, { interval, overdue: null, unchained: true })
```

[Delays](../flow/3.delays.md) covers `context.delay` itself.

### An operation meant to be re-entered

Some operations come back to themselves on purpose: a walk over a tree of categories, or a
workflow where every finished step moves the whole on, which starts the next step, whose end
moves it on again. Declare such an operation `unchained`:

```yaml
# components/store.catalog/manifest.toa.yaml
operations:
  walk:
    type: computation
    unchained: true
    input:
      type: object
      properties:
        category: { type: string }
        depth: { type: integer }
      required: [category, depth]
    output:
      type: integer
```

```javascript
// components/store.catalog/operations/walk.js
export async function computation (input, context) {
  if (input.depth === 0) return 0 // the stop is yours to write

  const below = await context.remote.store.catalog.walk({
    input: { category: input.category, depth: input.depth - 1 }
  })

  return below + 1
}
```

Every call to an `unchained` operation begins a chain of its own: the chain it arrives with is
dropped, and the one it passes on begins with it. Neither limit applies to a circle that runs
through it, so it goes round for as long as its own code keeps calling. **Stopping is the
operation's responsibility.** A circle elsewhere in the chain is refused as before.

### Settings

Two environment variables, for the whole deployment:

| variable            | meaning                                                          | default |
| ------------------- | ---------------------------------------------------------------- | ------- |
| `TOA_TRAIL_REPEATS` | times one hop may be entered before the call is refused; `0` refuses nothing | `3` |
| `TOA_TRAIL_DEPTH`   | hops a chain may grow to                                         | `32`    |

`TOA_TRAIL_REPEATS=0` is the way out if a deployment starts refusing calls it has always made.
Read the refused chain before leaving it off: a handshake that goes `a > b > a > b > a` is three
visits to `a`, and it stays refused until it is written another way or `a` is declared
`unchained`. The depth limit still applies.

## Chains that may only read

A client, a cache or a crawler repeats a `GET` freely, on the understanding that it changes
nothing. Whether that holds depends on everything the request reaches, so the runtime holds the
whole chain to it:

```
SafetyException: 'store.orders.approve' may change state, and this call may only read
```

### Where one begins

Only at the gateway:

| begins a readonly chain                 | does not                                              |
| --------------------------------------- | ----------------------------------------------------- |
| `GET`, `HEAD`                           | `POST`, `PUT`, `PATCH`, `DELETE`, `LOCK`, `UNLOCK`    |
| a procedure or a tool served under `GET` | an event, a task made elsewhere, a pulse, a delayed call |

What the gateway does on its own behalf around a request — reading a credential, re-issuing one,
the components a directive calls — is not part of the chain.

### What is refused

A call to an operation that *may* change state, whether or not this call of it would:

| type                                              | under a readonly chain |
| ------------------------------------------------- | ---------------------- |
| `observation`, `computation`                      | proceeds               |
| `transition`, `assignment`, `effect`, `unmanaged` | refused                |

So an observation that looks harmless but calls a transition somewhere below fails when it is
reached by `GET`:

```javascript
// components/store.orders/operations/summary.js
export async function observation (input, entry, context) {
  // refused under GET: `touch` is a transition
  await context.remote.store.accounts.touch({ query: { id: entry.customer } })

  return { status: entry.status, total: entry.total }
}
```

The refusal happens **where the call is made, before it is sent**. Nothing is read, committed,
published or queued. A component cannot clear the mark for a call of its own: there is nothing
to pass in the request that does it.

### Where you meet it

- **In a call you made.** Thrown at the `await`. Let it through; over HTTP it is a `500`. The
  client asked for what the route offered — the route is what is wrong.
- **`context.delay`.** Handing a call over stores something, so arming a delay under a readonly
  chain is refused whatever the delayed call would have been.
- **A task.** A readonly chain may hand a task to a safe operation, and that operation is in the
  chain too. If it then calls something unsafe, nobody is waiting and the refusal is permanent,
  so the message is [parked at once](1.delivery.md#parked-messages).
- **An event.** Never. An event comes from a state change, and a readonly chain makes none.

### Saying otherwise

A route can state that its reading method does change state, with the
[`io:readonly`](../gateway/6.io.md#read-only-calls) directive:

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:id/confirmation:
    GET:
      endpoint: confirm # a transition, reached by a link in an email
      io:readonly: false
```

`HEAD` is served by the same method, and writes with it. The directive is inherited, so a node
states it for every method under it; `io:readonly: true` holds any other method to reading.

**This is not recommended.** "Safe" is HTTP's rule, not the runtime's, and other software acts
on it: a crawler walking your links, a browser prefetching one, and a cache revalidating a stored
reply each make the request, and none of them asked for what it does.

A tool exposed to a model tells the truth either way: its read-only hint follows what the route
declares, not the verb it is served under.

## What a chain is not

**Not a security boundary.** Both rules stop an application wired wrongly by accident. Neither is
a defence against a participant that deliberately sends something else.

**Not a view beyond the runtime.** A chain covers calls to operations and the events between them. A
lock taken through `context.atom`, a request through [`context.fetch`](../services/4.fetch.md), and
whatever an `unmanaged` operation does with its storage are not calls to an operation, and a
readonly chain does not restrain them.

## What you write

| you want                                        | you write                                   |
| ----------------------------------------------- | ------------------------------------------- |
| circles refused                                 | nothing                                     |
| an operation that re-enters itself on purpose   | `unchained: true` on the operation          |
| a delayed call that starts afresh               | `unchained: true` in the options of `context.delay` |
| a `GET` that only reads, all the way down       | nothing                                     |
| a `GET` that writes                             | `io:readonly: false` on the route           |
