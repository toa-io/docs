# Delivery and Retries

[Errors](../components/3.errors.md) teaches the two ways a call can go wrong: an operation
*returns* an error to refuse, and anything *thrown* is an exception. This article is about what
happens next: who is told, what is tried again, and what your operations have to tolerate because
of it. The reasoning behind the rules is in the model's
[Delivery](../../model/reliability/1.delivery.md).

Everything depends on one question: is anybody waiting for the outcome?

## When somebody waits

A call made with `context.remote` or `context.local` suspends the caller until the reply arrives:

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, entry, context) {
  if (entry.status !== 'pending') return new Error('NOT_PENDING')

  const reply = await context.remote.store.accounts.debit({
    query: { id: entry.customer },
    input: { amount: entry.total }
  })

  if (reply instanceof Error) return reply // INSUFFICIENT_FUNDS, passed on

  entry.status = 'approved'

  return entry
}
```

Three things can come back, and you write code for one of them:

- **An output.** Carry on.
- **An error.** A value; check `reply instanceof Error`, then handle it or return it as your own
  answer. Nothing is retried because of it.
- **An exception.** Thrown at the `await`. Let it through: your operation then fails in turn, and
  the failure travels back to whoever started the chain. Over HTTP that is a `500`.

**The runtime does not run a failed operation again for a waiting caller.** Whoever waits decides
whether to ask again — at the far end that is usually the client.

Do not catch an exception you cannot answer. An operation that swallows a failure from below
returns a wrong answer instead of a failure, and nothing retries a wrong answer.

### What is absorbed for you

- **The component is not running** — restarting, being deployed, scaled to nothing. The call
  waits for it. An ordinary call has no deadline, so the caller sees a slow call, not a failure.
- **The process that took the call stopped before answering.** Another replica takes it.

The second point has a consequence: the operation may have done its work before the process
stopped, and another replica does it again. A call somebody waits for can run twice too.

## When nobody waits

Two kinds of work have no caller to tell:

- an operation invoked by a [receiver](../components/7.receivers.md), because of an event;
- a [task](4.tasks.md), a call made with `task: true`.

Take a component `store.reports` that keeps a sales line per order, under the order's id, and
updates it when the order is approved:

```yaml
# components/store.reports/manifest.toa.yaml
namespace: store
name: reports

entity:
  properties:
    total: { type: integer }
    changes: { type: integer }
    applied: { type: integer }
  blank:
    total: 0
    changes: 0
    applied: 0

operations:
  add:
    type: transition
    concurrency: retry
    input:
      type: object
      properties:
        total: { type: integer }
        version: { type: integer }
      required: [total, version]

receivers:
  store.orders.approved: add
```

What `add` returns goes nowhere, so its two kinds of outcome mean this:

| `add` does                            | what happens to the message                      |
| ------------------------------------- | ------------------------------------------------ |
| returns an output                     | done                                             |
| returns an error                      | done — the refusal is final, and nobody reads it |
| throws, or a call it makes throws     | tried again, then kept                           |
| fails in a way that cannot pass later | kept at once                                     |

### An error ends the work

A returned error is an answer given to nobody. The message is finished and is not tried again. If
a refusal has to be visible, the operation makes it visible itself: it writes a state somebody
reads, which may publish an event.

### An exception is tried again

The message is delivered again after a pause that grows with each attempt:

| attempt | made after     |
| ------- | -------------- |
| 1       | —              |
| 2       | 1 second       |
| 3       | 10 seconds     |
| 4       | 30 seconds     |
| 5       | 90 seconds     |

That is five attempts over a little more than two minutes. A dependency that was away for a
moment, or a conflict that resolves, clears on its own this way. Meanwhile the component keeps
handling its other messages: only the message that failed waits.

A retried message goes back behind whatever arrived while it waited, and any replica may take the
next attempt.

**Do not throw to refuse.** A thrown refusal is retried for two minutes and then kept as though
something were broken.

### A failure that cannot pass is kept at once

Some failures are the same on every attempt, so the message is set aside on its first delivery:

- the request does not fit the operation's contract, or the reply does not;
- the query is malformed, or names a version that has passed;
- a task names an operation the component does not have;
- the call went [round in a circle](6.call-chains.md#cycles), or would write under a
  [chain that may only read](6.call-chains.md#chains-that-may-only-read);
- the operation used something its manifest does not declare.

A missing entity is *not* among them: an event about an entity can arrive before the one that
creates it, so "not found" is tried again.

### A message that keeps failing is kept

After the fifth attempt the message is *parked*: moved to a queue of its own on the broker, where
it stays until a person deals with it. It is never dropped, and it does not block the messages
behind it.

## Parked messages

One queue, `comq.parked`, holds every parked message of every component on that broker. A message
there is as it was published, with headers saying what happened to it:

| header            | what it says                                           |
| ----------------- | ------------------------------------------------------ |
| `x-comq-queue`    | the queue it was consumed from                         |
| `x-comq-exchange` | the exchange it was originally published to            |
| `x-comq-key`      | the routing key it was originally published with       |
| `x-comq-reason`   | the message of the exception that ended its attempts   |
| `x-comq-cause`    | the message of that exception's cause, when it has one |
| `x-comq-at`       | when it was parked, in milliseconds since the epoch    |
| `x-comq-attempt`  | which attempt its last delivery was                    |

A message parked at once says why in `x-comq-reason`, starting with the kind of failure, for
example the chain of a refused circle.

You hear about it two ways:

- the process logs an error, `AMQP message discarded`, with the queue and the exception message;
- the counter `toa.amqp.diagnostics` is incremented with `condition="discard"`. Alert on it.

What to do with one:

1. Read `x-comq-queue` and `x-comq-reason` to find which operation failed and why.
2. Fix the cause: deploy the fix, restore the dependency, correct the data.
3. Put the message back on the queue `x-comq-queue` names, with the broker's own tools, or
   remove it if the work is no longer wanted.

The queue grows until somebody drains it. Do not delete `comq.parked` or the `comq.retry.*`
queues on a running system: the second kind holds the messages that are waiting for their next
attempt.

## What an operation must tolerate

**An operation may run more than once for one message, and the run before may have got halfway.**
This is certain for anything an event or a task reaches, and possible for any call. Nothing
deduplicates it unless you ask. There are four ways to live with it, from the cheapest.

### Write a change that repeats safely

```javascript
// runs twice, counts twice
entry.changes += 1

// runs twice, ends the same
entry.status = 'approved'
```

Setting a value is safe. Accumulating is not.

### Skip what you have already applied

Every event is about one state of one entity, and that state has a `VERSION` that only grows.
Pass it to the operation and keep the last one applied:

```javascript
// components/store.reports/receivers/store.orders.approved.js
export const request = (payload) => ({
  query: { id: payload.id },
  input: { total: payload.total, version: payload.VERSION }
})
```

```javascript
// components/store.reports/operations/add.js
export async function transition (input, entry) {
  if (entry.applied >= input.version) return entry // a repeat, or a stale one

  entry.applied = input.version
  entry.total = input.total
  entry.changes += 1 // cumulative, and counted once per version

  return entry
}
```

The same check handles events that arrive out of order, which they may: see
[what subscribers can rely on](2.committed-events.md#what-a-subscriber-can-rely-on).

### Ask the runtime to apply it once

An operation that declares `once` changes state once per call, however many times the call
arrives. See [Idempotency](3.idempotency.md).

### Take care of what leaves the system

An email, a payment through a third party, any request to the outside is made again in full on
every attempt. Either make it safe to repeat — most payment and messaging services accept a key
they deduplicate on — or record that you did it in the same state change, and read that first.
An effect that is a sequence of such steps can be declared resumable: see
[Continuity](5.continuity.md).

## Summary

|                          | somebody is waiting            | nobody is waiting                  |
| ------------------------ | ------------------------------ | ---------------------------------- |
| recipient absent         | the call waits                 | the message waits                  |
| returned error           | given to the caller            | ends the work                      |
| exception                | thrown where the call was made | tried again, then parked           |
| failure that cannot pass | thrown where the call was made | parked at once                     |
| process stopped mid-work | another replica takes the call | another replica takes the message  |
| who decides to try again | the caller                     | the runtime                        |
