# Collection Streams

An `enumerate` returns a page. A reader that needs the whole collection — an export, a search
index, a client that keeps a local copy — reads a *stream* instead: the entities one at a time,
at the cost of the one in hand, and afterwards only what changed. The concept is described in
[Collection Streams](../../model/flow/2.collections.md).

## Reading a collection

A component that takes the generic prototype already has a `stream` operation. Call it like any
other and iterate over the reply:

```javascript
// components/store.reports/operations/count.js
export async function computation (input, context) {
  const stream = await context.remote.store.orders.stream({
    query: { criteria: 'status==approved' }
  })

  let total = 0

  for await (const part of stream)
    if (part.entry !== undefined) total += part.entry.total

  return total
}
```

`store.reports` is a component that computes figures over orders. However many orders there are,
neither side holds more than one of them at a time.

## Parts

A stream does not yield bare entities. It yields *parts*, each one of three:

```json
{ "entry": { "id": "a1", "customer": "c7", "total": 1200, "VERSION": 4 } }
{ "removed": "a2" }
{ "token": "eyJ2IjoxLCJwIjoi..." }
```

| Part | Meaning | What a reader does |
| --- | --- | --- |
| `entry` | An entity of the collection: one it has, or one that changed in it. | Put it in the copy. |
| `removed` | The id of an entity that left the collection. | Drop it from the copy. |
| `token` | The point the reader has reached; the last part of a complete stream. | Keep it for the next read. |

"The collection" is what the query selects. An order that stops matching `status==pending` has
left the collection of pending orders: its reader is told `removed`, though the order still
exists. An order that starts matching arrives as an `entry`.

## An operation of your own

To do something with the entities where they are stored, declare an operation with the `stream`
scope. The Node bridge reads the scope from the name of the second parameter, `stream`:

```javascript
// components/store.orders/operations/export.js
export async function* observation (input, stream) {
  for await (const part of stream)
    if (part.entry !== undefined) yield toRow(part.entry)
}

function toRow (order) {
  return `${order.id},${order.customer},${order.total}\n`
}
```

The operation is handed the parts and answers what it makes of them. Here it answers a
[streamed reply](5.streamed-calls.md#streamed-replies) of CSV rows.

The scope is available to an `observation` and to an `effect`. Where the scope cannot be read
from the source, declare it:

```yaml
# components/store.orders/manifest.toa.yaml
operations:
  export:
    type: observation
    scope: stream
```

An operation that yields its own values, as `export` does, hides the token from its caller. One
that is to be read again from a token passes the `token` part through, or returns the stream as
it is — which is all the prototype's `stream` does.

## Reading only what changed

A complete stream ends with a token. Present it on the next read, with the same query, and the
answer is what happened in the collection since, followed by a new token.

`store.search` keeps a search index of pending orders in step with `store.orders`:

```javascript
// components/store.search/operations/sync.js
export async function effect (input, context) {
  const query = { criteria: 'status==pending' }

  if (context.state.token !== undefined) query.token = context.state.token

  const stream = await context.remote.store.orders.stream({ query })

  for await (const part of stream) {
    if (part.entry !== undefined) await index.put(part.entry)
    else if (part.removed !== undefined) await index.drop(part.removed)
    else if (part.token !== null) context.state.token = part.token
  }
}
```

The first run, without a token, transfers the collection. Every later run transfers the
difference, and nothing if nothing changed. A reader applies both the same way. Called by a
[pulse](1.pulses.md), `sync` keeps the index a few minutes behind at most.

Here the token is kept in [process memory](6.stateful.md#process-memory) for brevity; a reader
whose copy outlives its process keeps the token beside the copy.

## Windows

A reader may take a bounded number of entities at a time by stating `limit`:

```javascript
const stream = await context.remote.store.orders.stream({
  query: { criteria: 'status==pending', limit: 100, token }
})
```

Every window ends with a token, and the next read carries the last one received:

| Read | Answer |
| --- | --- |
| `limit: 100` | 100 entries, then token `T1` |
| `limit: 100`, `token: T1` | the next 100, then `T2` |
| `limit: 100`, `token: T2` | 42 entries — a short window, so the collection has been read — then `T3` |
| later: `limit: 100`, `token: T3` | what changed since, then `T4` |

A window that comes back with `limit` entries is continued by its token. A window that comes back
short has reached the end of the collection, and its token continues with changes.

### Order

Windows are ordered by `id` ascending by default. `sort` may order them by `id` or by `CREATED`,
in either direction; entities that share a creation time are ordered by `id`.

```javascript
query: { criteria: 'status==pending', sort: ['CREATED:desc'], limit: 100 }
```

These two never change for an entity, so an entity stays on one side of a window boundary for the
whole read. **`sort` by any other property is refused beside `limit` or `token`**, with
`RequestContract`. Changes arrive in the order they happened.

### The first window only

`stop: true` reads the first window and nothing deeper. Its token continues with changes:

```javascript
query: { criteria: 'customer==c7', sort: ['CREATED:desc'], limit: 20, stop: true }
```

That is the shape of a feed: the newest twenty, then whatever changes. A change arrives for any
entity of the collection, including those deeper than the window that the reader never received.

## The query

A stream reads what an `entries` observation reads:

| Key | Meaning |
| --- | --- |
| `criteria` | Selects the collection. |
| `projection` | The properties of each `entry`. |
| `sort` | Any order for a read without `limit` or `token`; otherwise `id` or `CREATED`. |
| `limit` | The size of a window. Absent, the whole collection is read at once. |
| `token` | The token of the previous read. |
| `stop` | `true` to read no deeper than the first window. |
| `deleted` | `true` to include deleted entities. |

`omit` is not available: a window is continued by its token, not by an offset.

A deleted entity is left out of the collection, and its deletion arrives as `removed`. With
`deleted: true` it is part of the collection, and a deletion arrives as an `entry` with `DELETED`
set.

## What a reader handles

**Keep the higher `VERSION`.** An entity may arrive twice, once in a window and once as a change.
Where the query states a `projection`, include `VERSION` in it, and keep the later one.

**A stream that ends without a token was cut.** A stream that failed ends too, so the token is
what says a stream is whole. Read again with the token already held: nothing read before it is
lost.

**A token can expire.** The storage remembers changes for a limited time. A read from a token
past it throws the `StateHistory` exception. Drop the copy and read the collection again, without
a token.

**A token belongs to its query.** Presented with other criteria or another order, it is refused
with `QuerySyntax`.

**A token may be `null`.** A storage that keeps no history of changes still ends a full window
with a token that continues the collection, and ends a complete stream with `{ "token": null }`:
the collection is whole and there is nothing to continue from. What changed is learned by
reading it again. The `sync` example above handles this by not keeping a `null`.

## What it requires from the storage

With MongoDB, a stream ends with a token of changes where two things hold.

**MongoDB runs as a replica set.** A standalone server streams and windows a collection, and ends
with `token: null`.

**The collection keeps images** of what an entity was before each change. That is how a change
that takes an entity out of the collection is told from a change outside it. Turn them on with a
[migration](../components/12.migrations.md):

```yaml
# components/store.orders/migrations/0003-images.yaml
- images: true
```

Without the migration, streams of the component end with `token: null`.

Things to know before turning images on:

- They cost a copy of every changed entity for as long as the replica set's oplog holds it.
- A token lasts as long as the oplog holds the point it names. The size of the oplog and the rate
  of writes decide how long that is.
- A read from a token costs what the whole replica set wrote since that point, whatever of it
  concerns the collection. Read often enough to keep that small.
- `- images: false` in a later migration stops keeping them. Tokens issued before are then
  refused as expired.

## Over HTTP

The gateway serves a stream to a client as a multipart response, with the token as a query
parameter; see [Collection streams](../gateway/9.streams.md#collection-streams).

## Streams or events

Both tell an interested party that state changed. A component that reacts to a change subscribes
to an [event](../components/6.events.md). A reader that keeps a copy of a collection current uses
a stream: it starts from the current state, pulls when it wants to, and is told what left the
collection as well as what entered it.
