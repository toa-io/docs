# Delays

A delay hands one call over to be made later. Unlike a [pulse](1.pulses.md), it is stored: it
survives restarts and deployments, and it is made when its time comes even if nothing was running
in between. Use it when each item has its own moment — this order in thirty minutes, that
reminder in a week. The concept is described in [Cadence](../../model/flow/1.cadence.md#delay).

## The smallest delay

`store.notifications` sends email. It reminds a customer about an order a day after it was
created. A component that delays calls names the extension in its manifest; there is nothing to
declare under it:

```yaml
# components/store.notifications/manifest.toa.yaml
cadence: ~

receivers:
  store.orders.created: watch
```

That puts `delay` on the operation context:

```javascript
// components/store.notifications/operations/watch.js
const DAY = 24 * 3600 * 1000

export async function effect (order, context) {
  await context.delay(
    'store.notifications.remind',
    { input: { order: order.id } },
    { interval: DAY, overdue: null }
  )
}
```

A day later `store.notifications.remind` is called with `{ input: { order } }`, as if a component
had called it then.

`context.delay` takes three arguments:

1. **The endpoint**, as `<namespace>.<component>.<operation>`. It may be an operation of any
   component, the caller's own included. A component without a namespace is addressed as
   `default.<name>.<operation>`.
2. **The request**, exactly what an ordinary call would pass: `input`, `query`, or both. Pass
   `null` for an operation that takes nothing.
3. **The options**, described next. `interval` and `overdue` are both required.

A component that already declares pulses or schedules under `cadence` has `context.delay` too.
`toa types` adds it to the component's generated `Context` type.

## Options

| Option | Meaning |
| --- | --- |
| `interval` | Milliseconds from now; `0` or more. |
| `overdue` | Milliseconds the call may be late and still be made, or `null` for no bound. |
| `unchained` | `true` when the call begins a chain of its own; see [A delay is a hop](#a-delay-is-a-hop). |

Note the unit: a delay is stated in **milliseconds**, where the manifest's `cycle` and a
schedule's `overdue` are in seconds.

### How late is too late

A call is normally made at the moment it is due. It is late when something failed: the target was
away, nothing was running to make the call. `overdue` says what to do then.

| `overdue` | Meaning |
| --- | --- |
| `null` | No bound: made whenever it can be, however late. |
| `0` | On time or never. |
| a number | Made if no more than that many milliseconds late. |

**There is no default, and you state it on every call.** Only the caller knows whether a late
call is still the right call. A payment reminder is useful whenever it arrives; an order that
expires at noon expires on time or not at all. The wrong `null` makes a stale call, and the wrong
number drops a call and says nothing.

A call that passed its bound is dropped silently.

## Cancelling

`context.delay` answers an id, and the id cancels the call. `store.orders` gives a customer
thirty minutes to pay, and takes the deadline back when the order is approved:

```javascript
// components/store.orders/operations/checkout.js
const MINUTE = 60 * 1000

export async function transition (input, order, context) {
  order.deadline = await context.delay(
    'store.orders.lapse',
    { query: { id: order.id } },
    { interval: 30 * MINUTE, overdue: 10 * MINUTE }
  )
}
```

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, order, context) {
  // ...

  await context.delay.cancel(order.deadline)

  order.status = 'approved'
}
```

`deadline` is a string property of the order's entity. `cancel` throws where the id was never
issued.

**A cancellation is reliable only while the call is more than a minute away** (the
[discreteness](#discreteness)). Closer than that it is a race, and the call may already be on its
way. So do not rely on cancellation alone: `lapse` checks the state it finds.

```javascript
// components/store.orders/operations/lapse.js
export async function transition (input, order) {
  if (order.status !== 'pending') return new Error('NOT_PENDING')

  order.status = 'cancelled'
}
```

## What a delay promises

**A call may be made more than once.** Where a second one would cost something, the target
refuses it, as `lapse` does; see [Idempotency](../../model/reliability/3.idempotency.md).

**A call may not be made at all**, in four ways:

- **The caller crashed** between committing its own change and handing the call over. Arming a
  delay is not part of the operation's commit, and nothing can tell that it was lost. Where the
  semantics allow it, hand the call over first, as `checkout` does: it arms the deadline before
  its change to the order is committed.
- **It expired**: it was given an `overdue`, and nothing could make it in time.
- **It was cancelled.**
- **It could not be made.** One attempt is given. A call that could not go out is reported in the
  logs and dropped, not tried again.

What happens after the call was handed to its target is the target's concern. An exception the
target throws is reported by the component that threw it, under the rules for
[tasks](../../model/reliability/4.tasks.md).

**The call waits for its target.** A target that is not running when the call is made takes it
when it is back.

**A horizon of years costs nothing**, but the call is worth no more than the target that will be
there to take it. By then the operation may be gone, or may no longer accept that input, and the
attempt is spent either way.

## Discreteness

Stored calls are looked over on a period called *discreteness*: 60 seconds by default, set in the
[Context](#running-cadence). Everything about timing is measured against it.

- **A delay shorter than the discreteness is served late.** A five-second delay under the default
  lands up to a minute after it was asked for. A delay longer than the discreteness is made on
  time.
- **An `overdue` shorter than the discreteness can be missed when nothing is wrong**, and
  combined with a short delay almost always will be. State an `overdue` several times the
  discreteness, or `null`.
- **A cancellation closer than the discreteness to the call is a race.**
- **One replica takes at most 200 calls per pass**, oldest first. When more come due at once, the
  rest are taken on a later pass and are late by that much, and it is logged.

A call is due by the clock of the replica that took the `delay` and made by the clock of the
replica that dispatches it. Ordinary clock disagreement between machines is covered.

A call that must be made, or cancelled, within seconds of its time needs a discreteness of
seconds, at the price of looking the calls over that much more often.

## Where a delay is refused

**From a chain that may only read.** Arming a delay is a write, whatever the delayed call itself
would do. An operation reached through the gateway by `GET` or `HEAD` runs in a
[readonly chain](../../model/reliability/6.chains.md#chains-that-may-only-read):
`context.delay` throws there, nothing is stored and no id is answered.

**With `instance` in the request.** A delayed call is made later by whichever process takes it,
so it cannot name a process of a [stateful operation](6.stateful.md). It is refused with
`RequestContract`.

**With a stream in the request.** A [streamed call](5.streamed-calls.md) cannot be deferred.

## A delay is a hop

A delayed call continues the [chain](../../model/reliability/6.chains.md) that armed it. An
operation that delays a call to itself is therefore going round in a circle, however slowly, and
its third round is refused.

Nothing repeats a delayed call: it is made **once**. What repeats is an operation that arms the
next call as it finishes this one. `unchained: true` says the call being armed begins a chain of
its own:

```javascript
// components/store.notifications/operations/chase.js
const DAY = 24 * 3600 * 1000

export async function effect (input, context) {
  // ... remind about the unpaid invoice

  await context.delay(
    'store.notifications.chase',
    { input },
    { interval: DAY, overdue: null, unchained: true }
  )
}
```

Without the option the second `chase` is hop two of one chain and the third is refused. With it
they go on for as long as the operation keeps arming them.

An operation declared `unchained: true` in the manifest begins a chain of its own on every call,
delayed or not, and needs no option:

```yaml
# components/store.notifications/manifest.toa.yaml
operations:
  chase:
    unchained: true
```

Prefer a [pulse](1.pulses.md) for recurring work where it fits: one timer for the component
instead of a stored call per item, and no chain to break. Re-arm a delay when each item has its
own rhythm.

## Running cadence

Delays and schedules are kept and made by a service the runtime ships. It is deployed with the
application automatically, as a service of its own, and keeps the calls in the Context's MongoDB.
Three things are yours to provide or choose.

**Redis, through [`atomicity`](../services/6.shared-decisions.md#setting-it-up).** Delays, schedules
and a component's pulses all rely on it:

```yaml
# context.toa.yaml
atomicity:
  redis: redis://redis.example.com
```

**Without it none of them is made.** Only a pulse declared
[`scope: replica`](1.pulses.md#work-that-belongs-to-a-process) runs without it. The address is
usually stated [per environment](../running/2.environments.md):

```yaml
# context.toa.yaml
atomicity:
  redis@local: redis://localhost:6379
  redis@production: redis://redis.example.com
```

**The `cadence` annotation**, optional:

```yaml
# context.toa.yaml
cadence:
  discreteness: 60 # seconds between passes over the stored calls
  regions: [0] # the regions whose calls this deployment makes, by rank
```

| Key | Default | Meaning |
| --- | --- | --- |
| `discreteness` | `60` | Seconds between passes; an integer, at least `1`. See [Discreteness](#discreteness). |
| `regions` | the deployment's own rank | Ranks of the regions whose stored calls, pulses and schedules this deployment makes. |

**The service, when you run locally.** `toa mono` starts it by itself, because a component
declares `cadence`. With `toa compose`, name it, or run it beside the composition:

```shell
$ toa compose ./components/* --service cadence
$ toa serve cadence
```

Without the service running, `context.delay` has nothing to hand the call to, and no delayed or
scheduled call is made.

A composition may also run the service in its own pods instead of a separate deployment, by listing
`cadence` under its `services`; see
[Services in a composition](../running/3.compositions.md#services-in-a-composition).

### Taking over a lost region

In an application deployed as several [regions](../../model/running/5.regions.md), every region
holds every region's delayed calls and makes only its own, so there is nothing to configure while
all of them are up.

When a region is gone, redeploy a surviving one naming the lost rank beside its own. It then
makes both regions' delayed calls, and the pulses and schedules
[declared for the lost one](2.schedules.md#one-region-or-every-region):

```yaml
# context.toa.yaml
cadence:
  regions: [0, 1] # this region's calls, and those of the region that was 1
```

The delayed calls it takes over it keeps, so nothing has to be handed back.

**Two regions naming one rank make every one of its calls twice**, and nothing detects it. Write
the table once and deploy it everywhere.

A cancellation reaches the region that owns the call as any other write does, so across regions
it is slower than within one.
