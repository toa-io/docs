# Addresses and Credentials

The database, the broker, the cache: every connector and extension that connects to something is
told where it is in the Context, and all of them read addresses the same way. This article
describes that one scheme, and how the credentials that go with an address are supplied.

A component never sees any of this. Its manifest says *that* it stores an entity or uses the
stash; the Context says *where*.

## One address for everything

The simplest declaration is a URL:

```yaml
# context.toa.yaml
amqp: amqp://rmq.example.com
mongodb: mongodb://mongo.example.com
stash: redis://redis.example.com
```

Every component of the application then uses that broker, that database and that cache.

Which keys take addresses:

| Key | Address of | Taught in |
| --- | --- | --- |
| `amqp` (`amqp.context`) | the message broker | [Connectors](12.connectors.md#bindings) |
| `amqp.sources.<source>` | a broker of another system | [Connectors](12.connectors.md#brokers-of-other-systems) |
| `mongodb` | the database | [Connectors](12.connectors.md#storages) |
| `stash` | Redis for the stash | [Stash and State](5.stash-and-state.md) |
| `http` | components, for streamed calls | [Connectors](12.connectors.md#the-http-binding) |

`atomicity.redis` and the telemetry endpoints are addresses too, but plain ones: one value for
the whole application, without the per-component keys described below.

## Per environment

Addresses are the part of the Context that differs most between environments. Suffix the key:

```yaml
# context.toa.yaml
mongodb@local: mongodb://localhost:27017
mongodb@production: mongodb+srv://db.example.com

stash@local: redis://localhost:6379
stash@production: redis://redis.internal:6379

amqp:
  context:
    .@local: amqp://localhost:5672
    .@production:
      - amqp://rmq-0.internal:5672/store
      - amqp://rmq-1.internal:5672/store
```

An address is a URL as the technology understands it, so it may carry a path, such as a broker's
virtual host, and options in its query string.

## Different addresses for different components

Written as a map, a declaration gives an address for everything, for a namespace, or for one
component. `.` is the default:

```yaml
# context.toa.yaml
mongodb:
  .: mongodb://mongo.example.com # everything else
  store: mongodb://store.mongo.example.com # every component of `store`
  store.orders: mongodb://orders.mongo.example.com # `store.orders` alone
```

**A component takes the longest key that matches its id:**

| Component | Takes |
| --- | --- |
| `store.orders` | `orders.mongo.example.com` |
| `store.accounts` | `store.mongo.example.com` |
| `billing.invoices` | `mongo.example.com` |

`mongodb: mongodb://mongo.example.com` is the same map with the single key `.`.

A component that matches no key, where there is no `.`, is refused, and the message names the
component.

**A component without a namespace is in `default`.** Its id is `default.<name>`, and that is what
a key has to say: `default` for all such components, `default.catalog` for one.

## Several addresses under one key

A key may hold a list, and every component that resolves to it is given all of them:

```yaml
amqp:
  context:
    .:
      - amqp://rmq-0.example.com
      - amqp://rmq-1.example.com
```

Numbered hosts can be written as a range in braces:

```yaml
amqp:
  context: amqp://rmq-{0-2}.example.com
```

which is `rmq-0`, `rmq-1` and `rmq-2`. What several addresses *mean* is up to whoever reads them:
the broker binding uses them as nodes to connect to, while the stash uses only the first.

## Credentials

**An address never contains credentials.** One that does is refused:

```text
Pointer URI 'mongodb://user:pass@mongo.example.com' must not contain credentials.
```

A user name and a password are supplied separately, as a
[secret](../running/9.secrets.md#credentials) in the environment the application is deployed to.
There is one secret per *key* of the declaration, not per component: every component that resolved
to a key shares it, and so does every address listed under it.

The secret's name is made of the declaration's identifier and the key, with dots turned into
dashes:

| Declaration | Key | Secret |
| --- | --- | --- |
| `mongodb` | `.` | `mongodb.default` |
| `mongodb` | `store` | `mongodb-store` |
| `mongodb` | `store.orders` | `mongodb-store-orders` |
| `amqp.context` | `.` | `amqp-context.default` |
| `amqp.context` | `store.orders` | `amqp-context-store-orders` |
| `amqp.sources.payments` | — | `amqp-sources-payments` |

Each holds the keys `username` and `password`:

```shell
$ toa conceal mongodb-store-orders username=orders password=secret
$ toa conceal amqp-context.default username=store password=secret
```

`toa conceal` deploys the secret with the prefix `toa-` (`toa-mongodb-store-orders`). A secret
created by other means has to carry that prefix itself.

There is no need to work the names out. Ask for the list:

```shell
$ toa export secrets production
toa-amqp-context.default:
  username
  password
toa-mongodb.default:
  username
  password
```

A deployment into an environment that lacks any of them is refused before anything is built,
naming what is missing:

```text
Secrets are not deployed: toa-mongodb.default/username, toa-mongodb.default/password
```

Addresses on protocols that carry no credentials have no secret: `redis`, `http` and `https`.
TLS client configuration through this scheme is not available.

### Locally

For a local run the credentials are variables in the `.env` file that
[`toa env`](../running/2.environments.md#the-local-environment) writes. It adds one pair per secret,
and what is already in the file is kept when it runs again:

```shell
$ toa env --interactive   # asks for each value
$ toa env --dev           # fills in development defaults
```

Running locally is covered in [Running Locally](../start/3.running.md).

## Keys of configuration are a different thing

Do not confuse the two kinds of secret:

- the credentials of an *address* are named after the declaration and supplied as described
  here;
- a secret *value of a component's configuration*, such as the key of an external API, is
  declared `format: secret` in the manifest, referenced as `$NAME` in the Context, and deployed
  into the secret `configuration`. See [Configuration](2.configuration.md#secrets).

External HTTP systems a component calls through `context.fetch` are of the second kind: their
address and key are configuration of the calling component
([Calling the Outside World](4.fetch.md#addresses-and-keys)).
