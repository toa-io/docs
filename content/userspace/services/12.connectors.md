# Connectors

Operations are *run*, state is *stored*, and calls are *carried*. The technology behind each verb
is a connector: a *bridge* runs code, a *storage* keeps entity state, a *binding* carries calls
and events. There is a default of each, and most components never name one. The model article
[Connectors](../../model/platform/6.connectors.md) explains the separation.

A developer meets them in a few places: where a connector is named, and in what the defaults ask
of you.

| Kind | Default | Named in the manifest by |
| --- | --- | --- |
| Storage | MongoDB (`mongodb`) | `entity.storage` |
| Binding | the message broker (`amqp`) | `bindings`, per component or per operation |
| Bridge | Node.js (`node`) | `bridge`, per component or per operation |

A connector is named by its shortcut, by a package reference such as
`@toa.io/storages.mongodb`, or, for one of your own, by a relative path.

## Storages

### The default: MongoDB

A component with an `entity` stores it in MongoDB without saying so. All that is needed is the
address in the Context:

```yaml
# context.toa.yaml
mongodb: mongodb://mongo.example.com
```

The address may differ per namespace or component, takes the `@environment` suffix, and its
credentials are supplied as a secret; all of that is in
[Addresses and Credentials](13.addresses-and-credentials.md):

```yaml
# context.toa.yaml
mongodb:
  .: mongodb://mongo.example.com
  store.orders: mongodb://orders.mongo.example.com
```

What to know about it as a developer:

**One database per application, one collection per component.** The database is named after the
application (the Context's `name`). Components of different applications sharing a MongoDB do not
share data. The name of a database cannot exceed 63 bytes, and a process whose name is longer
does not start.

**Use a replica set.** [Committed events](../reliability/2.committed-events.md) and
[`once`](../reliability/3.idempotency.md) rely on writing a record together with the entity, which
MongoDB does only as a replica set or a sharded cluster. Against a standalone server, events are
published without that guarantee, and the process says so at startup. Run a single-member replica
set locally to have the same behavior as in production.

**URL options are passed to the driver.** A connection option the driver does not know stops the
component at startup:

```text
option foo is not supported
```

**An outage is waited out.** If the database becomes unreachable, calls wait and are answered
when it is back; the component reconnects by itself.

**Indexes and data changes are migrations**, written as files in the component's `migrations`
directory. See [Migrations](../components/12.migrations.md). Only this storage applies them.

**Deleted entities stay as tombstones**, and moments are stored as dates. Both matter when you
write an index; see [Manifest](../components/1.manifest.md) and
[Migrations](../components/12.migrations.md).

**Collection streams need images.** A stream of a collection ends with a token from which changes
can be read later. This requires a replica set and a collection that keeps what each record was
before a change, which a migration turns on:

```yaml
# components/store.orders/migrations/0003-images.yaml
- images: true
```

Images cost a copy of every changed record for as long as the database's operation log holds it. `-
images: false` stops keeping them, and a token issued before that is then refused with `410`. A
token is valid for as long as the operation log still holds the point it names, which depends on the
log's size and the rate of writes. Reading from a token scans the log from that point, so it costs
in proportion to everything the replica set wrote since. Streams are covered in
[Collection Streams](../flow/4.collection-streams.md).

**Commands are traced.** Each storage command is a `client` span named `<command> <collection>`
in the trace of the operation that caused it, and an observation of
`toa.storage.query.duration` when metrics are on. This adds no waiting to the operation.

### No storage: `storage: ~`

A component that declares an entity but should keep nothing sets its storage to null:

```yaml
# components/store.quotes/manifest.toa.yaml
name: quotes
namespace: store

entity:
  storage: ~
  properties:
    product: { type: string }
    price: { type: integer }
```

Every write is accepted and discarded, and every read finds nothing. Nothing needs to be
configured in the Context for it.

A component that declares migrations against it does not start:

```text
Component 'store.quotes' declares migrations, which storage '@toa.io/storages.null' does not apply
```

A component with no `entity` at all uses no storage; this is the usual form for components made
of computations and effects.

### What a storage must be able to do

Some features depend on what the storage can guarantee:

| The storage can | Needed for |
| --- | --- |
| write an entity atomically with a record beside it | committed events, `once` |
| write several entities atomically | transitions over a set |
| remember the order of committed writes | changes in collection streams |

A component that asks for a feature its storage cannot support does not start, and says which
feature and which storage.

## Bindings

### The default: the message broker

Calls between compositions, events and [tasks](../reliability/4.tasks.md) travel through an AMQP
broker. A component declares nothing for it; the Context gives the address:

```yaml
# context.toa.yaml
amqp: amqp://rmq.example.com
```

This is short for:

```yaml
# context.toa.yaml
amqp:
  context:
    .: amqp://rmq.example.com
```

`context` is the broker the application itself runs on. As with other addresses it can be given
per namespace or component and may hold several addresses of one cluster:

```yaml
amqp:
  context:
    .@local: amqp://localhost:5672
    .@production:
      - amqp://rmq-0.example.com
      - amqp://rmq-1.example.com
```

Credentials are a secret; see [Addresses and Credentials](13.addresses-and-credentials.md).

### Brokers of other systems

A receiver can consume an event published by a system that is not part of the application. It
names the binding and a *source*:

```yaml
# components/store.orders/manifest.toa.yaml
receivers:
  payment_received:
    binding: amqp
    source: payments
    operation: approve
```

and the Context says which broker that source is:

```yaml
# context.toa.yaml
amqp:
  context: amqp://rmq.example.com
  sources:
    payments: amqp://rmq.payments.example.com
```

Each source has credentials of its own. Receivers themselves, including how the event's payload
becomes a request, are covered in [Receivers](../components/7.receivers.md).

### Calls within a composition

Components that share a composition call each other in memory. Nothing is declared, and the
calling code is the same. This binding is the platform's own and cannot be named in a manifest.

### The HTTP binding

A streamed call, one whose input holds a stream, cannot pass through a broker. It is carried by
the `http` binding, directly to a replica of the component. An operation that takes a stream must
have that binding declared beside the default:

```yaml
# components/store.pictures/manifest.toa.yaml
bindings: [amqp, http]
```

Otherwise the component does not start:

```text
Operation 'resize' takes a stream, which none of its bindings carries
```

`bindings` can also be given for a single operation:

```yaml
operations:
  resize:
    bindings: [amqp, http]
```

The `http` binding carries streamed calls only. Ordinary calls, tasks and events of the same
component still go through the broker, so `amqp` stays in the list.

In a deployment nothing more is needed: each component is addressed at the service the deployment
renders for it, on port `8005`. The `http` annotation states addresses where that default does
not apply, typically for a local run where several processes share one machine:

```yaml
# context.toa.yaml
http@local:
  store.pictures: http://127.0.0.1:31006
  store.catalog: http://127.0.0.1:31007
```

A key applies to the component it names and to everything under it; `.` is every component. A
process reads the same map for the other side: it listens on the port in the address of each
component it serves.

Each streamed call opens a connection of its own and closes it when it ends, so a call that is
neither large nor long costs more this way than it saves. Calls between components of one
composition pass the stream as it is and need none of this. Streamed calls are covered in
[Streamed Calls](../flow/5.streamed-calls.md).

## Bridges

### The default: Node.js

Operations are JavaScript or TypeScript modules in the component's `operations` directory. Its
conventions are the subject of [Operations](../components/2.operations.md) and
[TypeScript](../components/11.typescript.md).

### The Bash bridge

An operation can be a shell script. Name the bridge for the whole component:

```yaml
# components/store.tools/manifest.toa.yaml
name: tools
namespace: store

bridge: bash

operations:
  checksum:
    input:
      properties:
        text: { type: string }
```

```shell
#!/bin/bash
# components/store.tools/operations/checksum.sh

while [[ "$#" -gt 0 ]]; do
  case $1 in
    --text) text="$2"; shift ;;
  esac
  shift
done

echo -n "$text" | sha256sum | cut -d ' ' -f 1
```

or for one operation of a component whose other operations are JavaScript:

```yaml
# components/store.catalog/manifest.toa.yaml
operations:
  checksum:
    bridge: bash
    input:
      properties:
        text: { type: string }
```

```javascript
// components/store.catalog/operations/label.js
export async function computation (input, context) {
  const sum = await context.local.checksum({ input: { text: input.title } })

  return `${input.title} (${sum.slice(0, 8)})`
}
```

The rules of a Bash operation:

- **Input** must be an object. Each property is passed to the script as a named argument,
  `--name value`, with the value converted to a string.
- **Output** is what the script writes to standard output, as a string.
- **Exit code `1`** makes the operation return an error whose message is what the script wrote to
  standard error. Any other non-zero code is an exception.
- There is no entity state and no operation context, so only computations are possible.
- The script does not see the platform's environment: every `TOA_*` variable is removed.

The bridge is mainly a demonstration that operations in different languages take part in one
application: they call one another and receive one another's events, because what passes between
them is defined by the model and not by the language.
