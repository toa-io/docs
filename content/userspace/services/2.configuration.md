# Configuration

A component declares the values it needs as a schema, reads them from the operation context, and
the Context supplies them. It never reads an environment variable or a file. The concept is in
the model article [Configuration](../../model/platform/2.configuration.md).

## Declaring and reading

`store.orders` refuses orders above a limit. The limit is configuration:

```yaml
# components/store.orders/manifest.toa.yaml
name: orders
namespace: store

configuration:
  schema:
    type: object
    properties:
      limit:
        type: integer
        minimum: 0
  defaults:
    limit: 5000
```

```javascript
// components/store.orders/operations/create.js
export async function transition (input, order, context) {
  if (input.total > context.configuration.limit)
    return new Error('LIMIT_EXCEEDED')

  Object.assign(order, input, { status: 'pending' })
}
```

`configuration` takes two keys and nothing else:

| Key | |
| --- | --- |
| `schema` | Required. A [JSON Schema](https://json-schema.org) of the configuration object. |
| `defaults` | Optional. The values the component runs with unless the Context says otherwise. |

`context.configuration` is one object, already validated against the schema. A value that does not
fit never reaches an operation, so operations do not check it.

### Defaults

`defaults` must fit the schema. It is the only way to give a value a default: **a `default` keyword
written inside the schema fills nothing**. What a component receives is the stored object, whole.

Mark a value `required` when there is no sensible default and the Context has to supply it:

```yaml
configuration:
  schema:
    properties:
      sender: { type: string, format: email }
    required: [sender]
```

### Nested values

The schema can be as deep as the values need. Objects and arrays work as they do in any JSON
Schema:

```yaml
# components/store.catalog/manifest.toa.yaml
configuration:
  schema:
    properties:
      currencies:
        type: array
        items:
          type: object
          properties:
            code: { type: string }
            rate: { type: number }
          required: [code, rate]
  defaults:
    currencies:
      - code: EUR
        rate: 1
```

```javascript
const { rate } = context.configuration.currencies.find((c) => c.code === input.currency)
```

### With a prototype

A component that takes a prototype declaring configuration extends it: the two schemas and the two
sets of defaults are combined, and the operations of the component read the prototype's values
and its own from the same object.

## Values from the Context

The `configuration` annotation holds values per component, keyed by component id:

```yaml
# context.toa.yaml
configuration:
  store.orders:
    limit: 10000
```

The Context's values stand over the manifest's `defaults` value by value: naming `limit` here
leaves every other default as the manifest declares it. The result is what the component is
deployed with, its *deployed defaults*. A component of the `default` namespace may be written by
its bare name.

A key that names no component, or a component that declares no configuration, stops the command
that reads the Context:

```text
Component 'foo.bar' does not request configuration or does not exist.
```

### Per environment

A value can differ between environments with the
[`@environment` suffix](../running/2.environments.md), at any depth:

```yaml
# context.toa.yaml
configuration:
  store.orders:
    limit: 10000
    limit@staging: 100
  store.notifications:
    provider: console
    provider@production: smtp
    sender@local: shop@localhost
    sender@production: shop@example.com
```

A key with only suffixed forms has no value from the Context in the other environments, which
then take the manifest's default if there is one.

### The values service's resources

One key of the annotation is not a component. `resources` states what the service that holds
configuration values may take in a deployment:

```yaml
# context.toa.yaml
configuration:
  resources:
    cpu: [200m, 1000m]
    memory: [200Mi, 500Mi]
  store.orders:
    limit: 10000
```

Each is a pair of request and limit; `resources: ~` deploys the service without any. A component
that is really named `resources` is written with its namespace: `default.resources`.

## Secrets

A value that must not be stored with the sources is declared with `format: secret`:

```yaml
# components/store.notifications/manifest.toa.yaml
configuration:
  schema:
    properties:
      provider: { type: string, enum: [console, smtp] }
      sender: { type: string, format: email }
      password: { type: string, format: secret }
    required: [provider, sender]
```

The Context then gives a *reference*: an uppercase name prefixed with `$`.

```yaml
# context.toa.yaml
configuration:
  store.notifications:
    password: $SMTP_PASSWORD
```

**A plain string in place of a secret is refused:**

```text
'password' is a secret and must be given as a $NAME reference.
```

A secret may sit anywhere in the schema, inside nested objects and array items, and several
components may refer to the same name.

### Reading a secret

On the context a secret is not a string. Call `unwrap()` where the value is used:

```javascript
// components/store.notifications/operations/send.js
export async function effect (input, context) {
  const { provider, sender, password } = context.configuration

  await deliver(provider, {
    from: sender,
    to: input.to,
    text: input.text,
    password: password?.unwrap()
  })
}
```

Converted to a string, serialized to JSON or inspected, a secret gives `<REDACTED>`. Returning
`context.configuration` from an operation or logging it therefore does not leak the value, but
log specific values rather than the whole object anyway.

### Supplying the value

Secret values are not deployed with the application. Deploy them once per environment, into the
[secret](../running/9.secrets.md#putting-secrets-in-the-cluster) named `configuration`:

```shell
$ toa conceal configuration SMTP_PASSWORD=xxxxxxxx
```

Several values can be given in one command, and values are added to a secret that already exists.

For a local run, `toa env` writes one empty variable per reference into `.env`, named
`TOA_CONFIGURATION__<NAME>`:

```text
TOA_CONFIGURATION__SMTP_PASSWORD=
```

Fill it in; values already in the file are kept when `toa env` runs again. The variable is not
visible to the component's code, which reads the secret only through `context.configuration`.

## Running one component with given values

Setting `TOA_CONFIGURATION_<NAMESPACE>_<NAME>` to a YAML or JSON object gives a component its
configuration directly. The manifest's `defaults` fill what the object leaves out, the schema is
applied, and nothing else is consulted:

```shell
$ TOA_CONFIGURATION_STORE_ORDERS='{"limit":1}' toa compose components/store.orders
```

Use it to try a component with values that differ from the Context, or to run it where the values
service is absent.

## Where values come from when a component starts

A component asks the *values service* for its configuration when it starts and waits until it is
answered; nothing of the component serves before that. The service is part of the application:
it is deployed with it, runs inside `toa mono`, and is started on its own with:

```shell
$ toa serve configuration
```

What the service answers with is, in order:

1. the latest object created for the component while running, if there is one;
2. otherwise the values the component was deployed with: the manifest `defaults` with the
   Context's values over them.

The first of these is how configuration changes without a deployment, and is the subject of
[Changing Configuration](3.configuration-values.md).

## What configuration is not for

- Addresses of the database, the broker or the cache belong to the Context annotations of the
  connectors that use them ([Addresses and Credentials](13.addresses-and-credentials.md)).
- Data that users of the application change is entity state, with operations and events of its
  own.
