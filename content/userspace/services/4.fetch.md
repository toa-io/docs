# Calling the Outside World

An operation reaches an HTTP API outside the application through `context.fetch`. It is the
standard `fetch`, with two additions made by the platform: optional retries, and telemetry for
every request.

Nothing is declared for it. Every component has `context.fetch`, with no manifest key and no
Context annotation.

## A request

`store.notifications` sends an email through a provider's HTTP API:

```javascript
// components/store.notifications/operations/send.js
export async function effect (input, context) {
  const response = await context.fetch('https://mail.example.com/messages', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ to: input.to, text: input.text })
  })

  if (response.status === 422) return new Error('REJECTED')

  if (!response.ok) throw new Error(`Mail provider answered ${response.status}`)

  const { id } = await response.json()

  return { id }
}
```

The arguments and the returned `Response` are those of the
[WHATWG `fetch`](https://developer.mozilla.org/en-US/docs/Web/API/fetch): a URL, a `URL` object
or a `Request`, and the usual options.

Two habits to keep:

- **Decide what a status means.** `context.fetch` does not throw on `4xx` or `5xx`. Return an
  error for an answer that is a refusal your operation declares, and throw for one that is a
  failure, so that the platform treats each correctly (see
  [Errors](../components/3.errors.md)).
- **Consume or cancel the body.** Connections are pooled and reused automatically; a response
  whose body is neither read nor cancelled (`response.body.cancel()`) holds its connection.

The platform does not cache responses.

## Addresses and keys

The address of an external system and the key for it are configuration of the component that
calls it, with the key declared as a secret:

```yaml
# components/store.notifications/manifest.toa.yaml
configuration:
  schema:
    properties:
      url: { type: string, format: uri }
      key: { type: string, format: secret }
    required: [url, key]
```

```yaml
# context.toa.yaml
configuration:
  store.notifications:
    url: https://sandbox.mail.example.com
    url@production: https://mail.example.com
    key: $MAIL_KEY
```

```javascript
const { url, key } = context.configuration

const response = await context.fetch(`${url}/messages`, {
  method: 'POST',
  headers: { authorization: `Bearer ${key.unwrap()}` },
  body: JSON.stringify(message)
})
```

See [Configuration](2.configuration.md#secrets) for supplying the secret's value.

## Retries

Retries are off unless you ask for them with `retry` in the second argument:

```javascript
const response = await context.fetch(`${url}/messages`, {
  method: 'POST',
  body: JSON.stringify(message),
  retry: { attempts: 3 }
})
```

| Option | Default | |
| --- | --- | --- |
| `attempts` | required | How many times the request is made at most, the first one included. |
| `expected` | `200`–`299` | The statuses that end the attempts. Any other status is tried again. |
| `delay` | `100` | Milliseconds before the second attempt. |
| `factor` | `2` | What the delay is multiplied by after each attempt. |

```javascript
const response = await context.fetch(`${url}/messages/${id}`, {
  retry: {
    attempts: 5,
    expected: [200, 404],
    delay: 200,
    factor: 3
  }
})
```

How it behaves:

- An attempt is repeated after an unexpected status and after a network failure.
- A `Retry-After` header in the response takes precedence over the calculated delay.
- When the attempts run out on an unexpected status, **that last `Response` is returned**, with
  its body untouched. Check the status even with retries on.
- When they run out on a network failure, the error is thrown.
- The bodies of the unexpected responses in between are discarded; you do not see them.
- Aborting the request through its `signal` also ends a wait between attempts.

### What cannot be retried

A request whose body is a `ReadableStream`, or a `Request` object that already carries a body,
cannot be sent twice. Asking for more than one attempt with such a body throws a `TypeError`:

```text
Cannot retry a request with a non-replayable body
```

Such bodies work without `retry`, or with `attempts: 1`.

### Retries and the platform's own

A request made on behalf of an event or a task is already retried by the platform when the operation
throws ([Delivery and Retries](../reliability/1.delivery.md#when-nobody-waits)). Retries here are
for riding out a short hiccup inside one run of the operation; keep `attempts` and delays small, and
let a longer outage fail the operation.

**The remote system sees every attempt.** Retry only requests it can safely receive twice, or
send it an idempotency key if it supports one.

## What is recorded

Every call is traced without any code. A call appears as one span named after the method and the
origin, with one nested span for each attempt actually made:

```text
POST https://mail.example.com
├── attempt 1
├── attempt 2
└── attempt 3
```

The outer span carries the final status and the number of attempts; each attempt carries its
number and its status. An attempt that failed on the network is marked as failed; the outer span
is marked only when the whole call failed.

**The path, the query string, headers and bodies are not recorded**, so keys and personal data in
them do not reach the telemetry backend.

With metrics configured, the platform also records, per origin:

| Metric | Type | Labels |
| --- | --- | --- |
| `toa.fetch.duration` | histogram, seconds | `origin`, `method` |
| `toa.fetch.responses` | counter | `origin`, `method`, `status` |
| `toa.fetch.retries` | counter | `origin` |

One attempt is one observation, so a retried request counts several times. See
[Traces](8.traces.md) and [Metrics](9.metrics.md).
