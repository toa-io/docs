# Changing Configuration

Configuration can be changed while the application runs, without a deployment. This article
covers how: over HTTP, from an operation, or in the page the platform serves, and what happens to
such changes when you deploy again. It continues [Configuration](2.configuration.md).

## The smallest change

Configuration values are held by a component the platform brings, `configuration.values`. With
the gateway running, creating a configuration for `store.orders` is one request:

```http
POST /configuration/values/store.orders/ HTTP/1.1
authorization: Token ...
content-type: application/yaml

configuration:
  limit: 20000
```

The answer carries the `id` of the object created and the `epoch` it belongs to:

```yaml
id: 7d8e…
epoch: 3f2a…
```

Every running replica of `store.orders` receives the new object and uses it from then on; a
replica that starts later gets it too. Delivery takes a moment and is not simultaneous across
replicas.

Three things to know before using it:

- **What you send is the whole configuration.** Nothing fills in a value you leave out, neither
  the manifest's `defaults` nor the previous object. Send every value the component needs.
- It must satisfy the component's schema. A value that does not, or an unknown component, is
  answered `422`.
- A secret is sent as its `$NAME` reference, exactly as in the Context. A plain string in its place
  is refused. The value behind the name is not changed this way: it is whatever was deployed with
  [`toa conceal`](../running/9.secrets.md#putting-secrets-in-the-cluster).

## Reading

```http
GET /configuration/values/store.orders/ HTTP/1.1
authorization: Token ...
```

answers with what the component currently runs with and the schema it is checked against:

```yaml
configuration:
  limit: 20000
schema:
  type: object
  properties:
    limit: { type: integer, minimum: 0 }
epoch: 3f2a…
created: 1767225600000
revision: null
```

| Field | |
| --- | --- |
| `configuration` | The values. Secrets appear as their references. |
| `schema` | The schema from the manifest. |
| `epoch` | Identifies the schema; see [Schema changes](#schema-changes). |
| `created` | When the object was created; `0` for deployed defaults that nobody replaced. |
| `revision` | Identifies the deployed defaults when they are what is served; `null` for a created object. |

A component without configuration is answered `404`.

`GET /configuration/values/` lists every component that declares configuration, ordered by
component name, each with the fields above and its `component` id.

## Resetting

```http
DELETE /configuration/values/store.orders/ HTTP/1.1
authorization: Token ...
```

answers `204` and brings the component back to its deployed defaults. A reset is more than
restoring the values of that moment: the component *follows* its defaults again, so a later
deployment that changes them in the Context changes what the component runs with.

An unknown component is answered `422`.

## Resources and roles

| Method | Path | Role |
| --- | --- | --- |
| `GET` | `/configuration/values/` | `system:configuration:get` |
| `GET` | `/configuration/values/:component/` | `system:configuration:get` |
| `POST` | `/configuration/values/:component/` | `system:configuration:create` |
| `DELETE` | `/configuration/values/:component/` | `system:configuration:create` |

`POST` and `DELETE` record the identity that made the request as the `originator` of the change.
Granting roles to identities is covered in [Roles and Bans](../identity/7.roles.md#granting).

## The page

The values service serves a page that lists the configured components, creates configurations
and resets them. It is published at `/.configuration/` on the hosts the Context declares for
ingress, and listens on port `8003`:

```yaml
# context.toa.yaml
ingress:
  hosts:
    - api.example.com
```

```text
https://api.example.com/.configuration/
```

The host must be one the gateway serves, because the page reads the API above on its own origin.
Reading needs the `system:configuration:get` role; creating and resetting need
`system:configuration:create`. A component running on a created configuration is marked in the
list, and reset is offered only for those.

The page is always published; the annotation has no switch for it.

## From an operation

`configuration.values` is an ordinary component, so an operation of yours can call it. This is how
to build a change into the application itself, for instance a back-office operation that adjusts
the limit:

```javascript
// components/store.orders/operations/limit.js
export async function effect (input, context) {
  const reply = await context.remote.configuration.values.create({
    input: {
      component: 'store.orders',
      configuration: { limit: input.limit },
      originator: { id: input.operator }
    }
  })

  if (reply instanceof Error) return reply
}
```

```yaml
# components/store.orders/manifest.toa.yaml
operations:
  limit:
    input:
      properties:
        limit: { type: integer, minimum: 0 }
        operator: { type: string }
      required: [limit, operator]
    errors: [UNKNOWN_COMPONENT, INVALID_CONFIGURATION]
```

Its operations:

| Operation | Input | Reply |
| --- | --- | --- |
| `get` | `{ component, epoch? }` | `{ configuration, schema, epoch, created, revision }`, or `null` when there is none |
| `fetch` | `[{ component, epoch }]` | `[{ component, epoch, configuration, created, revision }]` |
| `list` | — | `[{ component, epoch, schema, configuration, created, revision }]` |
| `create` | `{ component, configuration, originator }` | the stored object |
| `reset` | `{ component, originator }` | the stored object, holding the deployed defaults and their `revision` |

`create` answers the errors `UNKNOWN_COMPONENT` and `INVALID_CONFIGURATION`; `reset` answers
`UNKNOWN_COMPONENT`. `originator` is an object with the `id` of whoever makes the change.

`get` without `epoch` reads the deployed one. Asked for an epoch the deployment does not know, it
answers without a `schema`.

### The event

Creating and resetting both publish `configuration.values.created`, with the object as stored as
its payload. The object of a reset carries a `revision`; a created one does not. A component can
receive it like any other event, for instance to keep an audit trail:

```yaml
# components/store.audit/manifest.toa.yaml
receivers:
  configuration.values.created: record
```

## History

Nothing is edited in place. Each change is a new immutable object recording who made it, and the
configuration of a component is the last object created for it. Earlier objects stay.

## Deploying again

A deployment and a change made while running can disagree. The rules:

- **A created configuration outlives deployments.** While a component has one, changing its
  values in the Context has no visible effect. Reset the component to make it follow the Context
  again.
- **A component on its deployed defaults follows every deployment**, including one that changes
  only a value in the Context: such a deployment replaces the component's processes, as a change
  to its code does.

During a rolling deployment the values service of the previous release may still be answering. A
component does not take deployed defaults from it: it waits and asks again until the service of
its own release answers. While it waits it logs a warning, on the first refusal and every fifth
after:

```text
Configuration of another revision refused
```

with the `component`, its `epoch`, and the `expected` and `received` revisions. This ends by
itself when the rollout completes. A component that keeps logging it has a values service that
was not deployed with it.

A component started outside a deployment, by `toa compose` for example, takes whatever it is
served.

## Schema changes

Every configuration object belongs to the schema it was validated against. The schema's identity
is its *epoch*; changing anything in `configuration.schema` makes a new one.

After a deployment that changes the schema:

- the component starts from its deployed defaults for the new schema;
- configurations created for the old schema are not applied, and are not migrated.

So a value set long ago cannot break a release that changed its shape, and **a change made while
running has to be made again after a schema change** if it is still wanted. Put the values you
want to keep into the Context before deploying.

## What is not guaranteed

A change is not applied at one instant across the application. Replicas receive it one after
another, and work that spans several components, such as an order approved through a call to
`store.accounts`, can run partly with the old values and partly with the new.

Change configuration in ways that are safe during that window:

- make each new set of values compatible with operations already in progress;
- when a change needs new code, deploy the code so that it works with both the old and the new
  values, then change the values.
