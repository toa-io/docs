# Logs

An operation writes log entries through `context.logs`. The platform adds where the entry came
from and which request it belongs to, and delivers it to the console, to a log backend, or both.
The model article [Telemetry](../../model/platform/3.telemetry.md) gives the overall picture.

Nothing is declared for it: every component has `context.logs`.

## Writing an entry

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, order, context) {
  if (order.status !== 'pending') return new Error('NOT_PENDING')

  const reply = await context.remote.store.accounts.debit({
    query: { id: order.customer },
    input: { amount: order.total }
  })

  if (reply instanceof Error) {
    context.logs.warn('Order not approved', { order: order.id, reason: reply.code })

    return reply
  }

  order.status = 'approved'

  context.logs.info('Order approved', { order: order.id, total: order.total })
}
```

There are four methods, one per severity, with the same signature:

```text
context.logs.debug(message: string, attributes?: object): void
context.logs.info(message: string, attributes?: object): void
context.logs.warn(message: string, attributes?: object): void
context.logs.error(message: string, attributes?: object): void
```

They return nothing and are not awaited.

### Logging an error

An `Error` among the attributes is written with its `message`, `code`, `stack` and its `cause`
chain, so pass the error itself instead of picking fields out of it:

```javascript
try {
  await deliver(message)
} catch (error) {
  context.logs.error('Delivery failed', { to: input.to, error })

  throw error
}
```

An `Error` may also be passed as the attributes argument on its own.

## What an entry looks like

On the console an entry is one JSON line. `error` entries go to stderr, the rest to stdout:

```json
{
  "time": "2026-01-01T12:00:00.000Z",
  "severity": "INFO",
  "message": "Order approved",
  "attributes": { "order": "7d8e…", "total": 4200 },
  "context": { "namespace": "store", "component": "orders", "operation": "approve" },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7"
}
```

| Field | |
| --- | --- |
| `time` | ISO 8601 timestamp, to the millisecond. |
| `severity` | `TRACE`, `DEBUG`, `INFO`, `WARN` or `ERROR`. |
| `message` | The first argument. |
| `attributes` | The second argument, when given. |
| `context` | The component and operation that wrote the entry. Added by the platform. |
| `trace_id`, `span_id` | The trace and span in which it was written. Added by the platform. |

Because every entry written while serving one request carries the same `trace_id`, filtering a
log backend by it gives the whole story of that request across components. This works even for a
trace that was not sampled: the entries still carry its id, though the trace backend never
received it.

`TRACE` is not a method. It is the severity of the entries the platform writes for completed
spans; see [Traces](8.traces.md#seeing-spans-on-the-console).

## Levels

The Context sets the minimum severity that is written at all:

```yaml
# context.toa.yaml
telemetry:
  logs:
    level: info # trace < debug < info < warn < error
```

`info` is the default. An entry below the level is dropped where it is written; it reaches no
destination.

A level usually differs by environment:

```yaml
telemetry:
  logs:
    level: debug
    level@production: info
```

### One component at a different level

A key under `logs` that is a component id overrides the level for that component, so one
component can be examined in detail while the rest stay quiet:

```yaml
telemetry:
  logs:
    level: info
    store.orders:
      level: debug
```

Changing a level takes a deployment; it is part of the Context, not of
[configuration](2.configuration.md).

## Where entries go

There are two destinations, independent of each other:

- the **console**, which writes the JSON line and is on unless turned off;
- **`otlp`**, which sends entries to an OTLP/HTTP endpoint such as Loki or an OpenTelemetry
  Collector, and is off until an endpoint is given.

```yaml
# context.toa.yaml
telemetry:
  logs:
    level: info
    exporters:
      otlp:
        endpoint: http://loki:3100/otlp
```

With this, entries go to both. To stop writing to the console:

```yaml
telemetry:
  logs:
    exporters:
      console: false
      otlp:
        endpoint: http://loki:3100/otlp
```

Turn the console off where the platform under the application already collects the output of
every process into the same backend, or each entry arrives twice.

The level applies to both destinations: what a process writes is what it exports. Exporters are
set for the whole application; a per-component key under `logs` changes the level only.

The endpoint's options, the batching, and what happens when the backend is unavailable are the
same for all three signals and are described in
[Exporting Telemetry](10.exporting-telemetry.md).

### What a record carries over OTLP

| OTLP | From |
| --- | --- |
| body | the message |
| attributes | the attributes passed to the call, plus `namespace`, `component`, `operation` |
| `severityText`, `severityNumber` | the severity |
| trace and span ids | the trace in scope |

Records are exported under one resource per process:

| Resource attribute | Value |
| --- | --- |
| `service.name` | the application's name, or `exposition` for the gateway |
| `service.namespace` | the application's name |
| `deployment.environment.name` | the environment |

## When a process fails

A process that dies of an exception nobody caught, a promise rejection nobody handled, or a
failure to start prints the error to stderr and exits with code `1`. Before exiting it also sends
one record to the `otlp` exporter, so the reason is in the backend even where the console is off:

| | |
| --- | --- |
| message | `Process failed` |
| severity | `ERROR` |
| `reason` | `uncaught exception`, `unhandled rejection` or `command failed` |
| `error` | the error: its message, code and stack |

Searching the backend for `Process failed` is the quickest way to find out why a replica
restarted.

## Order of entries

Entries from different processes carry timestamps from different clocks, and exporters batch
them, so a backend's timeline across components is approximate. Do not conclude from two
timestamps on different machines which thing happened first.

Use the trace instead: `trace_id` groups the entries of one request, and `span_id` ties each to
the step it was written in, whose place among the other steps the [trace](8.traces.md) shows
exactly.

Two more things follow from timestamps having millisecond resolution: entries of one process
within the same millisecond have no reliable order, and two *identical* entries within the same
millisecond may be stored by a backend as one.

## What is not a log

Output of the `toa` command line is for whoever runs it. It has no severity and no context and
reaches no exporter. The same is true for anything an operation prints with the global `console`:
use `context.logs`.

## Writing good entries

**Keep the message constant; put what varies into attributes.** A constant message can be
searched, counted and alerted on.

```javascript
// no
context.logs.info(`Order ${order.id} approved`)

// yes
context.logs.info('Order approved', { order: order.id })
```

**State what happened, briefly.** A message is not an explanation or an instruction.

```javascript
// no
context.logs.error('Failed to send the email, please check the mail server configuration')

// yes
context.logs.error('Failed to send the email', { reason: 'SMTP error', status: response.status })
```

**Do not log what users supplied.** Names, addresses, message texts and the like are personal
data; log identifiers.

```javascript
// no
context.logs.info('Customer signed in', { name: customer.name })

// never
context.logs.error('Password is incorrect', { password: input.password })
context.logs.info('Payment received', { card: input.card })
```

**Do not log the configuration object.** Log the specific values you need.

```javascript
// no
context.logs.debug('Configuration', context.configuration)

// yes
context.logs.debug('Limits', { limit: context.configuration.limit })
```

**Choose the level by who needs the entry:**

| Level | Use for |
| --- | --- |
| `debug` | Development and troubleshooting. Not enabled in production. |
| `info` | The flow of the application: what was decided. |
| `warn` | Something that may need attention. |
| `error` | A failure that needs attention now. |

Do not log an error just because an operation *returns* one: a refusal is the operation working
as designed. Log what somebody will want to find later.
