# Shared Decisions

Replicas of a component run independently. `context.atom` is for the few things they have to
decide together: which replica does a piece of work, that only one does it at a time, and how
much all of them together have used of something. The model article
[Shared Decisions](../../model/platform/5.atomicity.md) explains when these are needed, and when
they are not.

Every component has `context.atom`. Nothing is declared in the manifest.

## Setting it up

The decisions are arbitrated by Redis, named in the Context:

```yaml
# context.toa.yaml
atomicity:
  redis: redis://redis.example.com
```

| Key | Default | |
| --- | --- | --- |
| `redis` | required | One address, or a list of an odd number of addresses. |
| `interval` | `5000` | How often a replica registers with its group, in milliseconds; at least `100`. |

```yaml
# context.toa.yaml
atomicity:
  redis@local: redis://localhost:6379
  redis@production:
    - redis://redis-0.example.com
    - redis://redis-1.example.com
    - redis://redis-2.example.com
  interval: 5000
```

Several addresses are **independent servers**, not the nodes of one cluster. A lock is taken on a
majority of them, so a minority can be lost without breaking it. Partitioning and metering use
the first address only. An even number is refused when the process starts:

```text
Atomicity takes an odd number of addresses, 2 given.
```

With a single address there is no majority: a Redis restart that loses the key, or a failover to
a replica that has not received it, can leave two holders of one lock.

The address carries no credentials.

The decisions of a component are shared by its replicas and by nobody else: a key used by
`store.orders` is not the same key in `store.accounts`, and applications sharing one Redis do not
meet.

The platform uses the same mechanism for itself. Pulses and the recovery of events that failed to
publish depend on it, so an application that uses those needs the annotation even if no operation
ever touches `context.atom`.

## Locking

`lock` runs a function while no other replica of the component holds the same key:

```javascript
// components/store.orders/operations/settle.js
export async function effect (input, context) {
  return await context.atom.lock('settlement', async () => {
    const batch = await collect(context)

    await submit(batch, context)

    return { submitted: batch.length }
  })
}
```

- The first argument is a key, or an array of keys to hold together.
- The call waits for as long as it takes to acquire the lock. There is no timeout; other replicas
  asking for the same key queue behind the holder.
- The lock is held for as long as the function runs and released when it returns or throws. What
  the function returns is what `lock` returns.
- A replica that dies while holding a lock stops extending it, and the lock expires.

### When the lock is lost

The lock is kept by being extended while the function runs. If extending fails, for instance
because Redis became unreachable, the function is told through an `AbortSignal` passed as its
argument. Check it before a step that must not overlap:

```javascript
await context.atom.lock('settlement', async (signal) => {
  const batch = await collect(context)

  if (signal.aborted) throw signal.error

  await submit(batch, context)
})
```

### What not to lock

Do not lock around changes to an entity. A transition is already protected by the entity's version,
and a repeated call by [`once`](../reliability/3.idempotency.md). Use a lock for work that reaches
outside the application and must not overlap with itself.

Waiting for a lock happens inside the operation, so it counts toward the operation's duration.

## Partitioning

Partitioning divides a fixed number of slots among the replicas that are running, so that each
slot belongs to exactly one replica at a time. `slots(total)` answers which of `total` slots this
replica owns:

```javascript
context.atom.slots(128) // [0, 2, 4, …] with two replicas, or null
```

Use it to split work that every replica is asked to do. `store.notifications` has a
[pulse](../flow/1.pulses.md) that drains an outgoing queue of an external mail system, divided into
16 partitions; each replica takes its share:

```javascript
// components/store.notifications/operations/drain.js
export async function effect (input, context) {
  const slots = context.atom.slots(16)

  if (slots === null) return

  for (const partition of slots)
    await drain(partition, context)
}
```

**`slots` returns `null` while the replica owns nothing**: at startup, during a rollout, or while
Redis is unreachable. Do nothing in that case. Do not treat `null` as "all of them".

A replica that has just joined owns nothing until the group has agreed on the new division, which
takes about two `interval`s. When a replica starts or stops, slots are redistributed among those
present, so the set a replica owns changes over time. Ask every time; do not remember the answer.

With one replica, it owns every slot: `slots(4)` is `[0, 1, 2, 3]`.

### Being told

Code that asks rarely, once an hour say, sees one moment only, and if that moment falls in a
rollout it loses the whole hour. `onassigned` calls a listener with the assignment instead, at
once and again each time it changes:

```javascript
const off = context.atom.onassigned((assignment) => {
  if (assignment === null) return pause()

  const { i, n } = assignment // this replica is number i of n

  resume(i, n)
})
```

- The listener is called once as it is added, with the assignment as it stands, and then only on
  a change: one arrived, was lost, or the group resized. It is not a heartbeat.
- `assignment` is `{ i, n }`, or `null` while the replica owns nothing. The slots owned out of
  `total` are `i`, `i + n`, `i + 2n`, … below `total`.
- The returned function removes the listener.
- **A listener must not throw.** One that does takes this replica out of its group: it owns
  nothing from then on and `slots` answers `null`.

## Metering

Metering counts usage per key across all replicas, so that a limit applies to the component as a
whole. Usage is kept as a *debt* in milliseconds that drains by itself, one millisecond per
millisecond:

```javascript
const [debt] = await context.atom.meter(['customer:42'], [1000])
```

`meter(keys, deltas)` adds each delta to the debt under the matching key and returns what each
debt has reached, counting what every replica has added.

To allow a customer ten requests to a paid external service per minute, charge each request a
tenth of a minute and refuse when more than a minute is owed:

```javascript
// components/store.catalog/operations/appraise.js
const COST = 6_000 // one request is worth 6 seconds: ten per minute
const WINDOW = 60_000

export async function effect (input, context) {
  const [debt] = await context.atom.meter([`appraise:${input.customer}`], [COST])

  if (debt > WINDOW) return new Error('TOO_MANY_REQUESTS')

  return await appraise(input.product, context)
}
```

A refused request has still added its cost, so a caller that keeps asking stays refused. To read
a debt without adding to it, pass a delta of `0`.

Several keys can be charged in one call, for instance a per-customer and a global one:

```javascript
const [mine, everyone] = await context.atom.meter(
  [`appraise:${input.customer}`, 'appraise'],
  [COST, COST]
)
```

## When Redis is not configured or not reachable

| | Without `atomicity` in the Context | Redis unreachable |
| --- | --- | --- |
| `slots` | `null` | `null` |
| `onassigned` | called with `null` | called with `null` when the assignment is lost |
| `lock` | throws `Locking requires atomicity.` | refused: the call fails |
| `meter` | throws `Metering requires atomicity.` | refused: the call fails |

An unreachable Redis does not prevent a component from starting. Work that depends on slots
pauses and resumes by itself; it does not proceed on a guess.

Under unusual conditions, such as clocks disagreeing at the moment work changes hands, a piece of
work can be done twice. Write work coordinated this way with the same care as an operation that
an event can reach more than once.

## What is recorded

With metrics configured:

| Metric | Type | Labels |
| --- | --- | --- |
| `toa.atomicity.lock.wait` | histogram, seconds | `group` |
| `toa.atomicity.locks` | gauge | `group` |

`group` is the component. A rising `lock.wait` means replicas are queueing for the same key.
