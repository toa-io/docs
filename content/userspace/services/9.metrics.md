# Metrics

Traces describe single requests; metrics describe the application in aggregate. The platform
records metrics for its own machinery, and a component declares and records the ones that are
about the business. The concept is in the model article
[Telemetry](../../model/platform/3.telemetry.md#metrics).

## Turning metrics on

**Nothing is measured until the Context configures metrics**, and nothing leaves a process until
an exporter is named:

```yaml
# context.toa.yaml
telemetry:
  metrics:
    exporters:
      otlp:
        endpoint: http://prometheus:9090/api/v1/otlp
```

| Key | Default | |
| --- | --- | --- |
| `interval` | `15000` | Milliseconds between collections, and so between exports. |
| `exporters.otlp.endpoint` | required | An OTLP/HTTP receiver of metrics; `/v1/metrics` is appended. |

The other options of `otlp` are in [Exporting Telemetry](10.exporting-telemetry.md). There is no
console exporter for metrics; reading them takes a backend.

Without this annotation `context.metrics` still works, so the code is the same everywhere. It
just records nothing.

## Declaring a metric

A component records only the metrics its manifest declares. `store.orders` counts approvals:

```yaml
# components/store.orders/manifest.toa.yaml
telemetry:
  metrics:
    approvals:
      type: counter
```

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, order, context) {
  // …
  order.status = 'approved'

  context.metrics.approvals.add(1)
}
```

In the backend the series is named after the component and the declared name:
`store.orders.approvals`. Two components may declare the same name without their series merging.

### Labels

A label splits a metric into series. Each label is declared with the values it admits:

```yaml
telemetry:
  metrics:
    approvals:
      type: counter
      labels:
        channel: [web, app, partner]
```

```javascript
context.metrics.approvals.add(1, { channel: input.channel })
```

Every declared label takes a value on every call.

**A value the label does not list is recorded as `UNDECLARED`.** The operation is not affected,
and the first such value for a label is written to the log:

```javascript
// input.channel is 'kiosk', which the manifest does not list
context.metrics.approvals.add(1, { channel: input.channel }) // → { channel: 'UNDECLARED' }
```

A label declared with `~` admits any value:

```yaml
labels:
  channel: [web, app, partner]
  warehouse: ~
```

Its cardinality is then yours to keep bounded. Never put an identifier of an order, a customer or
a request into a label: each distinct value is a series, kept for the whole retention.

`labels: ~`, or no `labels` at all, declares a metric with no labels.

### The three types

```yaml
# components/store.orders/manifest.toa.yaml
telemetry:
  metrics:
    approvals:
      type: counter
      labels:
        channel: [web, app, partner]
    totals:
      type: histogram
      unit: EUR
      buckets: [5, 20, 50, 100, 500]
      labels:
        channel: [web, app, partner]
    backlog:
      type: gauge
```

| Type | Recorded with | Declare it for |
| --- | --- | --- |
| `counter` | `add(amount, labels?)` | Something that happens: an approval, a rejection, a retry. It only goes up; what you read is its rate. |
| `histogram` | `record(value, labels?)` | A value whose distribution matters: an amount, a size. Yields quantiles, a count and a sum. |
| `gauge` | `set(value, labels?)` | A level that stands: rows pending, connections held. Only the last value before a collection is exported. |

```javascript
context.metrics.approvals.add(1, { channel: input.channel })
context.metrics.totals.record(order.total / 100, { channel: input.channel })
context.metrics.backlog.set(pending.length)
```

A counter's amount is positive. Choosing between the types:

- Something that can also go down is a gauge, never a counter.
- Do not count with a gauge: two changes within one interval export as one number.
- An outcome with a handful of values is a counter with a label, not a histogram.
- A duration needs no metric: [`context.span`](8.traces.md#adding-a-span) measures its task and
  the duration is recorded whether or not the trace is sampled.

### Declaration reference

| Key | |
| --- | --- |
| `type` | Required. `counter`, `gauge` or `histogram`. |
| `labels` | Label keys, each with a list of admitted values (strings, numbers or booleans) or `~` for any. |
| `unit` | What the values are in. |
| `buckets` | Histograms only, and required for them: the bucket edges, ascending. |

Names of metrics and labels start with a letter, continue with letters, digits and underscores,
and do not end with an underscore.

A malformed declaration is refused when the manifest is read, before anything starts: a name that
is not an identifier, an unknown type, a histogram without `buckets` or with buckets that do not
ascend, `buckets` on a metric that is not a histogram, or a label that lists `UNDECLARED` among
its values.

```text
Histogram 'totals' declares no buckets
Buckets of 'totals' must ascend
```

### Using an undeclared metric

Reading a name from `context.metrics` that the manifest does not declare throws:

```text
Metric 'aprovals' is not declared
```

This is a defect in the code, so the exception is a permanent one: where the operation runs for
an event or a task, the message is set aside on its first delivery instead of being retried. See
[Errors](../components/3.errors.md).

## What a metric cannot show

**Nothing shorter than `interval`.** One collection is one sample per series. A rate computed
over a window shorter than about four intervals has too few samples to trust.

Counters and histograms lose nothing to this: everything that happened between two collections
is in the next value. **A gauge loses the value itself**: a level that rose and fell between two
collections was never recorded.

**Nothing finer than a bucket edge.** A quantile is interpolated inside a bucket, so choose edges
around the values you care to tell apart. Changing the edges later starts the history over.

Counters and histograms are cumulative from the start of the process, and every series carries
`service.instance.id`, so replicas do not collide. A lost export costs resolution, not totals.

## What it costs

A metrics backend charges for series, not for measurements. Traffic is free: a series costs the
same at ten requests a second and at ten thousand. What costs is label values:

- every combination of label values is a series;
- every histogram bucket is a series of its own: twelve edges are fifteen series per combination;
- a series that stops being written still occupies the retention.

Declared labels make this visible in the manifest: the number of series a metric can produce is
the product of its lists. `interval` multiplies the data points of every series; raise it where a
backend bills by data point.

## What the platform records

These are recorded for every application once metrics are on. Durations are in seconds. The
platform's metrics are prefixed `toa`; a component's own are named after it.

### Operations and calls

| Metric | Type | Labels |
| --- | --- | --- |
| `toa.operation.duration` | histogram | `component`, `operation` |
| `toa.operation.errors` | counter | `component`, `operation`, `code` |
| `toa.operation.exceptions` | counter | `component`, `operation`, `code`, `outcome` |
| `toa.operation.inflight` | gauge | `component` |
| `toa.call.duration` | histogram | `component`, `operation` |
| `toa.call.exceptions` | counter | `component`, `operation`, `code` |
| `toa.call.inflight` | gauge | `component` |
| `toa.event.publish.duration` | histogram | `event` |

`toa.operation.*` is an invocation as the component serving it sees it. `toa.call.*` is the same
invocation as its caller sees it, transport included; `component` there is the callee.

The three outcomes of an operation divide as follows:

- an error it returned is `toa.operation.errors`, by the `code` it declares;
- an exception is `toa.operation.exceptions`, with `outcome` `permanent` or `transient`,
  depending on whether another attempt could succeed;
- success is the count of `toa.operation.duration` less the two, since the histogram observes
  every invocation.

So the error codes an operation declares are already counted per code. Do not declare a metric
for them.

`toa.call.exceptions` counts only failures of transmission, never an exception the callee sent
back, which is counted where it happened.

### Storage, broker, events

| Metric | Type | Labels |
| --- | --- | --- |
| `toa.storage.query.duration` | histogram | `provider`, `collection`, `operation` |
| `toa.storage.conflicts` | counter | `provider`, `collection` |
| `toa.amqp.published` | counter | `topology` (`request`, `task`, `event`) |
| `toa.amqp.diagnostics` | counter | `condition`, `shard` |
| `toa.outbox.pending` | gauge | `destination` |
| `toa.outbox.age` | gauge | `destination` |
| `toa.outbox.failures` | counter | `destination` |
| `toa.outbox.unassigned` | gauge | — |

`toa.storage.conflicts` counts concurrent changes to the same entity. Where the operation
declares `concurrency: retry` the change is retried and succeeds, and this counter is the only
place the conflict shows; otherwise it is also an exception of the operation.

`toa.outbox.age` is how long the oldest unpublished event has waited, and is the number to alert
on for event delivery. `toa.outbox.unassigned` rising means this replica recovers nothing, which
points at [atomicity](6.shared-decisions.md) being unreachable.

`condition` of `toa.amqp.diagnostics` is one of `return`, `discard`, `taken`, `remove`, `lost`,
`recover`, `flow`, `drain`, `close`, `error`, `reconnect`, `exhausted`, `open`.

route.

### Process

| Metric | Type | Labels |
| --- | --- | --- |
| `toa.process.loop.delay` | gauge | `quantile` (`p50`, `p90`, `p99`, `max`) |
| `toa.process.memory` | gauge | `kind` (`rss`, `heap`, `external`) |

Recorded by every process, the gateway included. `toa.process.loop.delay` covers the whole
interval, not only the moment it was read: a high `p99` means operations of that process are
blocking the event loop.

### Telling applications and environments apart

Every series carries the application's name as `service.namespace` and the environment as
`deployment.environment.name`. Several applications and environments can share one backend and
are separated by those, not by metric names.
