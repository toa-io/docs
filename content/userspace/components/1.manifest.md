# Manifest

A component is declared by `manifest.toa.yaml` in its directory. This article covers what
identifies a component and what describes its state; each following article adds one section of
the manifest.

## Name and namespace

```yaml
# components/store.orders/manifest.toa.yaml
name: orders
namespace: store
```

Together they are the component's address: other components call `store.orders`, and its events
are `store.orders.<event>`. Each is a letter followed by up to 31 letters and digits. The
namespace `system` is reserved.

A manifest that states no `name` takes both from its directory: `store.orders` is `orders` in
`store`. A component with no namespace at all belongs to `default`, and is addressed as
`default.orders`.

## Entity

`entity` describes the state of one object the component keeps. `properties` are
[JSON Schema](https://json-schema.org/) definitions:

```yaml
entity:
  properties:
    customer:
      type: string
    items:
      type: array
      items:
        type: object
        properties:
          product: { type: string }
          quantity: { type: integer, minimum: 1 }
        required: [product, quantity]
    total:
      type: integer
      minimum: 0
    status:
      type: string
      enum: [pending, approved, cancelled]
  required: [customer, total, status]
  blank:
    items: []
    status: pending
```

- **`required`** names the properties every stored object has.
- **`blank`** is what an object holds before anything is written to it. It need not be a whole
  valid object, but each value must fit the property it names.

State is validated against this schema on every write, whichever operation writes it. An invalid
state is never stored; the call fails with an exception.

Operations usually repeat parts of the entity schema in their input. YAML anchors keep one
definition:

```yaml
entity:
  properties:
    total: &total
      type: integer
      minimum: 0

operations:
  create:
    input:
      type: object
      properties:
        total: *total
```

A component that keeps no state declares no `entity`. It can still have operations —
computations and effects; see [Operations](2.operations.md#types).

## System properties

Besides what is declared, every object carries properties the runtime writes:

| Property | What it holds |
| --- | --- |
| `id` | The object's identity: 32 hexadecimal characters, assigned at creation. |
| `VERSION` | A counter that grows with every write. |
| `CREATED`, `UPDATED` | When it was created and last written, in milliseconds since the epoch. |
| `DELETED` | When it was deleted, or `null`. |
| `REGION` | Which region wrote it; `0` unless the application is [deployed in several](../running/10.regions.md). |

They can be read, used in query criteria, sorted by and indexed. None of them may be declared in
`properties` or named in `blank`, except `id`:

```
System property 'DELETED' cannot be overridden
```

Two more exist only while a transition runs and are never stored: `TRAILERS`
([Events](6.events.md#trailers)) and `DISCARD` ([Errors](3.errors.md#deciding-not-to-write)).

## Identity

By default the runtime assigns the `id` when an object is created, and an operation never
generates one.

### Associated entities

Some objects are identified by something that exists elsewhere: an account belongs to a
customer, and the customer's id is the natural id of the account. Declare the entity
`associated`:

```yaml
# components/store.accounts/manifest.toa.yaml
name: accounts
namespace: store

entity:
  associated: true
  properties:
    balance:
      type: integer
      minimum: 0
  required: [balance]
  blank:
    balance: 0
```

Now any `id` names an account. Reading one that was never written returns its blank; the first
write creates it. There is no "create an account" step, and no "account not found".

### Custom identifiers

To use identifiers of another shape, declare `id` yourself:

```yaml
entity:
  properties:
    id:
      type: string
      pattern: ^[A-Z]{3}$
```

## Moments

A property that holds a point in time is declared with a format, and is then stored as a date
— so an index sorts, compares and expires by it:

```yaml
entity:
  properties:
    paid: { type: string, format: date-time }       # an ISO 8601 string in your code
    expires: { type: integer, format: epoch-millis } # what context.now() answers
```

Your code reads and writes the value as declared. Three things to know:

- `epoch-millis` is a moment, not a duration. A timeout or an interval declared with it would be
  stored as a date in 1970.
- Only a property of the object itself is stored as a date. A `date-time` nested in an object or
  an array is validated and stored as the string it is.
- Adding the format to a property that already holds data requires a
  [migration](12.migrations.md#changing-data) that converts what is stored.

## Storage

`storage` names where the state is kept. It defaults to MongoDB and is rarely stated:

```yaml
entity:
  storage: mongodb
```

`storage: ~` keeps nothing: writes are validated and dropped, and no query ever finds anything.
It is useful for a component under test. See
[Connectors](../services/12.connectors.md).
