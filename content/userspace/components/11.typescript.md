# TypeScript

An operation, an event, a receiver, a guard or a run command may be a `.ts` file. There is no
build step: Node.js erases the types and runs the file as it is, so the file beside the manifest
is the file that runs.

```typescript
// components/store.orders/operations/approve.ts
import type { ApproveInput, Context, State } from '../types/index.d.ts'

export async function transition (input: ApproveInput, entry: State, context: Context) {
  if (entry.status !== 'pending')
    return new Error('NOT_PENDING')

  entry.status = 'approved'

  return entry
}
```

The exported name still says the type, and the second parameter's name still says the scope.

JavaScript components get the same types through JSDoc:

```javascript
/** @import { ApproveInput, Context, State } from '../types/index.d.ts' */

/**
 * @param {ApproveInput} input
 * @param {State} entry
 * @param {Context} context
 */
export async function transition (input, entry, context) { /* … */ }
```

## Generated types

```shell
$ toa types
```

writes, for every component of the Context, a `types` directory beside its manifest:

| File | |
| --- | --- |
| `types/toa.d.ts` | Generated from the manifest. **Rewritten on every run**; do not edit. |
| `types/index.d.ts` | Written once and then left alone. Re-exports `toa.d.ts`; your own types go here. |

and the same pair in a `types` directory beside `context.toa.yaml`, for what the whole
application shares.

What a component's types contain:

| Type | |
| --- | --- |
| `Entity` | The stored object: the declared properties and the system ones. |
| `State` | What a transition receives: `Entity` plus `DISCARD` and `TRAILERS`. |
| `<Operation>Input`, `<Operation>Output` | From each operation's `input` and `output`: `ApproveInput`, `ApproveOutput`. |
| `Context` | The operation context of this component: `local` with its own operations, `remote` with every component of the application, and what its extensions add. |

Only what a manifest states is generated. An operation that declares no `output` returns
`unknown` — one more reason to declare outputs. Calls through `context.remote` are typed from the
other component's manifest, so a change to its contract shows up as a type error in its callers.

Each `types` directory is a package: a component's is `@components/<directory>`, the
application's is named after the Context. With the components listed as npm workspaces, one
component imports another's types by name:

```typescript
import type { Entity as Order } from '@components/store.orders'
```

Run [`toa types`](../running/6.cli.md#toa-types) again after changing a manifest. Options:

| | |
| --- | --- |
| `--path` | The Context root; `.` by default. |
| `--environment` | The environment the Context is read for. |
| `--quiet` | Print nothing. |

## Three rules of erased types

Node.js removes annotations and compiles nothing. Three things follow.

**A relative import names the file that exists**, with its extension:

```typescript
import { totals } from './lib/totals.ts'
```

**A type is imported with `import type`.** `import { type Context }` leaves an import statement
behind, which is then resolved at run time and fails for a module that only has types. It is also
what keeps a component independent: nothing under `@toa.io/*` is ever loaded by it.

```typescript
import type { Context } from '../types/index.d.ts'
```

**Only erasable syntax.** An `enum`, a `namespace` and a constructor parameter property emit
code, and Node.js refuses them when the module is loaded:

```
operations/create.ts: TypeScript enum is not supported in strip-only mode.
```

## Type checking

Nothing checks types when a component runs. Check them with `tsc`, with a configuration that
enforces the three rules:

```json
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "target": "esnext",
    "types": ["node"],
    "strict": true,
    "noEmit": true,
    "allowImportingTsExtensions": true,
    "verbatimModuleSyntax": true,
    "erasableSyntaxOnly": true
  },
  "include": ["operations", "events", "receivers", "guards", "rc", "types"]
}
```

## One name, one module

Two files that resolve to the same name are refused:

```
Component at '/app/components/store.orders' has more than one operations/create: create.js and create.ts
```

## Components shipped in packages

Node.js does not erase types under `node_modules`. A component your application contains may be
TypeScript; a component published in a package must be transpiled to JavaScript before it is
published.
