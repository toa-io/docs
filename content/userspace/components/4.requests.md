# Requests

Every call — from another operation, from the command line, from the gateway — hands the
operation a *request*. Its two main parts are kept apart on purpose: `input` is what the
operation is asked to do, `query` is which state it does it to.
[Calls](../../model/basics/1.calls.md) explains the split.

```javascript
await context.remote.store.orders.approve({
  query: { id: order },
  input: { note: 'gift' }
})
```

## Making a call

| | |
| --- | --- |
| `context.remote.<namespace>.<name>.<operation>(request)` | An operation of another component. |
| `context.local.<operation>(request)` | An operation of the same component. |

Both return a promise of the reply: the output, or an `Error` the operation returned
([Errors](3.errors.md#handling-an-error-from-a-call)). Neither needs to know where the other
component runs.

A local call is a real call, not a function call: the request is validated, state is retrieved
and stored, and events are published, exactly as for a call from outside.

The request may be omitted for an operation that takes no input and no query.

## Input

`input` must fit the operation's `input` schema. It is validated on the caller's side before
anything is sent, and a request that does not fit throws an exception at the call.

## Query

A query selects state within the operation's scope.

### One object

```javascript
{ query: { id: '5b1ad5d8a4c54e1dbb2a4a0b6e1f0c11' } }
```

A query that selects nothing is an exception for a transition or an assignment — the operation
does not run. An observation over `entry` runs nevertheless, and the prototype's `observe`
answers `null`.

A query may also select one object by criteria; the first match in sort order is taken:

```javascript
{ query: { criteria: 'customer==c1;status==pending', sort: ['CREATED:desc'] } }
```

### Several objects

```javascript
await context.remote.store.orders.enumerate({
  query: {
    criteria: 'status==pending;total>=1000',
    sort: ['total:desc', 'id:asc'],
    omit: 20,
    limit: 10
  }
})
```

| Property | Meaning |
| --- | --- |
| `id` | One object by identity. |
| `ids` | Several objects by identity. |
| `criteria` | A filter over properties, in RSQL. |
| `search` | A full-text search; needs a `text` [index](12.migrations.md#indexes). |
| `sort` | A list of `property`, `property:asc` or `property:desc`. |
| `omit`, `limit` | Skip the first objects of the selection, and take at most so many. |
| `sample` | Take so many objects at random from the selection. |
| `projection` | The properties the operation is given; `id` always is. Observations only. |
| `version` | The `VERSION` the object must be at. Not for observations. |
| `deleted` | `true` to select deleted objects as well. |

### Criteria

Criteria are written in [RSQL](https://github.com/jirutka/rsql-parser#grammar-and-semantic):

| | |
| --- | --- |
| `status==pending`, `status!=pending` | equal, not equal |
| `total>1000`, `total>=1000`, `total<1000`, `total<=1000` | comparison |
| `status=in=(pending,approved)`, `status=out=(cancelled)` | one of, none of |
| `a==1;b==2` | and |
| `a==1,b==2` | or |
| `(a==1,b==2);c==3` | grouping |

Values are read as the type the property is declared with. `note==null` matches objects where the
property is absent or null; quote a value to mean the text: `note=="null"`.

Criteria can name system properties: `CREATED>1764000000000`.

### What each operation accepts

- **`omit` and `limit`** are accepted only by an observation over `entries`, which *requires*
  `limit`. A transition cannot be limited to a page, and a single-object operation cannot be
  turned into a list.
- **A stream** accepts `limit` and a continuation `token` instead of `omit`; see
  [Collection Streams](../flow/4.collection-streams.md).
- **`projection`** is for observations only: a transition writes back what it read, so it reads
  all of it.
- An operation declared `query: false` accepts no query; one declared `query: true` requires
  one. An operation of a component without an entity accepts none.

A query that breaks one of these rules is an exception, like an input that does not fit.

## Creating

A transition called without a query creates an entity: it receives a blank object with a fresh
`id`, and what it leaves is stored as a new one.

```javascript
// components/store.orders/operations/create.js
export async function transition (input, entry) {
  entry.customer = input.customer
  entry.items = input.items
  entry.total = input.items.reduce((sum, item) => sum + item.price * item.quantity, 0)

  return { id: entry.id }
}
```

```yaml
operations:
  create:
    query: false
```

`query: false` makes it create-only. Without it, the same operation would also change an existing
order when called with a query — which is what the prototype's `transit` does, and rarely what an
operation with rules wants.

For an [associated](1.manifest.md#associated-entities) entity there is no creation: a query by
`id` always selects an object, written or not.

## Versions

Every write increments the object's `VERSION`. A caller that read an object and wants its change
applied only if nothing changed since names the version it saw:

```javascript
const reply = await context.remote.store.orders.transit({
  query: { id: order.id, version: order.VERSION },
  input: { total: 1200 }
})
```

If the object is at another version, the call fails with an exception — over HTTP, `412`. This is
the caller's check; `concurrency` on the operation is about changes that happen *while* it runs.

## Deleted objects

Nothing is removed from storage. The prototype's `terminate` sets `DELETED`, and from then on
queries do not find the object. `deleted: true` in a query finds it again — to show it, or to
restore it by assigning `DELETED: null`.

## Choosing what comes back

`output` in a request names the properties of the reply the caller wants; the rest is not sent:

```javascript
const orders = await context.remote.store.orders.enumerate({
  query: { criteria: `customer==${customer}`, limit: 100 },
  output: ['id', 'total']
})
```

It applies to each object of a reply that is a list. Unlike `projection`, it works for any
operation, and it trims what the operation returned rather than what it was given.
