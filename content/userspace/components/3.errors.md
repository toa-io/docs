# Errors

An operation can end in three ways: it returns an output, it returns an error, or it throws.
Which of the last two you use is not a matter of style: the runtime treats them differently
everywhere, for the reasons given in [Replies](../../model/basics/2.replies.md).

## Returning an error

An outcome the business logic expects — the order is not pending, the balance is too low — is
*returned*, as an `Error` whose message is the code:

```javascript
// components/store.accounts/operations/debit.js
export async function transition (input, entry) {
  if (entry.balance < input.amount)
    return new Error('INSUFFICIENT_FUNDS')

  entry.balance -= input.amount

  return { balance: entry.balance }
}
```

## Declaring errors

The codes an operation may return are part of its contract:

```yaml
# components/store.accounts/manifest.toa.yaml
operations:
  debit:
    concurrency: retry
    query: true
    input:
      type: object
      properties:
        amount: { type: integer, minimum: 1 }
      required: [amount]
    errors: [INSUFFICIENT_FUNDS]
```

A returned error:

- **Stores nothing.** A transition or an assignment that returns an error leaves the state as it
  was, and no event is published.
- **Is not a failure.** Nothing is retried, logged as a failure, or alarmed by it.
- **Must be declared.** A code missing from `errors` is not an answer the operation is allowed to
  give: the call fails with an exception instead of handing an unknown code to the caller.

## Handling an error from a call

A call resolves to the output or to the error. Tell them apart with `instanceof`:

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, entry, context) {
  if (entry.status !== 'pending')
    return new Error('NOT_PENDING')

  const reply = await context.remote.store.accounts.debit({
    query: { id: entry.customer },
    input: { amount: entry.total }
  })

  if (reply instanceof Error)
    return reply

  entry.status = 'approved'

  return entry
}
```

Returning the error passes it on as this operation's own answer, so its code must be among this
operation's `errors` too:

```yaml
# components/store.orders/manifest.toa.yaml
operations:
  approve:
    errors: [NOT_PENDING, INSUFFICIENT_FUNDS]
```

To answer something else, read `reply.code`:

```javascript
if (reply instanceof Error) {
  if (reply.code === 'INSUFFICIENT_FUNDS')
    return new Error('PAYMENT_DECLINED')

  return reply
}
```

## Exceptions

Anything *thrown* is a failure nobody chose: a bug, or something the operation depends on being
unavailable. Do not throw on purpose, and do not declare anything for it.

The runtime throws exceptions of its own for the same kind of thing:

| The call | Over HTTP |
| --- | --- |
| does not fit the operation's input or query | `400` |
| selects an entity that does not exist | `404` |
| names a version the entity is no longer at | `412` |
| lost a race with `concurrency: none`, or is a refused duplicate | `409` |
| went unanswered for too long | `504` |
| failed in any other way, including a reply that does not fit `output` and a state that does not fit the entity schema | `500` |

A returned error, by contrast, is answered over HTTP as `422` with the error as the body. The
gateway's side of this is in [Requests and Responses](../gateway/5.protocol.md).

An exception from a call is thrown where the call was made:

```javascript
const reply = await context.remote.store.accounts.debit(request) // may throw
```

**Do not catch it** unless you can truly answer in its place. An operation that lets it through
fails in turn, and the failure reaches whoever is waiting at the start of the chain — or, where
nobody is waiting, the work is tried again. An operation that swallows it returns a wrong answer,
and nothing retries a wrong answer.

## Three rules

**Do not throw to refuse.** Where nobody waits for the reply — an event, a
[task](../reliability/4.tasks.md) — a thrown refusal is retried again and again, then set aside as
though something were broken. A returned error ends the work.

**Do not return an error for a failure.** A returned error tells the runtime that everything
worked. Nothing will be retried.

**Do not assume once.** An operation may run more than once for one call or one event. What
that requires is in [Delivery](../reliability/1.delivery.md).

## Deciding not to write

Sometimes a transition looks at the state and finds nothing to change — and that is a success
with an answer of its own, not a refusal. Set `DISCARD` on the state:

```javascript
// components/store.accounts/operations/charge.js
export async function transition (input, entry) {
  if (entry.balance < input.amount) {
    entry.DISCARD = true

    return { balance: entry.balance, charged: false }
  }

  entry.balance -= input.amount

  return { balance: entry.balance, charged: true }
}
```

Nothing is written, the version does not grow, no event is published, and the caller receives
the output. Whatever the function changed on a discarded state is dropped without being
validated.

Over `entries`, an entry flagged `DISCARD` is left out of the write and the rest are stored.

| | Returns | State | For the caller |
| --- | --- | --- | --- |
| Output | a value | stored | the value |
| Discard | a value, with `DISCARD` set | untouched | the value |
| Error | `new Error('CODE')` | untouched | an `Error` with `code` |
| Exception | — (thrown) | untouched | thrown at the call |
