# Keep a Log of What Happens and Query It

The shop wants to know what sells, what customers search for and where they leave the storefront,
and wants to ask in words rather than build a dashboard. *Chronicles* keep a log of the
application in a store the Context names: the changes of the components that name them, facts an
operation sends, and what the storefront sends. An agent reads it over the gateway's
[MCP](../api/15.tools.md). The store Toa provides is [ClickHouse](https://clickhouse.com).

## Turn it on

Add ClickHouse to `docker-compose.yaml`, with a user that may create the reader queries run as:

```yaml
# docker-compose.yaml
services:
  clickhouse:
    image: clickhouse/clickhouse-server:26.8.34.13
    ports:
      - "8123:8123"
    environment:
      CLICKHOUSE_USER: developer
      CLICKHOUSE_PASSWORD: secret
      CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT: 1
```

Then the [Context](../shipping/1.context.md) names the store:

```yaml
# context.toa.yaml
chronicles:
  store:
    provider: clickhouse
    url: http://localhost:8123/store # the path names the database
chronicles@production:
  store:
    provider: clickhouse
    url: https://clickhouse.example.com:8443/store
  retention: 730 # days a row of events and of encounters is kept; absent, kept
```

The log is kept by a service of its own, `chronicles`, which takes the events the components declare
off the broker they are published to, as any receiver does, and writes them to the store. Add it
to what `sys` serves:

```javascript
// ecosystem.config.js
{ ...common, name: 'sys', args: 'serve configuration exposition introspection chronicles' },
```

```shell
$ npm run env
$ docker compose up -d
$ npm run restart
```

`npm run env` writes the credentials of the store into `.env`. In a deployment they are a
[secret](../shipping/6.secrets.md): the user, and `reader`, the password of the user queries run
as, which the service creates.

```shell
$ npx toa conceal chronicles-store username=store password=... reader=...
```

## Log the changes of a component

A component declares the [events](../logic/7.events.md) that are what happened to it, and the one
that is the order as it stands — and of each, what the log keeps, with what every field means:

```yaml
# components/store.orders/manifest.toa.yaml
chronicles:
  identity: customer
  events:
    created:
      description: An order was placed
      properties:
        total:
          type: integer
          description: The amount of the order, in cents
        items:
          type: array
          description: What was ordered
          items:
            type: object
            properties:
              sku:
                type: string
                description: The code of the product
              quantity:
                type: integer
                description: Units of the product
  state:
    event: snapshot
    description: An order as it stands
    properties:
      status:
        type: string
        enum: [new, paid, shipped]
        description: Where the order is in its life
      total:
        type: integer
        description: The amount of the order, in cents
```

`created` is an event every component has, and a row of the log every time an order is placed.
`snapshot` is an event of the order's own, which nothing else has to consume, and the log keeps
the latest of it for every order:

```typescript
// components/store.orders/events/snapshot.ts
import type { Event } from '../types/index.d.ts'

export function payload (event: Event) {
  return event.state
}
```

What is written is what the declaration names, at every depth, and nothing else: the customer's
email and address, which the order has, never reach the store, and neither does a field the order
gains later until it is declared. So the declaration is where personal data is kept out. A payload
whose declared field is of another type — a `total` that is a string — is not logged, and waits in
the parking queue of the service.

Every field has a `type` and a `description`, at every depth, or the component is refused when it
is read. A field is a `string`, an `integer`, a `number`, a `boolean`, an `object` of fields or an
`array` of any of these; a string may name an `enum` or a `format` — `date-time`, `date`, `uuid`,
`ipv4` — which is the type it is read as. The descriptions are what an agent reads to know that
`total` is in cents.

Which order changed, its version and when are read from the payload's `id`, `VERSION` and
`UPDATED`, before the declaration: a state must carry `id` and `VERSION`, or it is refused, and
none of them is declared. `identity` names the order's property that says whose it is, which is
the `identity` column of its rows; absent, it is `identity`, and `identity: ~` is none. A change is
logged however long the service is away, and once however often it is delivered; one committed
before the service first ran is not.

## Send a fact

A search changes nothing, and is still worth knowing:

```typescript
// components/store.search/operations/find.ts
import type { Context, FindInput } from '../types/index.d.ts'

export async function computation (input: FindInput, context: Context) {
  const results = await query(input.text, context)

  await context.chronicles.send('searched', { text: input.text, results: results.length })

  return results
}
```

```yaml
# components/store.search/manifest.toa.yaml
chronicles:
  facts:
    searched:
      description: A customer searched the catalogue
      properties:
        text:
          type: string
          description: What was typed
        results:
          type: integer
          description: How many products were found
```

A fact is declared as an event is, and `send` throws for a name the component does not declare or
a field of another type. It resolves once the broker has the fact, which then waits for the
service as an event does. An operation that knows whose the search is passes it as a third
argument, `{ identity: input.customer }`: the service is not told who called the operation.

## Take encounters from the storefront

What the storefront tells of its visitors — a page viewed, a button pressed — is an *encounter*:

```yaml
# context.toa.yaml
chronicles:
  encounters: true
```

The storefront keeps an id of the visitor, in `localStorage`, and one of the session, and posts
batches of what happened, at most 100 at a time. A signed-in customer's go to the route of their
identity, with their token, and are that customer's rows:

```javascript
await fetch(`https://api.store.example/chronicles/encounters/${customer.id}/`, {
  method: 'POST',
  keepalive: true,
  headers: { authorization: `Token ${token}`, 'content-type': 'application/json' },
  body: JSON.stringify({
    visitor, session,
    events: [{ id: crypto.randomUUID(), name: 'page_viewed', time: Date.now(), payload: { path: location.pathname } }]
  })
})
```

A visitor's go to the route of no one, which takes no credentials, so `navigator.sendBeacon` can
send them as the page closes, as a form whose `events` is their JSON:

```javascript
navigator.sendBeacon('https://api.store.example/chronicles/encounters/', new URLSearchParams({
  visitor, session,
  events: JSON.stringify([{ id: crypto.randomUUID(), name: 'page_left', time: Date.now(), payload: { path: location.pathname } }])
}))
```

```http
202 Accepted

accepted: 1
```

`visitor` and `session` are the storefront's own, at most 64 characters each, and either may be
left out. The same `visitor` before signing in and after is what tells which visits became which
customer: the rows of the route of an identity have both. A visitor is not a person — a customer
may have many, and a browser that clears its storage is a new one.

An event is `{ id, name, time, payload }`: its own id, which a retry sends again; lowercase
letters, digits and underscores; milliseconds by the browser's clock; an object of at most 16 KiB.
The route of an identity answers `403` to a token of another, and the route of no one refuses a
body that names an identity. Both are throttled, per identity and per address, which takes
[`exposition.ip`](../api/17.running.md#client-address) to name the address. Anyone can send
anything to the route of no one, so a user in its payload is what the browser said.

A payload is logged as it was sent, whatever its shape: a storefront that changes what an event
carries still has old pages open for months, so a shape that changes is a new name,
`checkout_started_v2`, rather than a new meaning of the old one. `time` is what the browser's clock
said, and is kept as it was; when the row was written is `received`.

Every encounter also has the `ip` and the `country` of its request, as the gateway reads them from
the headers [`exposition.ip` and `exposition.country`](../api/17.running.md#client-address) name. An
address is personal data, and the log erases nothing, so it keeps the network the address is in —
a `/24` of IPv4, a `/48` of IPv6 — unless the Context says `chronicles.ip: full`.

### Document what it sends

What each encounter is, and what its fields mean, is the [configuration](2.configuration.md)
of `chronicles.encounters`:

```yaml
# context.toa.yaml
configuration:
  chronicles.encounters:
    page_viewed:
      description: A page was shown
      fields:
        path: The URL path, without the query
    page_left:
      description: The visitor closed the page or went elsewhere
      fields:
        path: The URL path of the page left
```

It is what an agent reading the log is told of each encounter, and what whoever writes the
storefront reads, at `GET /chronicles/encounters/` with the role `system:chronicles:encounters`.
It documents, and checks nothing: an encounter it does not name is logged as any other.

## Read the log

The log is three tables.

`events` holds a row for everything a component did. The order placed and the search made above
are two rows of it:

| `label`                 | `component`    | `entity` | `version` | `payload`                        |
| ----------------------- | -------------- | -------- | --------- | -------------------------------- |
| `store.orders.created`  | `store.orders` | `9c1f…`  | `0`       | `{ total: 12000, items: [...] }` |
| `store.search.searched` | `store.search` | `NULL`   | `NULL`    | `{ text: "teapot", results: 3 }` |

A change is a row under `<component>.<event>` for every event it renders, and names the order
that changed and its version. A fact is a row under `<component>.<name>`, and names none. Every row
also has `time`, when it happened, `received`, when it was written, and `id`, the same however
often it is delivered.

`states` holds every order as it stands: the `snapshot` of its latest version, by `component` and
`entity`. It is the order now and nothing before it: what an order was yesterday is read from its
events, so an event that a question of history depends on has to carry what the question asks.

`encounters` holds what the storefront sent: `name`, `time` by the browser's clock, `received`,
`visitor`, `session`, `identity`, `ip`, `country` and `payload`.

Every declared event, fact and state is also a view of its own, named after its label with the
dots as underscores, whose columns are the declared fields in their types:

```sql
SELECT toDate(time) AS day, count() AS orders, sum(total) / 100 AS revenue
FROM store_orders_created GROUP BY day ORDER BY day

SELECT status, count() FROM store_orders GROUP BY status

SELECT item.sku, sum(item.quantity) FROM store_orders_created ARRAY JOIN items AS item GROUP BY 1
```

A value that is not of its type reads as `NULL` there. A query is written in the store's dialect.
In ClickHouse, the tables are read with `FINAL`, which collapses what was delivered twice; the
views read with it themselves:

```sql
SELECT name, count() FROM encounters FINAL GROUP BY name

SELECT visitor, groupUniqArray(identity) FROM encounters FINAL
WHERE identity IS NOT NULL GROUP BY visitor
```

Nothing arrives in order: order by `time`, or by `version` within one order.

## Read it over HTTP

The log is read through these routes of the gateway:

| Route                                    | Does                                                                          |
| ---------------------------------------- | ----------------------------------------------------------------------------- |
| `GET /chronicles/queries/`               | the dialect; the labels, states and encounters with their fields; the views   |
| `POST /chronicles/queries/`              | one statement, `{ sql }`, answered `{ columns, rows, truncated }`             |
| `PUT /chronicles/queries/views/:name`    | defines a view, `{ sql, title?, description?, refresh? }`                     |
| `DELETE /chronicles/queries/views/:name` | drops a view                                                                  |
| `GET /chronicles/encounters/`            | what the encounters are, as the configuration documents them                  |

Reading takes the role `system:chronicles:query`, views `system:chronicles:views`, and what the
encounters are `system:chronicles:encounters`; grant `system:chronicles` for all three. See
[Give Staff Wider Access](../access/7.roles.md#grant-a-role).

`GET /chronicles/queries/` tells of every declared label and state what it means, its view, how
many rows it has, the first and the last `time` of them, when the newest was `received` — which
tells whether rows still arrive — and its fields, with their types and descriptions. Of every
encounter it tells the fields the latest payloads had, with the types they were sent as — two
types of one field are two versions of the storefront — and what the configuration says of them.

A query reads the log and nothing else, and cannot write: for at most 30 seconds, 10,000 rows and
64 MiB, with at most 4 queries at once. A view is a statement a query could run; give it a `title`
and a `description`, which tell an agent that finds it what it counts. With `refresh`, in seconds
and at least an hour, it is computed on that cycle, read as a table, and told with when it was last
`refreshed`. A store has at most 50 views. A refusal is a `422` with its code: `REFUSED`, with what
the store said in `cause.message`, for a statement; `RESERVED`, for the name of a table or of a
declared view, `EXHAUSTED` and `NOT_FOUND` for a view.

### Try it

```http
POST /chronicles/queries/ HTTP/1.1
host: api.store.example
authorization: Basic cm9vdDpzZWNyZXQjMTIzNA==
accept: application/yaml
content-type: application/yaml

sql: SELECT status, count() AS n FROM store_orders GROUP BY status
```

```http
201 Created

columns:
  - name: status
    type: LowCardinality(Nullable(String))
  - name: n
    type: UInt64
rows:
  - [new, 3]
  - [paid, 9]
truncated: false
```

## Let an agent ask

Publish the gateway's [tools](../api/15.tools.md), and each of these routes is a tool an agent
holding its role is offered — `chronicles.queries.GET`, `chronicles.queries.POST`,
`chronicles.queries.views._name.PUT`, `chronicles.queries.views._name.DELETE` and
`chronicles.encounters.GET`:

```yaml
# context.toa.yaml
exposition:
  mcp:
    name: Store
```

An agent asks `chronicles.queries.GET` what the log holds and in which dialect, then writes its
queries and the views it keeps.
