# Keep a Log of What Happens and Query It

The shop wants to know what sells, what customers search for and where they leave the storefront,
and wants to ask in words rather than build a dashboard. *Chronicles* keep a log of the
application in a store the Context names: the changes of the components that name them, facts an
operation sends, and what browsers send. An agent reads it over the gateway's
[MCP](../api/15.tools.md). The store Toa provides is [ClickHouse](https://clickhouse.com).

## Turn it on

Add ClickHouse to `docker-compose.yaml`, with a user that may create the reader queries run as:

```yaml
# docker-compose.yaml
services:
  clickhouse:
    image: clickhouse/clickhouse-server:26.8.34.13
    ports:
      - "8123:8123"
    environment:
      CLICKHOUSE_USER: developer
      CLICKHOUSE_PASSWORD: secret
      CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT: 1
```

Then the [Context](../shipping/1.context.md) names the store:

```yaml
# context.toa.yaml
chronicles:
  store:
    provider: clickhouse
    url: http://localhost:8123/store # the path names the database
chronicles@production:
  store:
    provider: clickhouse
    url: https://clickhouse.example.com:8443/store
  retention: 730 # days a row is kept; absent, kept
```

The log is kept by a service of its own, `chronicles`, which takes the events the components name
off the broker they are published to, as any receiver does, and writes them to the store. Add it
to what `sys` serves:

```javascript
// ecosystem.config.js
{ ...common, name: 'sys', args: 'serve configuration exposition introspection chronicles' },
```

```shell
$ npm run env
$ docker compose up -d
$ npm run restart
```

`npm run env` writes the credentials of the store into `.env`. In a deployment they are a
[secret](../shipping/6.secrets.md): the user, and `reader`, the password of the user queries run
as, which the service creates.

```shell
$ npx toa conceal chronicles-store username=store password=... reader=...
```

## Log the changes of a component

A component names the [events](../logic/7.events.md) that are what happened to it, and the one
that is the order as it stands:

```yaml
# components/store.orders/manifest.toa.yaml
chronicles:
  events: [created]
  state: snapshot
  identity: customer
```

`created` is an event every component has, and a row of the log every time an order is placed.
`snapshot` is an event of the order's own, which nothing else has to consume: its payload is the
order without what identifies the customer, and the log keeps the latest of it for every order:

```typescript
// components/store.orders/events/snapshot.ts
import type { Event } from '../types/index.d.ts'

export function payload (event: Event) {
  const { email, address, ...order } = event.state

  return order
}
```

What an event's payload leaves out does not reach the store, so this is where personal data is
kept out. Which order changed, its version and when are read from the payload's `id`, `VERSION`
and `UPDATED`: a state must keep `id` and `VERSION`, as this one does, or it is refused. A list,
`chronicles: [created]`, names events and no state. `identity` names the order's property that
says whose it is, which is the `identity` column of its rows; absent, it is `identity`, and
`identity: ~` is none. A change is logged however long the service is
away, and once however often it is delivered; one committed before the service first ran is not.

## Send a fact

A search changes nothing, and is still worth knowing:

```typescript
// components/store.search/operations/find.ts
import type { Context, FindInput } from '../types/index.d.ts'

export async function computation (input: FindInput, context: Context) {
  const results = await query(input.text, context)

  await context.chronicles.send('searched', { text: input.text, results: results.length })

  return results
}
```

```yaml
# components/store.search/manifest.toa.yaml
chronicles: []
```

`send` resolves once the broker has the fact, which then waits for the service as an event does.
An operation that knows whose the search is passes it as a third argument,
`{ identity: input.customer }`: the service is not told who called the operation.

## Take events from the storefront

```yaml
# context.toa.yaml
chronicles:
  ingest: true
```

The storefront posts batches of what happened, at most 100 at a time. A signed-in customer's go to
the route of their identity, with their token, and are that customer's rows:

```javascript
await fetch(`https://api.store.example/chronicles/ingestion/${customer.id}/`, {
  method: 'POST',
  keepalive: true,
  headers: { authorization: `Token ${token}`, 'content-type': 'application/json' },
  body: JSON.stringify({ events: [{ id: crypto.randomUUID(), name: 'page.viewed', time: Date.now(), payload: { path: location.pathname } }] })
})
```

A visitor's go to the route of no one, which takes no credentials, so `navigator.sendBeacon` can
send them as the page closes:

```javascript
navigator.sendBeacon('https://api.store.example/chronicles/ingestion/', JSON.stringify({
  events: [{ id: crypto.randomUUID(), name: 'page.left', time: Date.now(), payload: { path: location.pathname } }]
}))
```

```http
202 Accepted

accepted: 1
```

An event is `{ id, name, time, payload }`: its own id, which a retry sends again; dotted
lowercase segments; milliseconds by the browser's clock; an object of at most 16 KiB. It is logged
under `client.<name>`. The route of an identity answers `403` to a token of another, and the route
of no one refuses a body that names an identity. Both are throttled, per identity and per address,
which takes [`exposition.ip`](../api/17.running.md#client-address) to name the address. Anyone can
send anything to the route of no one, so a user in its payload is what the browser said.

## Read the log

The log is two tables.

`events` holds a row for everything that happened. The order placed, the search made and the page
left above are three rows of it:

| `label`                 | `component`         | `entity` | `version` | `payload`                         |
| ----------------------- | ------------------- | -------- | --------- | --------------------------------- |
| `store.orders.created`  | `store.orders`      | `9c1f…`  | `0`       | `{ total: 120, status: "new" }`   |
| `store.search.searched` | `store.search`      | `NULL`   | `NULL`    | `{ text: "teapot", results: 3 }`  |
| `client.page.left`      | `chronicles.ingestion` | `NULL`   | `NULL`    | `{ path: "/pricing" }`            |

A change is a row under `<component>.<event>` for every event it renders, and names the order
that changed and its version. A fact is a row under `<component>.<name>`, and what the storefront
sends one under `client.<name>`; neither names an order. Every row also has `time`, when it
happened, and `id`, the same however often it is delivered.

`states` holds every order as it stands: the `snapshot` of its latest version, by `component` and
`entity`. The history of an order is in `events`, and the order now in `states`.

A query is written in the store's dialect. In ClickHouse, both tables are read with `FINAL`, which
collapses what was delivered twice:

```sql
SELECT toDate(time) AS day, count() FROM events FINAL
WHERE label = 'store.orders.created' GROUP BY day ORDER BY day

SELECT payload.status, count() FROM states FINAL
WHERE component = 'store.orders' GROUP BY 1
```

Nothing arrives in order: order by `time`, or by `version` within one order.

## Read it over HTTP

The log is read through four routes of the gateway:

| Route                                    | Does                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------ |
| `GET /chronicles/queries/`               | the dialect, the labels and the states with their fields, the views      |
| `POST /chronicles/queries/`              | one statement, `{ sql }`, answered `{ columns, rows, truncated }`        |
| `PUT /chronicles/queries/views/:name`    | defines a view, `{ sql, refresh? }`                                      |
| `DELETE /chronicles/queries/views/:name` | drops a view                                                             |

Reading takes the role `system:chronicles:query`, and views `system:chronicles:views`; grant
`system:chronicles` for both. See [Give Staff Wider Access](../access/7.roles.md#grant-a-role).

A query reads the log and nothing else, for at most 30 seconds and 10,000 rows, and cannot write. A
view is a statement a query could run; with `refresh`, in seconds and at least an hour, it is
computed on that cycle and read as a table. A store has at most 50 views. A refusal is a `422` with
its code: `REFUSED`, with what the store said in `cause.message`, for a statement; `RESERVED`,
`EXHAUSTED` and `NOT_FOUND` for a view.

### Try it

```http
POST /chronicles/queries/ HTTP/1.1
host: api.store.example
authorization: Basic cm9vdDpzZWNyZXQjMTIzNA==
accept: application/yaml
content-type: application/yaml

sql: SELECT label, count() AS n FROM events FINAL GROUP BY label
```

```http
201 Created

columns:
  - name: label
    type: LowCardinality(String)
  - name: n
    type: UInt64
rows:
  - [store.orders.created, 12]
truncated: false
```

## Let an agent ask

Publish the gateway's [tools](../api/15.tools.md), and each of the four routes is a tool an agent
holding the role is offered — `chronicles.queries.GET`, `chronicles.queries.POST`,
`chronicles.queries.views._name.PUT` and `chronicles.queries.views._name.DELETE`:

```yaml
# context.toa.yaml
exposition:
  mcp:
    name: Store
```

An agent asks `chronicles.queries.GET` what the log holds and in which dialect, then writes its
queries and the views it keeps.
