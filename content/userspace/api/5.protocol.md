# What a Client Sends and Receives

Someone writes the shop's web or mobile client. They ask which formats the API speaks, which
statuses it answers, what an error looks like and what a page on another origin may do. None of
it is declared per route.

## Formats

Request and response bodies are encoded in any of:

| Media type | Format |
| --- | --- |
| `application/json` | JSON |
| `application/yaml` | YAML |
| `application/msgpack` | MessagePack |
| `text/plain` | Plain text |

A request may also be sent as `application/x-www-form-urlencoded`. A name repeated in a form is
read as a list. Forms are only read: a response is never written as one.

The request says what it sends with `content-type` and what it wants back with `accept`. The two
are independent:

```http
POST /store/orders/ HTTP/1.1
content-type: application/json
accept: application/yaml

{"customer": "b70a7dbca6b14a2eaac8a9eb4b2ff4db", "total": 4200}
```

```http
HTTP/1.1 201 Created
content-type: application/yaml
vary: accept

id: 99988d785d7d445cad45dbf8531f560b
```

A `charset` parameter on `content-type` is accepted: `application/json; charset=utf-8`.

Without `accept`, the reply is JSON. An `accept` that names none of the formats above is
`406 Not Acceptable`. Errors are encoded by the same negotiation as successful replies.

```shell
$ curl -i http://localhost:8000/store/orders/ -H 'accept: application/yaml'
```

Routes that move bytes instead of values — stored files and streamed bodies — set their own
media types; see [Upload and Download Files](11.files.md) and
[Stream Through the API](9.streams.md).

## Statuses

The gateway answers with these statuses, each meaning what HTTP defines.

| Status | When |
| --- | --- |
| `200 OK` | The operation answered. |
| `201 Created` | The operation answered a `POST`. |
| `202 Accepted` | A workflow runs on a stored file, see [Process an Uploaded File](12.workflows.md). |
| `204 No Content` | The operation answered and the route returns no body. |
| `206 Partial Content` | A range of a stored file. |
| `304 Not Modified` | The client already holds this reply, see [Cache Replies and Prevent Lost Updates](8.caching.md). |
| `400 Bad Request` | The body, the query string or a header does not fit what the route takes. |
| `401 Unauthorized` | No credential, or one that is not valid. |
| `403 Forbidden` | The caller may not reach this method. |
| `404 Not Found` | No such route, or nothing found behind it. |
| `405 Method Not Allowed` | The route does not declare this method. |
| `406 Not Acceptable` | `accept` names nothing the route can answer in. |
| `409 Conflict` | The entity changed concurrently, or already exists. |
| `410 Gone` | A stream token the storage can no longer continue from. |
| `412 Precondition Failed` | The version in `if-match` is not the current one. |
| `413 Content Too Large` | The body is larger than the route takes. |
| `415 Unsupported Media Type` | The body's media type is not one the route takes. |
| `422 Unprocessable Entity` | The request is valid, and the operation refused it. |
| `429 Too Many Requests` | Throttled, see [`io:throttle`](6.io.md#limit-how-often-a-route-is-called). |
| `451 Unavailable For Legal Reasons` | Refused by the [censor](17.running.md#censor). |
| `500 Internal Server Error` | An exception. |
| `501 Not Implemented` | An HTTP method the gateway does not serve. |
| `503 Service Unavailable` | The deployment is [halted](../shipping/9.halt.md) or on its way there. |
| `504 Gateway Timeout` | The process a route named did not answer in time. |

`401` and `403` are the subject of [Access](../access/6.access.md).

## Errors

There are three kinds of failure, and they look different to a client.

**The operation refused.** It returned one of the errors it declares
([Refuse a Request](../logic/3.errors.md)). The status is `422` and the body is the error's
`code`, with its `cause` where the operation gave one:

```http
HTTP/1.1 422 Unprocessable Entity
content-type: application/yaml

code: INSUFFICIENT_FUNDS
```

A client branches on `code`. These codes are part of the application's contract and are listed
for each method by [`OPTIONS`](16.discovery.md#asking-a-resource).

**The request does not fit.** The gateway or the runtime refused it before the operation ran.
The status is in the `4xx` range and the body is a sentence saying what is wrong:

```http
HTTP/1.1 400 Bad Request
content-type: application/json

"must have required property 'customer'"
```

These messages are for the developer of the client. They are not codes, and a client should
branch on the status.

**Something broke.** An exception in an operation, or a dependency that did not answer. The
status is `500` and the body is empty; the exception is in the application's logs, under the
trace the `ray` header names.

### Seeing exceptions while developing

With `debug` on, the body of a `500` carries the exception:

```yaml
# context.toa.yaml
exposition:
  debug@local: true
```

```http
HTTP/1.1 500 Internal Server Error

Error: Cannot read properties of undefined (reading 'balance')
```

**Do not turn `debug` on in production**: an exception's text may show what the application
holds. The `@local` suffix limits the option to the `local` environment; see
[Environments](../shipping/2.environments.md).

## Headers on every reply

| Header | Value |
| --- | --- |
| `ray` | The trace ID of the request. |
| `server-timing` | How long the stages of processing took. |
| `exposition` | The gateway's build, the Context and the environment that answered. |
| `vary` | What the reply depends on: `origin`, `accept`, and any header a route maps. |

### `ray` and tracing

Every request is processed within a trace, and every log entry it causes anywhere in the
application carries the same trace ID. The reply returns that ID:

```http
HTTP/1.1 201 Created
ray: 0af7651916cd43dd8448eb211c80319c
```

Show it to the user beside an error message, or attach it to a support ticket: it finds the
request in the logs.

A client can supply the trace to continue. Two request headers are read:

- `traceparent` — the [W3C Trace Context](https://www.w3.org/TR/trace-context/#traceparent-header)
  header that instrumented clients and proxies send. The client's span becomes the parent of the
  gateway's.

  ```http
  traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
  ```

- `ray` — a bare trace ID, 32 lowercase hex digits, for a client without instrumentation that
  wants to correlate its requests with the server's traces.

  ```http
  ray: 4bf92f3577b34da6a3ce929d0e0e4736
  ```

If both are present, `traceparent` is used. A header with an invalid value is ignored and a new
trace starts. Traces are set up in [Traces](../platform/7.traces.md).

## Multipart responses

A reply that is a stream of values is sent as a multipart response: one part per value, written
as it becomes available. The media type is a `multipart/` subtype chosen by the same content
negotiation, once for the whole response:

| `accept` | `content-type` | Each part is |
| --- | --- | --- |
| `application/json` | `multipart/json` | JSON |
| `application/yaml` | `multipart/yaml` | YAML |
| `application/msgpack` | `multipart/msgpack` | MessagePack |
| `text/plain` | `multipart/text` | Plain text |

```http
GET /store/orders/feed/ HTTP/1.1
accept: application/json
```

```http
HTTP/1.1 200 OK
content-type: multipart/json; boundary=cut

--cut

"ACK"
--cut

{"entry":{"id":"4c4759e6f9c74da989d64511df42d6f4","status":"pending","total":4200}}
--cut

{"token":"eyJ2IjoxLCJwIjoi..."}
--cut

"FIN"
--cut--
```

Rules for the code that reads one:

- The boundary is always `cut`. Parts carry no headers of their own.
- The first part is the text `ACK`, sent as soon as the response starts.
- The last part is the text `FIN`.
- **Do not take `FIN` for success.** A stream that fails after it started, or that is still open
  when the gateway stops, also ends with `FIN`: the status was already sent. A stream that must
  be read whole carries its own end marker — a collection stream ends with a token.
- Some streams send a text part `heartbeat <time>` to tell a quiet stream from a lost one.

The kinds of streams are in [Stream Through the API](9.streams.md).

## Browsers on other origins

The gateway answers [CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS) requests from
any origin, with credentials allowed. Nothing is configured.

A preflight is answered for every path:

```http
OPTIONS /store/orders/ HTTP/1.1
origin: https://store.example
access-control-request-method: POST
```

```http
HTTP/1.1 204 No Content
access-control-allow-origin: https://store.example
access-control-allow-credentials: true
access-control-allow-methods: GET, POST, PUT, PATCH, DELETE, LOCK, UNLOCK, OPTIONS
access-control-allow-headers: accept, authorization, content-type, if-match, if-none-match
access-control-max-age: 3600
```

Request headers a page may send: `accept`, `authorization`, `content-type`, `if-match`,
`if-none-match`, and every header a route of the application reads through a directive — the
headers named in [`map:headers`](7.mapping.md#headers), `accept-language` where a language is
mapped, `content-attributes` and `content-location` where files are uploaded.

Response headers a page may read: `authorization`, `content-type`, `content-length`, `date`,
`etag`, `retry-after`.

Every reply of the gateway carries the CORS headers, errors included, so a page can read the
status and body of any failure the application answered.

An `OPTIONS` request without `access-control-request-method` is not a preflight. It is
[introspection](16.discovery.md#asking-a-resource), and a page may send it.

There are no cookies. A credential travels in the `authorization` header.

## When the deployment is halted

A [halted](../shipping/9.halt.md) deployment answers every request, preflights included, with
`503`:

```http
HTTP/1.1 503 Service Unavailable
cache-control: no-store
retry-after: 120
```

`retry-after` says when it is back, where that is known. A client should treat `503` as "try
later", not as an error of the request.

## A client's checklist

- Send a trailing slash on every path except those of stored files.
- Send `accept`; expect JSON otherwise.
- Branch on the status, and for `422` on `code`.
- On `429` and `503`, wait for `retry-after` seconds.
- On `412`, read the entity again and reapply the change.
- Keep `ray` of failed requests.
- For a multipart response, read until `FIN` and do not take `FIN` for success.
