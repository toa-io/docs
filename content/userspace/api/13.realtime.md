# Push Changes to the Browser

A customer watches their order page and sees the status change the moment it is approved; staff
see new messages about an order as they are written. The application already announces every
change with [events](../logic/7.events.md). Pushing them to clients takes two declarations: which
events go to which *keys*, and which routes serve the stream of a key.

## A first stream

The shop lets a customer and the support staff exchange messages about an order.
`store.messages` holds them: each message has an `order`, a `sender` and a `text`.

```yaml
# components/store.messages/manifest.toa.yaml
name: messages
namespace: store

entity:
  properties:
    order:
      type: string
    sender:
      type: string
    text:
      type: string

realtime:
  created:
    key: order
    expose: [id, sender, text]

exposition:
  /:
    io:output: [id]
    POST: create
  /of/:order/stream:
    GET:
      realtime:stream: order
```

The `realtime` section says: when a message is created, send the event to the stream of the key
held in its `order` property, with the properties `id`, `sender` and `text`.

The route says: `GET /store/messages/of/<order>/stream/` answers with the stream of the key that
`:order` holds.

The Context says where streams are kept:

```yaml
# context.toa.yaml
realtime:
  streams: redis://localhost:6379
```

A client opens the stream and keeps the connection:

```http
GET /store/messages/of/4c4759e6f9c74da989d64511df42d6f4/stream/ HTTP/1.1
accept: application/json
```

```http
HTTP/1.1 200 OK
content-type: multipart/json; boundary=cut

--cut
"ACK"
--cut
{"event":"token","data":"MTcyNjY4OTc0MjAwMC0w"}
```

When anyone posts a message for that order, a part arrives on the open connection:

```text
--cut
{"event":"store.messages.created","data":{"id":"a7edded6b2ab47a0aca9508cc4da4138","sender":"b70a…f4db","text":"Has it shipped?"}}
--cut
{"event":"token","data":"MTcyNjY4OTc0NTUxMi0w"}
```

Try it with two terminals, with `anonymous: true` on both routes for the experiment. `-N` makes
curl print parts as they arrive:

```shell
$ curl -N http://localhost:8000/store/messages/of/4c4759e6f9c74da989d64511df42d6f4/stream/
```

```shell
$ curl http://localhost:8000/store/messages/ -H 'content-type: application/json' \
    -d '{"order": "4c4759e6f9c74da989d64511df42d6f4", "sender": "b70a7dbc", "text": "Has it shipped?"}'
```

## Routing events to keys

The `realtime` section of a manifest is keyed by event label. Each entry is a route for that
event:

```yaml
realtime:
  created:
    key: order
    expose: [id, sender, text]
  updated:
    key: order
    expose: [id, text]
```

| Key | Meaning |
| --- | --- |
| `key` | Where the event goes: a property of the event, a literal, or a list of them. Required. |
| `expose` | The properties of the event the stream carries. Required. |

The event is what the component publishes for its entity: the event's payload, or the entity
state for an event that declares no payload. The label is that of any event of the component,
including the ones every component has without declaring them: `created`, `updated`, `deleted`
and `sync` (see [Announce a Change](../logic/7.events.md)). Routing `sync` is the usual way to
keep clients up to date with an entity:

```yaml
# components/store.orders/manifest.toa.yaml
realtime:
  sync:
    key: customer
    expose: [id, status, total, VERSION]
```

Only a component can route its own events. Realtime routes are not declared in the Context.

### Keys

A key is any value that names an audience: an order, a customer, a group the application makes
up.

- **A property** — `key: order`. The event goes to the stream of the value the property holds.
- **A property holding a list** — the event goes to the stream of every value in it.
- **Several keys** — `key: [sender, recipient]`. The event goes to each.
- **A literal** — `key: ~staff`, see [Literal keys](#literal-keys).

A value that begins with `~` is never used as a key; the event simply does not go there.

### What a stream exposes

`expose` is required, and a stream is given nothing it does not name. A realtime route without
it is refused when the manifest is read.

An event may carry internal properties. What leaves the application is the subset the route
lists — the same closed-by-default rule as [`io:output`](6.io.md#choose-what-comes-back). Where
the two should match, share the list with a YAML anchor:

```yaml
realtime:
  sync:
    key: customer
    expose: &order [id, status, total, VERSION]

exposition:
  /of/:customer:
    io:output: *order
    GET: enumerate
```

Expose `VERSION` whenever clients update a copy from the stream; see
[Rules for the client](#rules-for-the-client).

## Serving a stream

`realtime:stream` on a `GET` answers with the stream of a key. Its value is the route variable
that holds the key:

```yaml
exposition:
  /of/:order/stream:
    auth:role: staff
    GET:
      realtime:stream: order
```

**Whatever authorizes the route authorizes the stream.** There is no separate permission model for
realtime. The directives on the route decide who may open it, exactly as they would for a `GET` that
returns data; a caller they refuse gets `401` or `403`, and nothing is opened. Access rules are in
[Access](../access/6.access.md).

The key is a value of the whole application, not of one component. Any component that routes an
event to the key `4c47…d6f4` writes to the same stream, whichever component serves the route.
`store.orders` could route its `sync` by `id`, `store.messages` its `created` by `order`, and a
client reading the stream of one order identifier would receive both.

### An identity's own stream

An identity's id is a key like any other, and the gateway serves every identity its own stream
without a route being declared:

```http
GET /realtime/b70a7dbca6b14a2eaac8a9eb4b2ff4db/ HTTP/1.1
authorization: Token …
accept: application/json
```

Only the identity itself may open it. So to push something to a user, route an event by a
property that holds the user's identity id:

```yaml
# components/store.orders/manifest.toa.yaml
realtime:
  sync:
    key: customer            # holds the customer's identity id
    expose: [id, status, total, VERSION]
```

Every customer now receives the changes of their own orders on `/realtime/<their id>/`, along
with everything any other component routes to them. A client application typically opens this
one stream at sign-in and dispatches on the `event` name.

### Literal keys

A key that begins with `~` is a *literal*: the key itself, the same for every event, not a
property. Use it for an audience that is not a value of any entity — "all staff", "everyone
watching the catalogue".

```yaml
# components/store.orders/manifest.toa.yaml
realtime:
  created:
    key: ~incoming
    expose: [id, customer, total]

exposition:
  /incoming/stream:
    auth:role: staff
    GET:
      realtime:stream: ~incoming
```

`realtime:stream` names the literal the same way, so its route needs no variable.

- The key is `~incoming`, tilde included.
- A value of a property is never taken for a literal. Whoever controls the values — a customer
  naming something `~incoming` — cannot route an event into a literal's stream.
- A literal's stream is read only at a route that names it. A route variable that happens to
  hold `~incoming` is answered `404`.
- Literals and properties mix: `key: [~incoming, customer]`.

## Reading a stream

A stream is a [multipart response](5.protocol.md#multipart-responses) that stays open. After
`ACK`, each part is one of three:

| Part | Shape | What to do |
| --- | --- | --- |
| An event | `{ "event": "<namespace>.<component>.<label>", "data": { … } }` | Apply it. |
| A token | `{ "event": "token", "data": "<token>" }` | Keep the last one. |
| A heartbeat | the string `heartbeat <time>` | Nothing; it shows the stream is alive. |

- `event` is the event's full name: `store.messages.created`. For a component without a
  namespace it is `default.<component>.<label>`.
- `data` is what the route exposes.
- A token is sent once when the stream opens and again after every event.
- A heartbeat is sent every 16 seconds. A client that has seen nothing for noticeably longer
  should consider the connection lost.

The format of the parts follows `accept`, as everywhere.

In a browser, read the stream with `fetch` and a reader over the response body: the standard
`EventSource` cannot send an `authorization` header, and this is not the Server-Sent Events
format.

### Reconnecting

A reader that lost its connection reconnects with the last token it was given, and is sent what
was routed to the key since:

```http
GET /store/messages/of/4c4759e6f9c74da989d64511df42d6f4/stream/?token=MTcyNjY4OTc0NTUxMi0w HTTP/1.1
```

The events of a key are kept while it has a reader, and for a while after its last reader left:
300 seconds unless the Context says otherwise. A token older than that is answered with whatever
is left, which may be nothing. A client away for longer reads the current state again.

When the gateway stops, an open stream is ended with `FIN`. Treat `FIN` like a lost connection:
reconnect with the last token.

## Rules for the client

- **Open the stream first, then read the current state.** A stream starts when it is opened;
  what was routed to a key before is not sent.
- **An event may arrive twice, and events arrive in no promised order.** Applying one must be
  harmless to repeat: keep the `VERSION` you have and drop an event with an older one.
- **Access is checked when a stream is opened.** A reader who loses access afterwards keeps the
  stream until it closes.
- **Only what operations publish is sent.** A record changed by a migration or removed by expiry
  produces no event. A client that must never miss a change synchronizes with a
  [collection stream](9.streams.md#collection-streams) and uses realtime to know when to look.

The reasons are in [Realtime](../../model/edge/3.realtime.md).

## One stream per interest

A client opens one stream per key it cares about. Where that would be many — every order on a
board, every product in a list — give them a common key. The event carries the group it belongs
to, and the group is the key:

```yaml
# components/store.orders/manifest.toa.yaml
realtime:
  sync:
    key: [customer, ~incoming]
    expose: [id, customer, status, total, VERSION]
```

The customer hears about their orders on their own stream, and staff hear about all orders on
one. Choosing keys is a modelling decision; the entities usually already say who the audiences
are.

## Configuration

Streams are kept in Redis. The `realtime` annotation of the Context is required as soon as a
component declares realtime routes:

```yaml
# context.toa.yaml
realtime:
  streams: redis://realtime.store.example
  expire: 300
```

| Key | Meaning | Default |
| --- | --- | --- |
| `streams` | The Redis URL, or a list of them. Required. | — |
| `expire` | Seconds a key's events are kept after its last reader left. | `300` |

`expire` is the window a client has to reconnect without loss.

With a list, the streams are spread over several Redis instances; each key is kept by one of
them:

```yaml
realtime:
  streams:
    - redis://realtime-0.store.example
    - redis://realtime-1.store.example
```

Keys are prefixed with the Context's name, so several applications may share a Redis. Changing
the list moves keys, and a reader whose key moved is not sent what it missed.

The address usually differs per environment:

```yaml
realtime:
  streams@local: redis://localhost:6379
  streams@production: redis://redis.internal:6379
```

## Summary

| Where | Declaration | Meaning |
| --- | --- | --- |
| Manifest | `realtime.<event>: { key, expose }` | Route an event of this component to keys. |
| Manifest | `realtime:stream: <variable>` | Serve the stream of the key in a route variable. |
| Manifest | `realtime:stream: ~<literal>` | Serve the stream of a literal key. |
| Context | `realtime: { streams, expire }` | Where streams are kept, and for how long. |
| Built in | `GET /realtime/:id/` | The stream of the identity `:id`, for that identity. |
