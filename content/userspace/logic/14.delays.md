# Do Something Later

An order that is not paid within an hour is cancelled. Each order has its own hour, so this is
not [a schedule](13.schedules.md): the order arms a *delay*, one call handed over to be made
later. It is stored, so it survives restarts and deployments.

## Arm a delay

A component that delays calls names the `cadence` extension in its manifest. There is nothing to
declare under it; a component that already declares pulses or schedules there has delays too.

```yaml
# components/store.orders/manifest.toa.yaml
cadence: ~

entity:
  properties:
    # ... as before
    deadline: { type: string }

operations:
  lapse:
    type: transition
    scope: entry
    errors: [NOT_PENDING]
```

That puts `delay` on the operation context:

```typescript
// components/store.orders/operations/create.ts
import type { Context, CreateInput, State } from '../types/index.d.ts'

const MINUTE = 60 * 1000

export async function transition (input: CreateInput, entry: State, context: Context) {
  // ... fill the order from the input, as before

  entry.deadline = await context.delay(
    'store.orders.lapse',
    { query: { id: entry.id } },
    { interval: 60 * MINUTE, overdue: 10 * MINUTE }
  )

  return entry
}
```

```typescript
// components/store.orders/operations/lapse.ts
import type { State } from '../types/index.d.ts'

export async function transition (input: null, entry: State) {
  if (entry.status !== 'pending') return new Error('NOT_PENDING')

  entry.status = 'cancelled'

  return entry
}
```

An hour later `store.orders.lapse` is called with that query, as if a component had called it
then.

`context.delay` takes three arguments:

1. **The endpoint**, `<namespace>.<component>.<operation>`: an operation of any component, the
   caller's own included. A component without a namespace is `default.<name>.<operation>`.
2. **The request**, what an ordinary [call](4.calls.md) would pass: `input`, `query`, or both.
   Pass `null` for an operation that takes nothing.
3. **The options.** `interval` and `overdue` are both required.

| Option      | Meaning                                                                         |
| ----------- | ------------------------------------------------------------------------------- |
| `interval`  | Milliseconds from now; `0` or more.                                             |
| `overdue`   | Milliseconds the call may be late and still be made, or `null` for no bound.    |
| `unchained` | `true` for a call that re-arms itself; see [below](#a-call-that-repeats-itself). |

A delay is stated in **milliseconds**; the manifest's `cycle` and a schedule's `overdue` are in
seconds.

## Cancel it

`context.delay` answers an id, and the id cancels the call:

```typescript
// components/store.orders/operations/approve.ts
import type { ApproveInput, Context, State } from '../types/index.d.ts'

export async function transition (input: ApproveInput, entry: State, context: Context) {
  // ... check the status, debit the account

  await context.delay.cancel(entry.deadline)

  entry.status = 'approved'

  return entry
}
```

`cancel` throws for an id that was never issued.

**Do not rely on cancellation alone.** It is reliable only while the call is more than a minute
away (see [Timing](#timing)); closer than that the call may already be on its way. That is why
`lapse` checks the status it finds.

## Try it

Delays need the `cadence` service and Redis; see [What it needs to run](#what-it-needs-to-run).
`toa mono` starts the service with the components.

Lower the interval to a couple of minutes for the experiment, create an order, and observe it
after the interval has passed:

```shell
$ toa call store.orders.create "{ input: { customer: 'c1', items: [], total: 1800 } }"
$ toa call store.orders.observe "{ query: { id: '<the id it printed>' } }"
```

The order is `cancelled`. Create another, approve it in time, and it stays `approved`.

In a test, call `lapse` directly instead of waiting: what matters is what it does with a pending
order and with an approved one.

## Choose `overdue`

A call is normally made at its moment. It is late when something failed: the target was away, or
nothing was running to make the call. `overdue` says what to do then.

| `overdue` | Meaning                                           |
| --------- | ------------------------------------------------- |
| `null`    | No bound: made whenever it can be, however late.  |
| `0`       | On time or never.                                 |
| a number  | Made if no more than that many milliseconds late. |

**There is no default.** Only the caller knows whether a late call is still the right call: a
payment reminder is useful whenever it arrives, an order that expires at noon expires on time or
not at all. A call past its bound is dropped silently.

## Timing

Stored calls are looked over on a period called *discreteness*: 60 seconds unless the
[Context](#context-settings) says otherwise.

- **A delay shorter than the discreteness is served late**, up to a minute by default. A longer
  one is made on time.
- **An `overdue` shorter than the discreteness can be missed when nothing is wrong.** State an
  `overdue` several times the discreteness, or `null`.
- **A cancellation closer than the discreteness to the call is a race.**
- **One replica takes at most 200 calls per pass**, oldest first. When more come due at once, the
  rest are made on a later pass, and it is logged.

A call that must be made, or cancelled, within seconds of its time needs a discreteness of
seconds.

## What can go wrong

**The call can be made more than once.** Where a second one would cost something, the target
refuses it, as `lapse` does; see [Handle Repeated Calls](10.repeats.md).

**The call can be not made at all:**

- **The caller stopped at the wrong moment.** Arming is not part of the operation's commit, so an
  operation that stops between the two leaves one without the other. Where it fits, arm first, as
  `create` does: a call about an order that was never stored is better than an order nobody
  cancels.
- **It passed its `overdue`.**
- **It was cancelled.**
- **It could not be handed to its target.** One attempt is made; a failure is logged and the call
  is dropped.

Once the call is handed over, it is handled like a [task](9.tasks.md): it waits for a target that
is not running, an exception has it tried again, and a returned error ends it.

**A delay of years is accepted**, but by then the operation may be gone or may no longer accept
that input.

## A call that repeats itself

A delayed call is made once. Work that repeats per item — remind about this invoice every day
until it is paid — arms the next call as it finishes this one. Such a call must say
`unchained: true`, or the third round is [refused as a loop](18.chains.md#a-call-refused-as-a-loop):

```typescript
// components/store.notifications/operations/chase.ts
import type { ChaseInput, Context } from '../types/index.d.ts'

const DAY = 24 * 3600 * 1000

export async function effect (input: ChaseInput, context: Context) {
  // ... remind about the unpaid invoice

  await context.delay(
    'store.notifications.chase',
    { input },
    { interval: DAY, overdue: null, unchained: true }
  )
}
```

An operation declared `unchained: true` in the manifest needs no option:

```yaml
# components/store.notifications/manifest.toa.yaml
operations:
  chase:
    unchained: true
```

Stopping is the operation's to write. Where the same work is due for everything at once, a
[pulse](13.schedules.md) is simpler.

## Where a delay is refused

| `context.delay` called                                         | What you see                |
| -------------------------------------------------------------- | --------------------------- |
| in an operation reached by a `GET` or `HEAD` request           | it throws; nothing is stored and no id is answered; see [read-only requests](18.chains.md#a-get-that-reaches-a-write) |
| with `instance` in the request                                 | `RequestContract`; a delayed call cannot name a [process](17.processes.md#call-one-particular-process) |
| with a [stream](16.streams.md#take-a-stream-as-input) in the request | `RequestContract`     |

## What it needs to run

**Redis, named in the Context**, as for [schedules](13.schedules.md#what-it-needs-to-run):

```yaml
# context.toa.yaml
atomicity:
  redis@local: redis://localhost:6379
  redis@production: redis://redis.example.com
```

**The `cadence` service.** It is deployed with the application without anything declared, and
keeps the calls in the application's MongoDB. Locally `toa mono` starts it; with `toa compose`,
name it or run it beside:

```shell
$ toa compose ./components/* --service cadence
$ toa serve cadence
```

**Without either, no delayed call is made.**

## Context settings

```yaml
# context.toa.yaml
cadence:
  discreteness: 60 # seconds between passes over the stored calls
  regions: [0] # the regions whose calls this deployment makes, by rank
```

| Key            | Default                   | Meaning                                              |
| -------------- | ------------------------- | ---------------------------------------------------- |
| `discreteness` | `60`                      | Seconds between passes; an integer, at least `1`.    |
| `regions`      | the deployment's own rank | Ranks of the regions whose delayed calls, pulses and schedules this deployment makes. |

In an application deployed as several [regions](../shipping/8.regions.md), each region makes its
own delayed calls and there is nothing to configure. When a region is lost, redeploy a surviving
one naming the lost rank beside its own:

```yaml
# context.toa.yaml
cadence:
  regions: [0, 1] # this region's calls, and those of the region that was 1
```

It then makes both regions' delayed calls, and the pulses and schedules
[declared for the lost one](13.schedules.md#several-regions), and keeps the delayed calls it took
over. **Two regions naming one rank make every one of its calls twice**, and nothing detects it.
A cancellation made in another region arrives more slowly than one made in the same region.

`toa types` adds `delay` to the component's generated `Context` type; see
[Use TypeScript](19.typescript.md). The concept is in
[Cadence](../../model/flow/1.cadence.md#delay).
