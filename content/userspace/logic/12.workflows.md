# Write a Multi-Step Workflow

Approving an order means more than a debit: the stock is reserved, a courier is booked through
the courier's API, and the customer is told. If the last step fails, the work is tried again, and
it must not reserve the stock or book a courier a second time.

Write the steps as one effect and declare it under `continuity`. When it is tried again, the
steps that already answered are not made again: the effect is given their answers and goes on
from the step that failed.

## Declare the effect

`store.fulfilment` ships an approved order:

```yaml
# components/store.fulfilment/manifest.toa.yaml
namespace: store
name: fulfilment

configuration:
  schema:
    properties:
      courier: { type: string, format: uri }
    required: [courier]

operations:
  ship:
    type: effect
    input:
      type: object
      properties:
        order: { type: string }
      required: [order]

continuity:
  ship: 604800 # seconds an unfinished run can still be picked up
```

```typescript
// components/store.fulfilment/operations/ship.ts
import type { Context, ShipInput } from '../types/index.d.ts'

export async function effect (input: ShipInput, context: Context) {
  const order = await context.remote.store.orders.observe({ query: { id: input.order } })

  await context.remote.store.catalog.reserve({ input: { items: order.items } })

  const response = await context.fetch(`${context.configuration.courier}/bookings`, {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ order: order.id })
  })

  if (!response.ok) throw new Error(`Courier answered ${response.status}`)

  const booking = await response.json()

  await context.remote.store.notifications.send({
    input: { customer: order.customer, tracking: booking.tracking }
  })
}
```

The operation is written like any other; nothing in it is about resuming. If `send` throws, the
next attempt gets the order `observe` answered, the reply of `reserve` and the response of the
courier without asking again, and makes only `send`.

`continuity` is a section of the manifest, beside `operations`. Each key names an effect of the
component. The value is how long, in seconds, a run that has not finished can still be picked up.
There is no default, and the minimum is `600`. A manifest that states less, names an operation the
component does not have, or names one that is not an effect is refused:
`'transit' is not an effect`.

## Start it

As a [task](9.tasks.md):

```typescript
// components/store.orders/operations/approve.ts
import type { ApproveInput, Context, State } from '../types/index.d.ts'

export async function transition (input: ApproveInput, entry: State, context: Context) {
  // ... check the status, debit the account

  entry.status = 'approved'

  await context.remote.store.fulfilment.ship({ input: { order: entry.id }, task: true })

  return entry
}
```

or from a [receiver](8.receivers.md):

```yaml
# components/store.fulfilment/manifest.toa.yaml
receivers:
  store.orders.approved: ship
```

Each task, and each event, is one *run*. Attempts of one run share the answers; two runs share
nothing.

**A call that waits for the answer throws**, and a [pulse](13.schedules.md) may not name the
operation. The debit stays in `approve` for that reason: the customer waits to learn whether the
money was there, and [`once`](10.repeats.md#declare-once) protects it.

## Try it

Make the last step fail: add `throw new Error('down')` to `store.notifications.send` for a moment,
run the application, and approve an order.

```shell
$ toa call store.orders.approve "{ query: { id: '7a1c5e0c2b8f4d0e9a3b6c1d2e4f5a6b' } }"
```

The approval answers at once. In the logs `ship` is attempted again and again; `reserve` and the
courier are each called once. Remove the `throw`, restart, and the run finishes with the next
attempt, still without a second reservation or booking.

## What counts as a step

A step is something the operation asks of its `context`:

| Asked through `context`                    | A step                                          |
| ------------------------------------------ | ----------------------------------------------- |
| `remote` and `local` calls                 | yes                                             |
| `fetch`                                    | yes; status, headers and body come back as a `Response` |
| `stash`                                    | yes                                             |
| `id()`, `now()`, `random()`                | yes                                             |
| `logs`, `span`, `metrics`, `configuration` | no; the same on every attempt                   |
| `state`, `atom`                            | no                                              |

A step is recognized by what it asks, not by when. Two attempts that make the same request are
making the same step, so concurrent branches are fine:

```typescript
await Promise.all([
  reserve(context, 'warehouse-a').then((r) => label(context, r)),
  reserve(context, 'warehouse-b').then((r) => label(context, r))
])
```

## Rules for the code

### Take time, randomness and ids from the context

An argument that differs between attempts makes a new step, and the step is made again:

```typescript
// a new timestamp every attempt: the call is made again every attempt
await context.remote.store.invoices.issue({ input: { at: Date.now() } })

// the same timestamp on every attempt: the call is made once
await context.remote.store.invoices.issue({ input: { at: context.now() } })
```

| Instead of                         | Take               | Answers                          |
| ---------------------------------- | ------------------ | -------------------------------- |
| `Date.now()`                       | `context.now()`    | milliseconds since the epoch     |
| `Math.random()`                    | `context.random()` | a number in `[0, 1)`             |
| `crypto.randomUUID()` and the like | `context.id()`     | a new id, made as an entity's is |

A run sees one moment, one random value and one new id however many attempts it takes. They are
on [every operation context](21.context.md).

The same goes for anything else an argument is built from. An effect that reads its own entity
reads it again on every attempt, and a step whose arguments come from it is made again if the
entity changed.

### Keep nothing in the process

The next attempt may run in another process, after a restart or a deployment:

```typescript
// counts in whichever process the attempt runs in, not across attempts
context.state.sent = (context.state.sent ?? 0) + 1

// kept with the run, and given back wherever the next attempt runs
const sent = await context.remote.store.notifications.send({ input })
```

A module variable, a cache in memory, a file on the local disk and
[`context.state`](17.processes.md#keep-it-in-contextstate) do not travel with the run. Anything a
later attempt depends on comes from a step, or from state the operation writes and reads back.

### Take ids before branching

Two concurrent steps with the same arguments are the same request, and which branch gets which
answer is not fixed. `context.id()` called in two concurrent branches is the common case: take
the ids first, then branch.

## What can still repeat

**A step that took effect just before the process stopped is made again**, because its answer was
not kept yet.

- A call to another component arrives as the same call. Declare the callee
  [`once`](10.repeats.md#declare-once), and the repeat changes nothing.
- A `fetch` to a provider is sent again. Pass a key the provider recognizes repeats by;
  `context.id()` gives one that is the same on every attempt:

```typescript
const key = context.id()

const response = await context.fetch(`${context.configuration.courier}/bookings`, {
  method: 'POST',
  headers: { 'content-type': 'application/json', 'idempotency-key': key },
  body: JSON.stringify({ order: order.id })
})
```

**If one run is delivered twice at the same moment**, both copies go on with the answer the first
of them kept. `context.id()`, `context.now()` and `context.random()` are the exception: each copy
has its own value until one is kept, so a step built from it may be made by both.

## Failures you will see

- **A returned error ends the run**, as for any task. It is not tried again, and nobody reads it.
- **A step that answers with a stream throws `Unrecordable`**, and the run is set aside at once.
  A continued effect asks for values, and answers values.
- **An answer larger than 16 MB cannot be kept**, and the step throws.
- **A run that keeps throwing is set aside for an operator** after a few attempts; see
  [Operating](../shipping/10.operating.md). Put back within the time stated under `continuity`, it
  picks up where it stopped. Put back later, it starts from the beginning.
- **A run delivered again after it finished makes nothing.**

## What it needs to run

The answers are kept by a service the runtime brings along, in the application's MongoDB. It is
deployed with the application as a service of its own when a component declares `continuity`.

A Context whose `mongodb` names one address for everything has nothing to add. One that names
addresses per namespace names this one too:

```yaml
# context.toa.yaml
mongodb:
  store: mongodb://store.mongo.example.com
  continuity: mongodb://mongo.example.com
```

While that database is away, runs wait and pick up when it is back.

Locally `toa mono` runs the service with the components; with `toa compose`, name it:

```shell
$ toa compose ./components/* --service continuity
```

## Checklist

- The operation is an `effect`, named under `continuity` with at least `600` seconds.
- It is started with `task: true` or from a receiver, never waited for.
- Every value that would differ between attempts comes from `context`.
- Nothing a later attempt needs lives in the process.
- Callees that change state declare `once`; requests to providers carry a key.
- No step answers with a stream.
