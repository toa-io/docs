# Environments

An application runs in several places: on your machine, in a test pipeline, in production. The
components are the same everywhere. What differs is declared in the Context, per environment.
[Environments](../../model/running/1.environments.md) explains the idea; this article shows how to
write it.

## A value for one environment

Append `@<environment>` to a key:

```yaml
# context.toa.yaml
mongodb: mongodb://localhost
mongodb@production: mongodb://mongo.internal.example.com
```

A key without a suffix applies everywhere. A key with a suffix applies in that environment and
wins there. So in `production` the database is `mongo.internal.example.com`, and everywhere else
it is `localhost`.

The environment is named on the command line:

```shell
$ toa env local
$ toa deploy production
```

An environment is not declared anywhere. It exists because a key carries its suffix, or simply
because a command names it: an environment no key mentions takes every unsuffixed value.

## The suffix works at any depth

Any key of the Context can be suffixed, not only the top-level ones:

```yaml
exposition:
  authorities:
    main@local: localhost:8000
    main@production: api.example.com

configuration:
  store.orders:
    limit: 10000
    limit@staging: 100

compositions:
  - name: core
    components: [store.orders, store.accounts]
    replicas: 3
    replicas@staging: 1
```

A suffixed key replaces the whole value of the unsuffixed one. It is not merged into it:

```yaml
storages:
  pictures:
    provider: tmp
    directory: store-pictures
  pictures@production:
    provider: s3
    bucket: store-pictures
    region: eu-west-1
```

In `production`, `pictures` is the `s3` declaration alone.

Because `@` marks a suffix, a key of the Context cannot contain `@` for any other purpose. A
package name used as a key under `annotations`, which starts with `@`, is the one exception.

A key may exist only with suffixes. Then environments that are not named have no such key at all:

```yaml
evicted@production:
  components: [store.pictures]
```

## What you typically vary

- **Addresses** — `amqp`, `mongodb`, `stash`, storage buckets, the gateway's `authorities`, the
  ingress `hosts`.
- **Configuration values** — a limit that is small in tests, a sender address, a feature that is
  off locally.
- **Shape** — `compositions`, `replicas`, `resources`, `mono`.
- **What is deployed** — [`evicted`](3.compositions.md#evicting-in-one-environment).
- **How images are built** — `registry.base`, `registry.platforms`, `registry.services`.

Secret values are never written in the Context, in any environment. The Context names them, and
each environment is given its own values; see [Variables and secrets](9.secrets.md).

## The local environment

`toa env` without a name selects `local`:

```shell
$ toa env
```

This reads the Context for `local` and writes a `.env` file beside it with everything a process
needs to run there: the environment's name, the addresses, the configuration. Commands that run
components (`toa compose`, `toa mono`, `toa serve`, `toa call`) find that file by walking up from
the working directory, or take one with `--env <path>`.

```shell
$ toa env local --dev      # fill secrets with local development defaults
$ toa map                  # write the component map, see Contracts
$ toa compose ./components/*
```

`--dev` fills what it can: `developer` / `secret` for the local broker and database, generated
keys for identity tokens, and any secret whose name is set in your shell's environment. What it
cannot fill is written empty for you to fill in. `--interactive` asks for each missing secret
instead. A secret value already in the file is kept by both, so running `toa env` again does not
lose what you typed.

**Run `toa env` again after changing the Context.** The `.env` file is a snapshot.

Add `.env*` to `.gitignore`: the file holds secrets.

A typical project wraps this in one script:

```json
{
  "scripts": {
    "env": "toa env -d -i && toa map"
  }
}
```

`toa env` takes more options: `--path` for a Context elsewhere, `--as` to write another file,
`-c` and `-s` to write only what one component or one service needs. They are listed in
[The CLI](6.cli.md#toa-env).

## Several local environments

Nothing limits you to one. A common second one runs the application in a container on your
machine, where `localhost` is the container itself:

```yaml
mongodb@local: mongodb://localhost:27017
mongodb@docker: mongodb://host.docker.internal:27017
```

```shell
$ toa env docker --dev --as .env.docker
$ toa compose ./components/* --dock --env .env.docker
```

`--as` keeps the two environment files side by side.

## Derived environments

Environments are often nearly alike. Name them as a chain, separated by colons, and each key takes
the first name in the chain it has a suffix for:

```yaml
amqp: amqp://localhost
amqp@production: amqp://rmq.internal.example.com

mongodb@production: mongodb://mongo.internal.example.com
mongodb@staging: mongodb://mongo.staging.example.com

configuration:
  store.orders:
    limit: 10000
    limit@staging: 100
```

```shell
$ toa deploy staging:production
```

| Key | `staging:production` takes |
| --- | --- |
| `mongodb` | `@staging` |
| `amqp` | `@production`, as there is no `@staging` |
| `limit` | `@staging` |

A key with neither suffix takes its unsuffixed value. A chain may be longer:
`preview:staging:production`.

Three things to know about a chain:

- **The environment the processes run as is the first name.** `toa env staging:production` writes
  `TOA_ENV=staging`.
- **The chain is not stored.** It is written on the command line each time, never in the Context.
  Give the same chain to every command for that environment: the one `toa deploy` read is the one
  `toa export secrets` must read.
- An empty name in a chain is refused: `Environment 'staging:' contains an empty name.`

## Naming an environment

Every command that reads the Context takes an environment in the same form.

| Command | Default environment |
| --- | --- |
| `toa env`, `toa map`, `toa npm`, `toa types` | `local` |
| `toa deploy`, `toa push` | `default` |
| `toa export secrets`, `toa export tags`, `toa export deployment`, `toa export convergence` | none; it must be given |

**Do not name an environment eight hexadecimal digits**, or `deps-` followed by eight. A deploy
tags images with the environment's name, and such a name is indistinguishable from a content tag;
see [Images](8.images.md#tags).

## What an environment cannot change

An environment changes values in the Context. It cannot change a component: there is no way to
give an operation a different implementation, schema or contract in staging. An operation that
needs to behave differently reads a
[configuration](../../model/platform/2.configuration.md) value, and the environment sets it.

A running operation can read the environment's name as `context.env`; see
[The operation context](../components/8.context.md). Prefer a
[configuration value](../services/2.configuration.md#per-environment) to branching on the name: a
value says what differs, a name only says where.

## Keep lower environments capable

Some guarantees depend on the infrastructure. A local database without transactions cannot commit
events together with state, and the runtime says so in the log when it starts. Run local and
staging infrastructure that can do what production does, at a smaller size, so that what you test
is what you release.
