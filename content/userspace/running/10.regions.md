# Regions

An application can be deployed in several places at once, each with its own database, with all of
them ending up holding the same data. Each such deployment is a *region*, and the regions
*converge*. [Regions](../../model/running/5.regions.md) explains the model and its guarantees.

## Declaring regions

A region is an [environment](2.environments.md) that declares `convergence`:

```yaml
# context.toa.yaml
mongodb@eu: mongodb://mongo.eu.example.com
mongodb@us: mongodb://mongo.us.example.com

amqp@eu: amqp://rmq.eu.example.com
amqp@us: amqp://rmq.us.example.com

convergence@eu:
  priority: 0
  binding:
    provider: amqp
    pointer: amqp://cnv.eu.example.com

convergence@us:
  priority: 1
  binding:
    provider: amqp
    pointer: amqp://cnv.us.example.com
```

```shell
$ toa deploy eu
$ toa deploy us
```

Each region has its own database, its own broker, and one more broker used only for carrying
changes between regions.

- **`priority`** — the region's rank. `0` outranks `1`. It decides which of two concurrent writes
  wins, as described [below](#which-write-wins).
- **`binding.provider`** — `amqp`.
- **`binding.pointer`** — the address of this region's convergence broker: one URL or a list of
  them. It carries no credentials; they are a secret, listed by `toa export secrets`.

An environment without `convergence` is not a region. The same Context still deploys to `staging`
as a single place, and none of this applies there.

Nothing is declared in components. Every component that stores state converges, including the
ones extensions bring: an account registered in one region can sign in to another.

### Ranks

**Every region needs a distinct rank, and nothing checks it at deploy.** A deployment reads only
its own environment's declaration. Two regions with the same rank cannot settle a tie, and the
only sign is an error in the log when a record arrives carrying the receiving region's own rank.
Keep all `convergence@...` blocks together in the Context so that the table is visible.

**An application that already runs becomes rank `0`.** Its existing records are treated as
written by region `0`, so the environment you turn into the first region takes `priority: 0`.

## What it requires

A region refuses to start, or does not converge, where the infrastructure cannot guarantee that
no change is lost.

- **The database must be a replica set.** In a region, a component with state does not start
  without one.
- **[Atomicity](../../model/platform/5.atomicity.md) must be configured**
  ([`atomicity.redis`](../services/6.shared-decisions.md#setting-it-up) in the Context). Without it
  a change that failed to publish is never retried, and the log says so repeatedly.
- **Every region runs the same components.** A component deployed in one region and not another
  has nowhere to send its changes there; they are logged and dropped.
- **A storage that cannot converge is reported at start.** The component runs, but its state
  stays regional, and one line in the log says so. Look for it after the first deployment.

Convergence carries only what happens after it is on. Existing data is copied when a region is
added.

## Which write wins

Two regions can change the same entity before hearing from each other. Every region then applies
the same rule to every record it receives:

1. the record with the higher version wins;
2. at equal versions, the record written by the region with the better rank wins.

The loser is discarded **whole**. There is no merging of fields.

Say an order is at version `3` in both regions. In `eu` a customer cancels it; in `us`, at the
same moment, an operator approves it. Both regions now hold version `4`. When the records cross,
both regions keep the one written in `eu`, rank `0`. The approval is gone, including everything
else that write changed.

Events are not undone. `store.orders.approved` was published in `us` and its receivers ran. The
regions agree on the order's state; they do not agree retroactively on what happened.

## Writing components for several regions

Most components need no change. These are the cases that do.

### Keep one writer per entity where you can

A lost concurrent write is only possible when the same entity is written in two regions within
the delay of the link. If each customer is served by one region — their home region — an order
is never written in two places at once. This is a routing decision made outside the application,
in whatever directs clients to a region.

Where two regions can legitimately write the same entity, design the entity so that losing one
write whole is acceptable, or split it so that each part has one writer.

### Do not rely on unique indexes other than `id`

A unique index is enforced within one database. Two regions can each accept a product with the
same `sku` before hearing from the other. The record that arrives second cannot be stored in the
other region; it is logged and dropped, and the regions differ for that entity.

Identifiers generated by the runtime do not collide. If a value must be unique across regions,
make it the entity's `id`, or allocate it in one region only.

### Reads may be behind

A read in one region may not yet see a write made in another. The delay is that of the link
between the brokers, and it is unbounded while the link is down.

A client that writes in one region and immediately reads in another may not find what it wrote.
Nothing is transactional across regions.

### `once` is regional

An operation declared with [`once`](../reliability/3.idempotency.md) recognises a repeated call in
the region where it was first made. A client that retries the same call against another region is
not recognised there, and the operation runs again. Keep a client's retries in one region.

### Scheduled work

A delayed call is known in every region and made only by the region that asked for it. Pulses and
schedules are made by every region, each for itself, unless the entry names the region that makes
it. [Pulses](../flow/1.pulses.md#several-regions) shows `region` on a pulse and
[Delays](../flow/3.delays.md#taking-over-a-lost-region) shows `cadence.regions`, which also lets a
surviving region take over the scheduled work of a lost one.

### Telling where you are

`context.region` is the rank of the region the operation runs in. It is `0` where the application
is deployed as a single place.

```javascript
// operations/approve.js
export async function transition (input, order, context) {
  order.approvedIn = context.region
  // ...
}
```

Each entity also records the region that last wrote it, in the system property `REGION`.

## Adding a region

The application runs in `eu` and is to run in `us` as well. The order of the steps is what keeps
changes from being lost between copying the data and starting the new region.

### Before you start

- `eu` must be on a replica set with atomicity configured. **Turning convergence on for an
  application that is not on a replica set takes it down**, since its components refuse to start.
- Choose ranks: `eu` is `0`, `us` is `1`.

### 1. Stand up the new region's infrastructure

Its database, its application broker, its convergence broker. Deploy nothing onto it yet.

Declare both regions in the Context. The existing deployment is deployed as `eu`, with its own
convergence broker, so that it publishes its changes.

### 2. Federate the convergence brokers, both ways

Toa does not configure the link between brokers. On each region's convergence broker, add an
upstream for every other region and one policy. On the `us` broker:

```shell
$ rabbitmqctl set_parameter federation-upstream eu \
    '{"uri":"amqp://cnv.eu.example.com","exchange":"convergence.out","max-hops":1}'

$ rabbitmqctl set_policy convergence '^convergence\.in$' \
    '{"federation-upstream-set":"all"}' --apply-to exchanges
```

and the mirror of it on the `eu` broker, with an upstream named `us`.

It is one link per other region, whatever the number of components. The `eu` broker will log that
what it federates from does not exist yet; that is expected until the next step.

### 3. Declare the new region's queues

**Do this before copying any data.** Until the new region has queues, the old region's changes
have nowhere to go and are dropped, not kept. From the moment the queues exist, every change is
held in them.

`toa export convergence` prints exactly what the broker must hold, read from the Context:

```shell
$ toa export convergence us \
    | curl -u <user>:<password> -H 'content-type: application/json' \
           -X POST --data @- http://<us-convergence-broker>:15672/api/definitions
```

The import only adds, so it is safe to run twice. Where the broker's management API is out of
reach, `--format commands` prints `rabbitmqadmin` commands to run instead.

Do not change the arguments of what it declares. The application declares the same queues when it
starts and fails if they differ.

Check that the link picked them up. On the `eu` broker:

```shell
$ rabbitmqctl list_queues name messages | grep federation
```

### 4. Copy the data

Dump the `eu` database and restore it into the `us` database, **after step 3**. Changes made
while the dump was being taken are in the queues, so the copy and the queues overlap, and nothing
falls between them.

Copy the whole database. The record of applied migrations is part of it, and the new region must
not apply them again.

### 5. Deploy the new region

```shell
$ toa export secrets us
$ toa conceal ...
$ toa deploy us
```

It drains the queues and starts publishing its own changes. Changes the copy already contained
are received again and ignored, since their version is not higher.

### What to watch

- **The depth of the new region's queues between steps 3 and 5.** They hold every change made in
  that time. Do not leave a long gap on a busy application.
- **Returned messages in the old region's log.** After step 3, one means a component has no queue
  on the other side: it is deployed in one region and not the other.
- **An error about a record of this region's own rank.** Two regions share a rank. Fix the
  declaration and redeploy.

## Adding a component later

A new component that stores state has the same problem in miniature. It reaches one region
before the others, and until every region has a queue for it, its changes are dropped there.

So before deploying a release that adds such a component, declare its queue on every region's
convergence broker, from a checkout that has the component:

```shell
$ toa export convergence eu | curl ... # the eu broker
$ toa export convergence us | curl ... # the us broker
```

The export lists the same components for every region, and the import adds only what is missing.
Then deploy.

## Removing a region

Stop deploying to it, delete its federation upstream on every other region's broker, and delete
its queues. A queue left bound keeps filling with nothing reading it.

## Operating regions

- **A link that is down delays convergence and nothing else.** Each region keeps serving from its
  own database, and changes cross when the link returns.
- **[Halt](11.halt.md) reaches one region.** Each region is a separate deployment; halting
  another means sending the signal to its address.
- **Realtime streams are written in every region** a change reaches, so a client connected to
  any region sees changes made in all of them.
