# Contracts

To call `store.accounts.debit`, the process running `store.orders` has to know what `debit`
accepts. It is not asked from `store.accounts` at run time. It is *given*: every process starts
with a map of the whole application. [Contracts](../../model/running/3.contracts.md) explains why;
this article shows what you do about it.

## The map

```shell
$ toa map
```

This reads the Context and writes `.map.json` beside it. Every command that runs components
needs the file:

```shell
$ toa map
$ toa compose ./components/*
```

`toa compose`, `toa mono`, `toa serve` and `toa call` look for `.map.json` from the working
directory upwards, the way they look for `.env`. Either file can be named instead:

```shell
$ toa compose ./components/* --env application/.env --map application/.map.json
```

Where there is a Context and no map, they refuse to start:

```
Cannot find '.map.json' from '/home/me/store'. Run `toa map` to write one, or name one with `--map`.
```

A component run outside any Context needs no map: it can only call what is composed with it.

The map is generated. Add `.map.json` to `.gitignore` beside `.env*`.

`toa map` takes an environment, `local` by default, and `--path` and `--as` like `toa env`; see
[The CLI](6.cli.md#toa-map).

## What is in it

One line per component: its version and what it offers to callers.

```json
{
"store.accounts":{"version":"3f9a1c02","bindings":["@toa.io/bindings.amqp"],"entity":{...},"operations":{"debit":{"type":"transition","scope":"entry","input":{...},"errors":["INSUFFICIENT_FUNDS"]}},"events":{}},
"store.orders":{"version":"a81c07e4",...}
}
```

Since each component is on its own line, `grep store.accounts .map.json` finds one.

The map holds every component of the Context: your own, the ones extensions bring, and the ones
you [evict](3.compositions.md#leaving-things-out). It holds what a caller needs — operations with
their input, output, query and errors, the entity schema, events — and leaves out what only
matters to the component itself, such as its storage, concurrency settings and migrations.

## Versions

A component's version is a hash of its source files. It changes when the sources change, and
never otherwise. Nobody maintains it.

When a process starts, it checks every component it runs against the version the map states. A
mismatch is refused:

```
'store.orders' is composed at a version the component map does not state. Run `toa map`.
```

So the rule for local work is: **run `toa map` again whenever a component's sources change.** In
practice, put it in the same script that writes the environment:

```json
{
  "scripts": {
    "env": "toa env -d -i && toa map"
  }
}
```

[`toa deploy`](7.deployment.md) writes the map it deploys by itself. You never run `toa map` for a
deployment.

### What a version is made of

By default, every file in the component's directory counts, except what is never shipped:
`node_modules`, lockfiles, tests, type declarations, a `Dockerfile`, and tool and editor output.

A component can narrow or adjust this in its manifest:

```yaml
# components/store.orders/manifest.toa.yaml
files: [operations, events, receivers, lib, rc, package.json]
ignore: ['lib/fixtures/**', '!Dockerfile']
```

- **`files`** — what the version is made of. Everything in the directory by default.
- **`ignore`** — added to the built-in exclusions. A leading `!` puts an excluded file back.

The manifest itself always counts.

Use `ignore` for files that change without changing the component, such as notes or fixtures, so
that editing them does not require a new map.

**A symbolic link is read as what it points to.** Sources shared between components through a
link are part of each component's version, and changing them changes it. `files` and `ignore`
select linked sources by the path the link is written at.

## When there is no contract

A call to a component that is neither in the same process nor in the map fails with an exception
that names it:

```
Cannot call 'store.billing': the component map states nothing of it. Run `toa map`.
```

Either the map is stale, or the name is wrong.

## What a caller checks

The request is validated **by the caller**, against the contract in its map, before it is sent.
The callee does not validate again. An invalid request therefore throws at the point of the call,
without leaving the process.

A process reads a component's contract once, at its first call to that component, and keeps it
until it stops.

Nothing is read from other components when a process starts. A composition is ready as soon as
its own connections are up, whatever else is running. There is no start order to arrange.

## Rolling upgrades

A deployment replaces replicas gradually. For a while, old and new replicas of a component serve
together, and a call goes to whichever takes it. It is not routed by version.

Combined with caller-side validation, this gives the rules for changing a component that is
already deployed.

**Safe to roll:**

- adding an operation or an event — only the new version serves it;
- adding an optional input property;
- adding an optional entity property;
- any change inside an operation that keeps its contract.

**Not safe to roll:**

- making an input property required;
- renaming or removing an input property;
- changing what a property means or its type;
- an entity schema change the previous release cannot live with, since both versions read and
  write the same entities;
- a [migration](../components/12.migrations.md) whose result the previous release cannot read.

For example, `store.accounts.debit` takes `{ amount }` and you want it to take a required
`currency`. A caller with the old contract sends requests without `currency` to new replicas,
which trust the caller's validation and run with `input.currency` undefined.

Do it in two releases instead:

```yaml
# release 1: optional, with the operation handling its absence
operations:
  debit:
    input:
      properties:
        amount: { type: integer, minimum: 1 }
        currency: { type: string }
      required: [amount]
```

```javascript
// operations/debit.js
export async function transition (input, account) {
  const currency = input.currency ?? 'USD'
  // ...
}
```

Release 2, once every caller sends `currency`, makes it required.

Removal runs the other way: stop sending the property first, then remove it from the contract.

## Changes that cannot be rolled

Some changes have no compatible intermediate step. For those, the two versions must never serve
together: stop the deployment, upgrade, start. [Halt](11.halt.md) stops a deployment without
losing work in progress, and
[Rolling what cannot be rolled](11.halt.md#deploying-a-release-that-cannot-be-rolled) gives the
procedure.

## Events from outside

A receiver of another component's event needs no declaration beyond the event's name; the map
tells it how the event arrives.

```yaml
# components/store.notifications/manifest.toa.yaml
receivers:
  store.orders.approved: send
```

An event that comes from another application is not in the map, because its source is not a
component of the Context. Such a receiver states its binding itself:

```yaml
receivers:
  warehouse.shipments.dispatched:
    binding: amqp
    operation: notify
```

Nothing checks the other side: the payload's shape is whatever the source sends, so validate what
the operation receives. [Receivers](../components/7.receivers.md) covers the declaration,
including `source` for events with arbitrary names, and the Context's `amqp.sources` addresses.

The reverse direction — an event of yours consumed by another application — is declared in the
Context's [`events`](1.context.md#events-consumed-outside).

## An evicted component

An [evicted](3.compositions.md#leaving-things-out) component is in the map like any other, and
its callers are held to what the map says. Two things follow for whoever builds and runs it:

- **Deploy it from the same sources the Context was deployed from.** Otherwise its contract and
  the one its callers hold differ.
- **Its build must hash the same files.** A process started from files other than the ones the
  map was written from is refused at start. If the component is built with its own
  `.dockerignore`, make its `files` and `ignore` describe exactly what that build copies.

## Reading a deployed map

In a deployment the map is mounted into every pod, compressed:

```shell
$ kubectl exec <pod> -- zcat /etc/toa/.map.json.gz | grep store.accounts
```

This shows which version of each component the deployment intends to run, and the contract
callers are held to.
