# Variables and Secrets

Everything a process is told about its environment reaches it as environment variables: where the
database is, what the configuration values are, which services to run. You do not write those
variables. They are derived from the Context — for a deployment by [`toa deploy`](7.deployment.md),
for a local run by `toa env`.

Secrets are the exception. They are never in the Context, and you supply their values yourself,
once per environment.

## Variables

Run `toa env` and look at the file:

```shell
$ toa env local
$ cat .env
TOA_ENV=local
TOA_CONTEXT=store
TOA_AMQP_CONTEXT={".":["amqp://localhost"]}
TOA_AMQP_CONTEXT__USERNAME=
TOA_AMQP_CONTEXT__PASSWORD=
TOA_MONGODB_STORE_ORDERS=mongodb://localhost
...
```

Each connector and extension contributes the variables its components need. They are an
interface between the tooling and the runtime, not something to edit by hand: change the Context
and run `toa env` again.

The same set is given to deployed pods directly. A container reads no `.env` file.

A deployed pod carries only the variables of the components it runs. The address of the database
of `store.catalog` is not in a pod that does not run `store.catalog`.

## What is a secret

Two kinds of values are secrets.

**Credentials of infrastructure.** An address in the Context must not contain a user name or a
password. One that does is refused:

```
Pointer URI 'mongodb://user:pass@mongo.example.com' must not contain credentials.
```

The credentials are supplied as a secret with `username` and `password` keys.

**Secret configuration values.** A configuration value written as `$NAME` in the Context is a
reference to a secret, not a value:

```yaml
configuration:
  store.notifications:
    sender: orders@example.com
    apiKey: $EMAIL_API_KEY
```

[Configuration](../services/2.configuration.md#secrets) covers this in full. Other extensions have
secrets of their own, such as a storage provider's keys.

You do not need to work out the list. Ask for it.

## What a deployment needs

```shell
$ toa export secrets production
toa-amqp-context.default:
  username
  password
toa-configuration:
  EMAIL_API_KEY
toa-mongodb.default:
  username
  password
toa-storages-pictures:
  ACCESS_KEY_ID (optional)
  SECRET_ACCESS_KEY (optional)
```

Each block is one Kubernetes secret and the keys it must hold. A key marked `(optional)` may be
absent; the workload starts without it.

The list follows from the Context for that environment. Run the command again after changing
addresses, configuration or storages.

## Putting secrets in the cluster

```shell
$ toa conceal mongodb.default username=store password=s3cret
```

`toa conceal <secret> <key=value>...` creates the secret, or adds the keys to it if it exists.
Keys you do not mention are left as they are.

- The name is given **without** the `toa-` prefix; `toa conceal` adds it.
- `--namespace` chooses the Kubernetes namespace. Use the one you deploy into.

To be asked for every secret of an environment in turn, instead of naming them:

```shell
$ toa conceal --interactive --environment production
```

To read one back:

```shell
$ toa reveal mongodb.default
username: store
password: s3cret
```

Secrets can be created by other means: `kubectl`, an operator, a sealed-secrets workflow. They
then carry the `toa-` prefix themselves, exactly as `toa export secrets` prints the names.

### A deploy checks first

`toa deploy` reads the namespace's secrets before it builds anything and refuses if a required
key is missing, naming all of them:

```
Secrets are not deployed: toa-mongodb.default/username, toa-mongodb.default/password
```

Required are the keys `toa export secrets` lists, except the optional ones, plus the image pull
secret named by [`registry.credentials`](8.images.md#private-registries). Only presence is
checked. An empty value counts as present, and a wrong password is found by the process that
uses it.

Changing a secret's value does not restart anything. Pods read their secrets when they start, so
roll the workloads that use it for a new value to take effect.

## Secrets for a local run

Locally, secrets are lines of the `.env` file. `toa env` writes them with empty values and offers
two ways to fill them:

```shell
$ toa env local --dev           # fill what has a known local default
$ toa env local --interactive   # ask for each one
$ toa env local -d -i           # fill what can be filled, ask for the rest
```

`--dev` fills:

- `developer` / `secret` as the credentials of the default broker and database, which is what a
  local development stack is expected to use;
- freshly generated keys for identity tokens;
- any secret whose key is set in your shell's environment. With `EMAIL_API_KEY=... toa env -d`,
  the `$EMAIL_API_KEY` configuration secret takes that value.

Whatever is left is written empty. A component should treat an empty secret as "not configured"
where that is meaningful locally — for example, by not sending real email.

**A value already in the file is kept.** Fill a secret in by hand once, and later runs of
`toa env`, with any options and for any environment written to the same file, preserve it.

Keep `.env*` out of version control.

Do not read these variables from `process.env` in an operation: what `.env` holds is kept away
from component code on purpose. A secret reaches an operation through what declares it — a
configuration value through `context.configuration`, a storage's keys through the storage.

## Addresses

Addresses of infrastructure are ordinary Context values: `amqp`, `mongodb`, `stash`, and others
that connectors and extensions define. They share one syntax.

One address for everything:

```yaml
mongodb: mongodb://mongo.example.com
```

Different addresses for a namespace or a component. A component takes the most specific key that
matches its `<namespace>.<name>`:

```yaml
mongodb:
  .: mongodb://mongo.example.com
  store: mongodb://store.mongo.example.com
  store.catalog: mongodb://catalog.example.com
```

| Component | Takes |
| --- | --- |
| `store.catalog` | `catalog.example.com` |
| `store.orders` | `store.mongo.example.com` |
| `billing.invoices` | `mongo.example.com` |

`.` is the default. Without a `.` key, a component that matches nothing is refused by name.

A component without a namespace is in `default`: `default` addresses all of them,
`default.<name>` one.

Several addresses under one key, as a list or a range. Every component that resolves to the key
gets all of them:

```yaml
stash:
  .:
    - redis://redis0.example.com
    - redis://redis{1-3}.example.com
```

`{1-3}` expands to `redis1`, `redis2`, `redis3`.

Some keys have sections. The broker's own address is `amqp.context`, and `amqp: <address>` is
shorthand for it; the brokers that events of other applications come from are `amqp.sources`,
keyed by source:

```yaml
amqp:
  context: amqp://rmq.example.com
  sources:
    warehouse: amqp://rmq.warehouse.example.com
```

[Connectors](../services/12.connectors.md) describes each connector's keys.

## Credentials

Credentials belong to a *key* of the address map, not to a component. Every component that
resolves to a key shares its secret, and so does every address under that key.

The secret's name is the connector's identifier, then the key, with dots turned into dashes. The
`.` key is `.default`:

| Key in `mongodb` | Secret |
| --- | --- |
| `.` | `toa-mongodb.default` |
| `store` | `toa-mongodb-store` |
| `store.catalog` | `toa-mongodb-store-catalog` |

```shell
$ toa conceal mongodb-store-catalog username=catalog password=s3cret
```

For the broker the identifier is `amqp-context`, so the default secret is
`toa-amqp-context.default`, and a source's is `toa-amqp-sources-<source>`.

Each such secret holds `username` and `password`. An address on a protocol without credentials —
`redis`, `http`, `https` — has no secret.

Again, `toa export secrets` prints the exact names; the rule is here so that the output is not a
surprise.

## Per-environment values

Addresses vary by [environment](2.environments.md) with the usual suffix:

```yaml
mongodb@local: mongodb://localhost
mongodb@production: mongodb://mongo.internal.example.com
```

Secret *names* do not vary: `toa-mongodb.default` is the same name in every environment. The
values differ because each environment is a different namespace or cluster, or a different `.env`
file, holding its own.

## Checklist for a new environment

1. Add the environment's suffixed keys to the Context.
2. `toa export secrets <environment>` — see what it needs.
3. `toa conceal ...` for each secret, in the target namespace.
4. Create the image pull secret, if the registry is private.
5. `toa deploy <environment>`.
