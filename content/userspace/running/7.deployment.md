# Deployment

Deploying turns the Context into running processes. Toa ships tooling that does it for
Kubernetes in one command. Using it is a choice: an application runs wherever its processes can
be started. [Deployment](../../model/running/4.deployment.md) explains the approach; this article
shows both ways, starting with the supplied one.

## One command

```shell
$ toa deploy production --wait
```

This builds an image for every composition, pushes the images, renders a Helm chart from the
Context and applies it to the current Kubernetes context. Nothing else describes the deployment:
no Dockerfiles, no charts, no per-service manifests.

## What you need

On the machine that deploys:

- `@toa.io/operations` beside the CLI — see [Installing](6.cli.md#installing);
- `docker`, `helm` and `kubectl` on the `PATH`, logged in to the registry and pointed at the
  cluster. The current `docker` and `kubectl` contexts are the ones used.

In the Context:

```yaml
# context.toa.yaml
name: store
version: 1.4.0

registry:
  base: registry.example.com/store

resources:
  cpu: [200m, 1]
  memory: [256Mi, 1Gi]

amqp: amqp://rmq.internal.example.com
mongodb: mongodb://mongo.internal.example.com
```

- **`version`** is required to deploy. Without it:
  `Context 'store' declares no version, which is what its chart is versioned by.`
- **`registry.base`** is where images are pushed; see [Images](8.images.md).
- **`resources`** must be stated, on the Context or on every workload; see
  [Resources](3.compositions.md#resources).

In the cluster: the secrets the deployment refers to. That is the one thing a first deployment
needs prepared.

## A first deployment

```shell
$ toa export secrets production
toa-amqp-context.default:
  username
  password
toa-mongodb.default:
  username
  password

$ toa conceal amqp-context.default username=store password=...
$ toa conceal mongodb.default username=store password=...

$ toa deploy production --wait
```

`toa export secrets` lists what the cluster has to hold, `toa conceal` puts it there, and
`toa deploy` does the rest. [Variables and secrets](9.secrets.md) covers the first two.

## What `toa deploy` does

In order:

1. **Checks the secrets.** It reads the secrets of the namespace it deploys into and stops if a
   key a workload would read is missing, naming every one:

   ```
   Secrets are not deployed: toa-mongodb.default/username, toa-mongodb.default/password
   ```

   Nothing has been built or pushed at this point, so a refused deploy changes nothing.
2. **Builds and pushes** every image the registry does not already have.
3. **Renders the chart** into a temporary directory.
4. **Tags** each image with the environment's name, so the registry shows what an environment
   runs.
5. **Applies** the chart as a Helm release named after the Context.

### Options

```shell
$ toa deploy production --namespace store --wait --timeout 15m0s
```

- **`--namespace`** — the Kubernetes namespace of the release, and the one whose secrets are
  checked.
- **`--wait`** — return only when the rollout is complete: new replicas ready and the replaced
  ones gone. Without it the command returns once the chart is applied. Use it in a pipeline, so
  that a failed rollout fails the pipeline.
- **`--timeout`** — how long `--wait` may take; five minutes by default. A rollout that makes no
  progress for fifteen minutes fails regardless.
- **`--dry`** — print what would be applied and stop. No cluster is read, so it works without
  one.
- **`--mono`** — deploy the [single-image form](#one-image-for-everything).

To look at the chart as files instead:

```shell
$ toa export deployment production ./chart
```

## What gets deployed

| For | Kubernetes objects |
| --- | --- |
| each [composition](3.compositions.md) | a `Deployment` named `composition-<name>` |
| each extension service no composition runs | a `Deployment` named `extension-<group>-<name>` |
| each service that listens on a port | a `Service` of the same name |
| each service reachable from outside | an `Ingress` of the same name |
| the [component map](4.contracts.md) | a `ConfigMap`, mounted into every pod |

The gateway, for example, is `extension-exposition-gateway`.

Pods carry labels you can select by:

| Label | On |
| --- | --- |
| `toa/composition: <name>` | the pods of a composition |
| `toa/component-<namespace>-<name>: "1"` | pods running that component |
| `toa/service-<group>-<name>: "1"` | pods running that service |

```shell
$ kubectl get pods -l toa/component-store-orders
```

Each container runs one fixed command: `toa compose` for a composition, `toa serve` for a
service, `toa mono` for the single-image form. It is not configurable. What a component needs to
do when it starts belongs in its [run commands](../components/10.lifecycle.md).

## How a rollout behaves

These are fixed, and worth knowing because your components live under them.

**Nothing is replaced until its replacement is ready.** All new replicas of a workload start at
once, and old ones are removed as new ones report ready. During that time both versions serve;
[Contracts](4.contracts.md#rolling-upgrades) says what that requires of a change.

**A replica has five minutes to start.** Readiness is polled every two seconds, and a replica
that has not reported ready within five minutes is restarted. Everything a component does before
it serves counts: its `preflight` run command, and its migrations.

**A replica has 45 seconds to stop.** When asked to stop, it keeps serving for five seconds while
traffic is routed away, then finishes what is in progress and disconnects. An operation still
running when the time is up is cut off; whatever was calling it sees a failure, and the usual
[delivery](../../model/reliability/1.delivery.md) rules apply.

**Replicas are spread across nodes** where the cluster has room, counted per release, so a
rollout is not held back by where the old pods are. This needs Kubernetes 1.27 or later.

**What did not change is not redeployed.** An image is identified by the content it was built
from, so a release that changes one component rolls out the composition containing it and leaves
the others running.

## Probes and ports

A workload reports readiness over HTTP, and the deployment wires the probes itself:

- a composition answers `GET /.ready` on port `8001` once all its components are connected;
- the gateway answers on its own port, `8004`.

The ports the platform uses are listed in [Ports](3.compositions.md#ports). Your components do
not open ports of their own: they are reached through the broker, and streamed calls use `8005`.

## Ingress

Services that are reachable from outside — the gateway, the introspection and configuration
UIs — declare their own port and path. The Context says where they land, once for all of them:

```yaml
ingress:
  hosts:
    - api.example.com
  class: nginx
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: 16m
  default: true
```

| Key | Meaning |
| --- | --- |
| `hosts` | hostnames of the ingress rules; at least one |
| `class` | the ingress class |
| `annotations` | annotations copied onto every `Ingress` |
| `default` | `true` adds a rule without a host, as a fallback |

`hosts` must be hostnames the gateway is configured to answer on, since the UIs are published
on the same hosts and call the API beside them.

A service that needs an ingress where no host is given is refused:

```
Service 'introspection-explorer' declares an ingress, but no hosts are defined. Declare them in
the context's 'ingress' section.
```

## Migrations at deploy time

A component's [migrations](../components/12.migrations.md) are applied by the component itself
when it starts, not by `toa deploy`. For a deployment this means:

- The first new replica to start applies them; the others wait. A migration is applied once per
  database.
- They run **before the component serves**, inside the five-minute start limit. A backfill over
  a large collection does not belong in a migration; put it in an operation and call it.
- They run **while the previous release is still serving**. The old replicas keep reading and
  writing the data a migration just changed, so a migration must leave the data usable by the
  previous release. Where it cannot, do not roll: see
  [Changes that cannot be rolled](4.contracts.md#changes-that-cannot-be-rolled).
- Migrations of an [evicted](3.compositions.md#leaving-things-out) component are not applied by
  the deployment. They are applied when whatever runs that component starts it.

## One image for everything

`--mono` deploys the whole application as one workload: every component and every extension
service in a single process.

```shell
$ toa deploy staging --mono
```

It produces one `Deployment`, one `Service` and one `Ingress`, all named `mono`. The ingress
serves every service's path, and the service fronts every port.

```yaml
# context.toa.yaml
mono:
  replicas: 2
  resources:
    cpu: [200m, 2]
    memory: [256Mi, 2Gi]

mono@preview:
  replicas: 1
```

Without `mono`, it runs two replicas with the Context's `resources`. Evicted components are left
out, as in any deployment.

This form suits small installations, previews and early stages. `toa build --mono`,
`toa export deployment --mono`, `toa export images --mono` and `toa export tags --mono` use the
same layout.

Switching between `--mono` and compositions later changes nothing in the components.

## Deploying from a pipeline

A pipeline does what you do by hand: log in to the registry, point `kubectl` at the cluster,
install dependencies, and deploy.

```shell
$ npm ci
$ npx toa deploy production -n store -p application --wait --timeout 15m0s
```

Three practical notes:

- Give the same environment name, or chain, to every command of a pipeline.
- Secrets are not part of a deploy. They are put in the cluster once, by whoever may know them,
  and the deploy only checks they are there.
- A pipeline interrupted in the middle of a rollout can leave the Helm release in a pending
  state, which makes Helm refuse the next one. Check `helm status <context name>` and roll back
  or uninstall the pending release before deploying again.

To separate building from deploying, run `toa push` first. A deploy of sources that were already
pushed builds nothing.

## Without the supplied tooling

Nothing in the runtime requires Kubernetes. A process needs:

- Node.js and the application's sources with their dependencies installed, including
  `@toa.io/runtime`;
- the variables of its environment — what `toa env <environment>` writes — in its environment
  or in a `.env` file;
- the component map, written by `toa map <environment>`;
- network access to the broker, the database and whatever else the Context names.

Then start processes with the same commands the images use:

```shell
$ toa compose components/store.orders components/store.accounts
$ toa serve exposition
```

or everything at once with `toa mono components/*`. Run as many copies of each as you want
replicas. Process supervision, restarts and rolling replacement are then yours to arrange, and
the rules in [Contracts](4.contracts.md#rolling-upgrades) apply to however you replace them.

A middle way is to let Toa build and render, and apply the result yourself:
`toa push`, then `toa export deployment` for the chart.
