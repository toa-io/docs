# Halt

A halt stops a whole deployment cleanly: every process finishes what it has, closes every
connection to the broker, the database and the cache, stays down for an interval you choose, and
comes back by itself. Nothing is lost and nothing is left half-done.
[Halt](../../model/running/6.halt.md) explains the idea.

Use a halt to work on what the deployment runs on — upgrade the broker, fail the database over,
take a consistent backup — and to deploy a release that cannot run beside the previous one.

## Enabling

Halt is off by default. Turn it on in the Context:

```yaml
# context.toa.yaml
introspection:
  halt: true
```

It is part of [introspection](../services/11.introspection.md#the-context-annotation), which in turn
needs the gateway, so both must be in use.

With halt on, **every component must be on the introspection map.** A component that declares
`introspection: false` in its manifest fails the build, because the map is what decides whether
the deployment has gone quiet.

### Limits

How long a halt may last, and how long the deployment may be given to go quiet, are yours to
bound:

```yaml
introspection:
  halt:
    duration: [30, 3600]
    quiescence: [30, 1800]
```

Each pair is `[min, max]` in seconds. These values are the defaults, and `halt: true` means
exactly them.

- **`duration`** — how long the deployment may stay down.
- **`quiescence`** — how long it may be given to finish its work before it is checked.

A request outside the limits is not refused. It is carried out with the nearest allowed value.

## Requesting a halt

A halt is requested over the gateway:

```http
POST /introspection/signals/ HTTP/1.1
content-type: application/yaml

type: halt
seconds: 300
quiescence: 60
```

| Field | Required | Meaning |
| --- | --- | --- |
| `type` | yes | `halt` |
| `seconds` | yes | how long every process stays down |
| `quiescence` | yes | how long the deployment gets to go quiet before it is checked |
| `grace` | no | seconds a process that found work still going on waits for another to confirm the stop; `2` to `120`, `10` by default |

To read the limits a request must fit:

```http
GET /introspection/signals/ HTTP/1.1
```

```yaml
halt:
  duration: [30, 3600]
  quiescence: [30, 1800]
```

Both routes require the `system:halt` role; [Roles and Bans](../identity/7.roles.md#granting) covers
granting roles. A deployment with halt off has neither route.

There is no CLI command for a halt. It is an HTTP request to the gateway of the deployment being
halted.

## What happens

1. **Everything goes quiet.** The gateway answers `503`. [Pulses](../flow/1.pulses.md) stop firing
   and [delayed calls](../flow/3.delays.md) stop being dispatched. Each component's `pause` run
   command runs. Nothing is closed yet.
2. **Work in progress finishes.** For `quiescence` seconds the deployment completes what it
   already had: calls are answered, events delivered, queued tasks run.
3. **The deployment checks that it is idle.** If nothing anywhere was called since the signal,
   the stop is confirmed.
4. **Every connection closes.** No process holds anything open against the broker, the database
   or the cache.
5. **After `seconds`, every process rebuilds itself and carries on.**

**If anything was still working at the check, the halt is called off.** Nothing had been closed.
Every process resumes, and each component's `resume` run command runs. A deployment is never
stopped on a guess.

## What clients see

- **Requests to the gateway** get `503` with a `retry-after` header saying when the deployment is
  back. Clients should honour it.
- **Calls between components** made just before the stop wait on the broker and are served when
  the deployment returns, within the caller's own timeout.
- **A reply that was streaming** is cut when connections close. Its reader has to ask again.
- **Pulses** that would have fired during the halt are skipped, not made up afterwards.
- **Delayed calls** that came due during the halt are made when the deployment is back, unless
  their own `overdue` setting says they are then too late.

Processes are not restarted or replaced. They keep answering their readiness probe, so the
cluster sees nothing wrong.

## What your components must do

For most components: nothing. Operations, receivers, pulses and everything else that goes through
the operation context are quieted and restored by the runtime.

What needs your attention is anything a component **started itself**: a timer, a file watcher, a
connection to an external system opened in a [run command](../components/10.lifecycle.md). The
runtime did not create it and cannot stop it. If it keeps working, the deployment never looks
idle and **every halt is called off**.

Such a component takes part explicitly, with the `pause` and `resume` run commands:

```javascript
// components/store.catalog/rc/poller.js

export function preflight (context) {
  context.state.poller = setInterval(() => poll(context), 1000)
}

export function pause (context) {
  clearInterval(context.state.poller)
}

export const resume = preflight
```

`pause` runs when the deployment is told to go quiet, while the component is still whole and
serving. Release there whatever would otherwise keep working.

What `pause` released has to be taken again, and there are two ways a component comes back:

- **The halt went through.** The component was taken down and is built anew. `preflight` runs,
  as on any start.
- **The halt was called off.** The component is the same one, with the same `context.state` and
  everything it opened still open. Only `resume` runs.

So both `preflight` and `resume` must restore what `pause` stopped. Usually they are the same
function, as above.

**A component that exports `pause` without `resume` does not start.** It would come back from a
cancelled halt without what it paused.

`context.state` requires the component to declare `state: ~`; see
[Stash and State](../services/5.stash-and-state.md#state).

### Module scope survives a halt

A halt rebuilds what the runtime built. Your modules stay loaded, so a variable at module scope
is the same object afterwards. A connection kept there was neither closed by the halt nor
reopened after it:

```javascript
// kept at module scope: the halt does not touch it
const client = connect()
```

Either keep such things in `context.state` and manage them in `preflight`, `pause` and `resume`,
or close and reopen them yourself in the same commands.

### Forgotten timers

A timer that was not stopped will fire while the component is down and try to call through a
context that no longer exists. That call is refused. During the halt it is logged as a warning.
Once the process is working again, the same refused call ends the process, because a stale
context in a live process is a defect.

Test this with the stage: see [Pausing](5.testing.md#pausing).

## Choosing the numbers

- **`seconds`** is how long the work you are doing takes, plus margin. **A halt cannot be ended
  from outside**: the processes hold no connection through which anything could reach them. The
  deployment comes back when the interval is over, whether or not you are finished. Ask for an
  interval you can afford to be down for.
- **`quiescence`** is how long your slowest in-flight work takes. A deployment with long tasks
  needs a longer window. If halts keep being called off, either lengthen it or find the component
  that does not stop.

The one way to end a halt early is to start a new process: one that starts during a halt comes up
working. Whether you can do that depends on what supervises your processes.

## Deploying a release that cannot be rolled

Some changes cannot be deployed by a rolling update, because old and new replicas cannot serve
together: a renamed input property, an entity property that changes meaning, a migration the
previous release cannot read. See [Contracts](4.contracts.md#changes-that-cannot-be-rolled).

With a halt:

1. Request a halt with an interval the rollout fits into.
2. When the deployment is down, deploy the new release: `toa deploy production --wait`.
3. The new processes start working immediately. The halted ones are replaced by the rollout and
   never serve beside them.

Since the halt waited for all work to finish, nothing in transit was shaped for the old release.

If the halt is called off, nothing happened: fix what kept the deployment busy, or ask for a
longer `quiescence`, and try again. Do not deploy the incompatible release without it.

## Limits

- **It covers the processes that were connected when it was requested.** A process that starts
  during the quiet phase works normally, shows up as activity, and the halt is called off.
- **It reaches one deployment.** [Regions](10.regions.md) are separate deployments; each is
  halted through its own gateway.
- **A second request during a halt is ignored.**
- **It is for a healthy deployment.** A process that is disconnected from the broker never hears
  the signal. A halt is not a way to bring a broken deployment to rest.
- **Nothing reports the outcome back to the request.** What became of a halt is in the signal
  records: a `stop` record names the halt it answers, so a halt with no stop beside it was
  called off.

## Rehearse it

A halt is used rarely and under pressure, and whether it works depends on every component
behaving as described here. A new component with an unmanaged timer is enough to break it.

Run a halt on a schedule, with a short interval, in conditions where nothing is at stake. The day
it is needed should not be the first time it is tried.
