# Testing

An operation is a function, and its pure parts can be tested as functions. What makes a component
a component — schemas, state, events, calls to other components — only exists when the runtime
runs it. The *stage* boots components inside a test process, so a test calls real operations
against real infrastructure and checks what comes back.

## Setup

The stage is part of the `@toa.io/userland` package:

```shell
$ npm i -D @toa.io/userland
```

It works with any test runner. The examples use Node's own.

A staged component needs what a locally run one needs: the variables
[`toa env`](2.environments.md#the-local-environment) writes, and the infrastructure they point to.
The stage finds the `.env` file by walking up from the working directory, exactly as `toa compose`
does. So before the tests:

```shell
$ toa env local --dev
```

## The smallest test

```javascript
// test/orders.test.js
import { it, before, after } from 'node:test'
import assert from 'node:assert/strict'
import { resolve } from 'node:path'
import * as stage from '@toa.io/userland/stage'

const components = resolve(import.meta.dirname, '../components')

let orders

before(async () => {
  orders = await stage.component(resolve(components, 'store.orders'))
})

after(async () => {
  await stage.shutdown()
})

it('creates an order', async () => {
  const order = await orders.invoke('create', {
    input: { customer: 'c1', items: [{ product: 'p1', quantity: 2 }], total: 1800 }
  })

  assert.equal(order.status, 'pending')
})
```

`stage.component(path)` boots one component from its directory and returns it.
`invoke(endpoint, request)` calls an operation with a [request](../components/4.requests.md) and
resolves to the reply. `stage.shutdown()` disconnects everything the test staged.

## Replies, errors and exceptions

`invoke` behaves like a call from another operation:

- an output is returned;
- a declared [error](../components/3.errors.md) is returned as an `Error` with a `code`;
- an exception is thrown, so the promise rejects.

```javascript
it('refuses to approve twice', async () => {
  const { id } = await orders.invoke('create', { input: order })

  await orders.invoke('approve', { query: { id } })

  const reply = await orders.invoke('approve', { query: { id } })

  assert.ok(reply instanceof Error)
  assert.equal(reply.code, 'NOT_PENDING')
})

it('rejects invalid input', async () => {
  await assert.rejects(orders.invoke('create', { input: { total: 'a lot' } }))
})
```

A request that does not fit the operation's contract is an exception, as it is everywhere.

A helper that fails the test on an unexpected error keeps the tests short:

```javascript
async function call (component, endpoint, request) {
  const reply = await component.invoke(endpoint, request)

  assert.ok(!(reply instanceof Error), reply.code)

  return reply
}
```

## Several components together

`approve` calls `store.accounts.debit`. To test it, both components must run. A composition boots
several components in one process, the way `toa compose` does:

```javascript
let orders
let accounts

before(async () => {
  const paths = ['store.orders', 'store.accounts'].map((name) => resolve(components, name))

  await stage.composition(paths)

  orders = await stage.remote('store.orders')
  accounts = await stage.remote('store.accounts')
})

after(async () => {
  await stage.shutdown()
})

it('debits the account on approval', async () => {
  const account = await accounts.invoke('transit', { input: { balance: 5000 } })
  const order = await orders.invoke('create', {
    input: { customer: account.id, items: [], total: 1800 }
  })

  await orders.invoke('approve', { query: { id: order.id } })

  const after = await accounts.invoke('observe', { query: { id: account.id } })

  assert.equal(after.balance, 3200)
})
```

`stage.composition(paths)` returns nothing. To call a composed component, connect to it with
`stage.remote(id)`, where `id` is `<namespace>.<name>`; a name without a namespace is taken as
`default.<name>`. A remote has the same `invoke`.

A call through a remote travels the way a call from another process does: it is validated against
the contract and goes through the broker. That is the most faithful way to test, and it is what
`toa call` does on the command line.

`stage.compose` is another name for `stage.composition`.

## The whole application

To stage everything, pass every component directory:

```javascript
import { readdir } from 'node:fs/promises'

const entries = await readdir(components, { withFileTypes: true })
const paths = entries
  .filter((entry) => entry.isDirectory())
  .map((entry) => resolve(components, entry.name))

await stage.composition(paths)
```

Leave out what cannot run in a test, such as a component that is
[evicted](3.compositions.md#leaving-things-out) because it needs special hardware.

A common arrangement for end-to-end tests is to stage the application once before the whole
suite, send requests to it from the tests — through remotes, or over HTTP through a gateway
started beside it — and shut the stage down after the suite.

## Events

A composition booted in a test publishes every event, whether or not anything consumes it.

Receiving is asynchronous: when `approve` resolves, the receivers of `approved` may not have run
yet. Poll for the effect with a deadline instead of sleeping for a fixed time:

```javascript
// `store.accounts` counts a customer's approved orders through a receiver
it('counts the approved order', async () => {
  await orders.invoke('approve', { query: { id: order.id } })

  const deadline = Date.now() + 5000
  let account

  do {
    await new Promise((resolve) => setTimeout(resolve, 50))

    account = await accounts.invoke('observe', { query: { id: order.customer } })
  } while (account.orders !== 1 && Date.now() < deadline)

  assert.equal(account.orders, 1)
})
```

[Committed events](../../model/reliability/2.outbox.md) are published on a cycle, five seconds by
default, when the immediate publication fails. Tests that depend on that path can shorten the
cycle for the local environment:

```yaml
# context.toa.yaml
outbox:
  interval@local: 100
```

To test a receiver without its publisher, call the operation the receiver is bound to with the
payload the event would carry. That tests the operation; the binding between event and operation
is exercised by a composition that holds both.

## Variables set by a test

Variables present in `process.env` when a component or composition is staged are taken into
account, and win over the `.env` file. A test can therefore set what it needs before staging:

```javascript
before(async () => {
  process.env.TOA_OUTBOX_INTERVAL = '100' // the same setting, for this test alone

  await stage.composition(paths)
})
```

Set them before the first `stage` call that boots something. Changing `process.env` afterwards
does not affect what is already running.

## Contracts in tests

A staged composition is not given a [map](4.contracts.md) unless the test states one. Without
one, components composed together know each other, which is enough for most tests.

When the staged components call something the test does not compose — a service running beside
the test, for instance — give the stage the map the same way a process gets it:

```javascript
import { readFile } from 'node:fs/promises'

before(async () => {
  stage.map(JSON.parse(await readFile(resolve(root, '.map.json'), 'utf8')))

  await stage.composition(paths)
})
```

Write the file with `toa map` before the tests run. `stage.shutdown()` forgets the map, so state
it again in the next `before`.

## Services

`stage.serve(reference)` starts an extension service in the test process, named by shortcut or
package name, as `toa serve` does:

```javascript
await stage.composition(paths)
await stage.serve('exposition')
```

The gateway then answers HTTP on its configured port, and a test can send requests through it.
The service needs its variables in the environment, as it does when run by `toa serve`.

## Pausing

A component that starts work of its own — a timer, a watcher — takes part in a
[halt](11.halt.md) through its `pause` and `resume`
[run commands](../components/10.lifecycle.md). The stage can trigger both:

```javascript
await stage.halt()      // every staged composition goes quiet: `pause` runs
await stage.restore()   // and works again: `resume` runs
```

This is the way to test that a component stops what it started and takes it up again.

## Shutdown

Always call `stage.shutdown()` when the tests are done, usually in `after`. It disconnects every
component, composition, service and remote the stage created, in one call. A test process that
does not shut the stage down keeps its connections and does not exit.

After a shutdown the stage is empty and can be used again.

## Reference

| Function | Does | Returns |
| --- | --- | --- |
| `component(path)` | boots one component from its directory | the component |
| `composition(paths)`, `compose(paths)` | boots components as one composition | nothing |
| `remote(id)` | connects to a running component by `<namespace>.<name>` | the component, as a caller sees it |
| `serve(reference)` | starts an extension service | the service |
| `map(contracts)` | states the component map for what is staged next | nothing |
| `manifest(path)` | reads and normalizes a component's manifest | the manifest |
| `halt()`, `restore()` | makes staged compositions go quiet, and work again | nothing |
| `shutdown()` | disconnects everything staged | nothing |

All but `map` are asynchronous. A component and a remote both have
`invoke(endpoint, request)`.

## Checking a composition starts

Outside of tests, the CLI can check that a set of components boots at all, which is a cheap
guard for a pipeline:

```shell
$ toa compose ./components/* --kill
```

`--kill` shuts the composition down as soon as it has started, and the command exits with `0`
when both went well. With `--dock` the same check runs inside the image a deployment would
build, which also proves the image builds and installs what the components need:

```shell
$ toa env docker --dev --as .env.docker
$ toa compose ./components/* --dock --kill --env .env.docker
```

`toa mono ./components/* --kill` does the same for the single-process form.
