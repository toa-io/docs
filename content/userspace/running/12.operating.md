# Operating

What exists for whoever looks after a running application: how to see what is deployed, where to
look when something is stuck, and a few tools for work around a deployment. All of it assumes the
application was deployed with the supplied tooling, as [Deployment](7.deployment.md) describes.

## What is running

The deployment is one Helm release, named after the Context:

```shell
$ helm status store -n store
$ helm history store -n store
```

Workloads are named after what they run, and pods are labelled by composition, component and
service:

```shell
$ kubectl get deployments -n store
composition-core
composition-media
extension-exposition-gateway
extension-configuration-values

$ kubectl get pods -n store -l toa/composition=core
$ kubectl get pods -n store -l toa/component-store-orders
$ kubectl logs -n store -l toa/component-store-orders --tail 100
```

The label of a component is the quickest way from "something is wrong with orders" to the pods
that run it, whatever composition it is in.

### Which version

```shell
$ toa export tags production
```

prints the image every workload of `production` would run for the sources you have checked out.
Compare it with what the cluster runs to see whether a checkout is what is deployed.

In the registry, the `:<environment>` tag of each image points at what was last deployed to that
environment.

For a single component, the [component map](4.contracts.md#reading-a-deployed-map) mounted into
every pod states the version of each component the deployment intends to run:

```shell
$ kubectl exec -n store <pod> -- zcat /etc/toa/.map.json.gz | grep store.orders
```

### Is it ready

A pod is ready when all its components are connected to everything they use. A pod that stays
unready is waiting for something: the broker, the database, a migration in progress.

```shell
$ kubectl describe pod -n store <pod>
$ kubectl logs -n store <pod>
```

A process that cannot start, or fails later, exits and writes one `Process failed` log record
with the reason — `command failed`, `uncaught exception` or `unhandled rejection` — and the
error. Search the logs for it first.

A composition refused at start for a version mismatch says so:

```
'store.orders' is composed at a version the component map does not state. Run `toa map`.
```

In a deployment this means an image and the map came from different sources, which happens when
an [evicted](4.contracts.md#an-evicted-component) component is built separately.

## Rolling back

There is no rollback command in Toa. Two ways:

- **Deploy the previous sources.** Check out the previous release and run `toa deploy` again. If
  its images are still in the registry, nothing is rebuilt.
- **`helm rollback store <revision>`**, which reapplies an earlier chart. It works as long as the
  images that chart pins still exist.

Either way, a rollback is a rollout in the other direction, and the rules of
[rolling upgrades](4.contracts.md#rolling-upgrades) apply: the release you return to must be able
to live with data the newer one wrote and with migrations it applied. Migrations are not undone.

How far back you can go is what your registry's retention keeps; see
[Cleaning your registry](8.images.md#cleaning-your-registry).

## Messages that could not be handled

An event or a [task](../reliability/4.tasks.md) that keeps failing is retried with growing pauses,
and then set aside rather than lost or retried forever.
[Delivery](../../model/reliability/1.delivery.md) explains the behaviour;
[Delivery and Retries](../reliability/1.delivery.md) covers it from the component's side.

For an operator this means there are two places where undelivered work accumulates. Watch both.

### Parked messages

Messages that exhausted their retries, or could never succeed — a payload that does not fit the
receiver's contract, a call that went round in a circle — are parked on the broker, in the queue
`comq.parked`. It is shared by every application on that broker's virtual host.

```shell
$ rabbitmqctl list_queues name messages | grep comq
```

A message arriving there is a defect or an outage that outlasted the retries. An alert on the
depth of that queue is the single most useful one to have.

Each parked message says where it came from in its headers:

| Header | Holds |
| --- | --- |
| `x-comq-queue` | the queue it was consumed from |
| `x-comq-exchange`, `x-comq-key` | where it was originally published |
| `x-comq-reason` | the message of the exception that failed it |
| `x-comq-at` | when it was parked |

Nothing consumes the queue, and it grows until somebody drains it. To handle a parked message,
inspect it with the broker's tools, fix the cause, and publish the message again to where it came
from. The broker's own management tooling does this; Toa has no command for it. Do not delete
`comq.parked` or the `comq.retry.*` queues on a running system.

Remember that receivers may run more than once for one message, so putting a message back is
safe for a correctly written receiver.

### Unpublished events

[Committed events](../../model/reliability/2.outbox.md) are stored with the state change that
caused them and published right after. One that could not be published stays stored and is
retried on a cycle until it goes out. It is never dropped and never expires.

Each component with events has a collection for them beside its entities, named
`<namespace>_<name>_outbox`. What is stuck, oldest first:

```javascript
db.store_orders_outbox.find({ published: false }).sort({ _id: 1 })
```

In a healthy deployment this is empty or nearly so. Rows that stay mean publication keeps
failing: the broker is unreachable, or an event's payload function throws. The second case blocks
every event of that state change, so look in the component's log for the exception.

Published rows are kept for a while as a change log — `outbox.retention` in the
[Context](1.context.md#runtime-settings) — and then expire.

## A look from inside the cluster

```shell
$ toa shell
$ toa shell mongo
$ toa shell -- nslookup rmq.internal.example.com
```

`toa shell` starts a throwaway pod in the current Kubernetes context and opens a shell in it,
with an image of your choice. Use it to check that the broker, the database or an external
service is reachable from where the application runs, with the same network rules. The pod is
removed when you leave.

To check a secret's content:

```shell
$ toa reveal mongodb.default
```

## Changing things without a release

**A secret.** `toa conceal` updates it; restart the workloads that use it:

```shell
$ toa conceal mongodb.default password=n3w
$ kubectl rollout restart deployment/composition-core -n store
```

**Replicas and resources.** They are declared in the Context. Change them there and deploy;
when only they changed, nothing is rebuilt. A change made with `kubectl scale` lasts until the
next deploy.

**Configuration values.** Declared in the Context and applied by a deploy.
[Changing Configuration](../services/3.configuration-values.md#deploying-again) says what is picked
up without a restart.

## The built-in UIs

Two extension services publish a web page on the hosts of the Context's
[`ingress`](7.deployment.md#ingress):

- the **introspection explorer** at `/.introspection/`: the application's topology — components,
  their operations and events, and which of them actually call each other;
- the **configuration UI**, for the values the configuration service serves.

The topology is the place to answer "who calls this?" before changing a contract, and "what would be
affected?" before taking a component down. They are covered in
[Introspection](../services/11.introspection.md#the-page) and
[Changing Configuration](../services/3.configuration-values.md#the-page).

## Stopping for maintenance

To stop the whole deployment cleanly for a while — to upgrade the broker or the database, or to
take a consistent backup — use a [halt](11.halt.md). It waits for work in progress, closes every
connection, and brings the deployment back by itself.

Scaling workloads to zero also stops them, but cuts off whatever is in progress; the delivery
guarantees repair that afterwards with retries. Prefer a halt when you can plan.

## A second copy on the same infrastructure

Sometimes you need another copy of the application next to the first, on the same broker,
database and cache, with the two seeing nothing of each other: a preview, a load test, a
rehearsal of an upgrade.

Every process names what it keeps after the Context's name. `TOA_SUFFIX` is appended to that
name:

```shell
$ TOA_SUFFIX=-preview toa compose ./components/*
```

| Where | Without a suffix | With `-preview` |
| --- | --- | --- |
| MongoDB | database `store` | database `store-preview` |
| Broker | queues and exchanges named by component | the same, prefixed with `store-preview.` |
| Redis | keys under `store:` | keys under `store-preview:` |

Rules:

- **Letters, digits and hyphens only.** Anything else, or an empty value, fails the start.
- **The suffix is appended as is.** Begin it with the separator you want.
- **Context name plus suffix is at most 63 bytes.** A longer one fails the start of a component
  with state.
- **It is read when the process starts**, from its environment or its `.env` file.
- **A copy starts empty.** It has its own database, queues and keys, and none of the first
  copy's data.
- **Not everything is separated.** Retry and parked queues on the broker are shared. Files in
  [storages](1.context.md#infrastructure-and-extensions) and the brokers of
  [regions](10.regions.md) are named as configured, so point a copy's storages elsewhere if it
  must not touch the originals.
- **Events from other applications do not arrive.** A receiver with a `source` listens under
  the suffixed name, which no outside publisher uses. Test such flows without a suffix.

## Several regions

When the application runs as [regions](10.regions.md), a few more things are worth watching:

- the depth of the `convergence.<namespace>.<name>` queues on each region's convergence broker.
  A queue that grows means a region is not applying changes;
- returned messages in a region's log: a component exists in one region and not another;
- an error about a record carrying the region's own rank: two regions share a `priority`.

## A short checklist

Worth having in place before an application matters:

- an alert on the depth of `comq.parked`;
- an alert on unpublished outbox rows older than a few minutes;
- an alert on `Process failed` log records;
- registry retention that keeps what each environment tag points at;
- a scheduled [halt rehearsal](11.halt.md#rehearse-it), if halt is something you count on;
- `--wait` on the deploy in the pipeline, so a failed rollout is noticed.
