# A First Component

The application is a small shop. Its first component keeps orders.

## A manifest is a component

```yaml
# components/store.orders/manifest.toa.yaml
name: orders
namespace: store

entity:
  properties:
    customer:
      type: string
    total:
      type: integer
      minimum: 0
    status:
      type: string
      enum: [pending, approved, cancelled]
  required: [customer, total, status]
  blank:
    status: pending
```

This is a complete, working component, with no code. `entity` describes the state of one order as
a JSON Schema; `blank` is what an order holds before anything is written to it.

A component that declares an entity inherits a set of operations from the
[generic prototype](../components/5.prototype.md):

| Operation | What it does |
| --- | --- |
| `transit` | Creates an order, or changes one, from its input. |
| `observe` | Returns one order. |
| `enumerate` | Returns a list of orders. |
| `assign` | Sets the given properties of an order. |
| `terminate` | Deletes an order. |

With the component running ([Running Locally](3.running.md) shows how), an order is created by
calling `transit` with the state as input, and no query:

```shell
$ toa call store.orders.transit "{ input: { customer: 'c1', total: 1500 } }"
```

```javascript
{
  id: '5b1ad5d8a4c54e1dbb2a4a0b6e1f0c11',
  customer: 'c1',
  total: 1500,
  status: 'pending',
  VERSION: 1,
  CREATED: 1764000000000,
  UPDATED: 1764000000000,
  DELETED: null,
  REGION: 0
}
```

The runtime assigned the `id`, filled `status` from `blank`, validated the result against the
schema, and stored it. The properties in capitals are the runtime's own; see
[Manifest](../components/1.manifest.md#system-properties).

The same operation with a query changes the order the query selects:

```shell
$ toa call store.orders.transit "{ query: { id: '5b1ad5d8a4c54e1dbb2a4a0b6e1f0c11' }, input: { total: 1200 } }"
$ toa call store.orders.observe "{ query: { id: '5b1ad5d8a4c54e1dbb2a4a0b6e1f0c11' } }"
$ toa call store.orders.enumerate "{ query: { criteria: 'status==pending', limit: 10 } }"
```

A request has two parts: `input` carries the arguments of the operation, `query` selects the
state it works on. [Requests](../components/4.requests.md) covers both.

## An operation of your own

`transit` lets any caller write any valid state. A shop needs rules: an order is approved only
while it is pending. A rule is an operation, and an operation is a file in the component's
`operations` directory, named after the operation:

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, entry) {
  if (entry.status !== 'pending')
    return new Error('NOT_PENDING')

  entry.status = 'approved'

  return entry
}
```

The name of the exported function says what the operation is: a `transition` reads the current
state, changes it, and has the change stored. The name of the second parameter says how much
state it works on: one `entry`. The runtime reads both from the file, so the manifest only adds
what the code cannot say:

```yaml
# components/store.orders/manifest.toa.yaml
operations:
  approve:
    concurrency: retry
    query: true
    errors: [NOT_PENDING]
```

- `concurrency: retry` — if the order changed while the operation was running, run it again on
  the fresh state.
- `query: true` — a call must select an order; `approve` never creates one.
- `errors` — the refusals the operation may answer with.

```shell
$ toa call store.orders.approve "{ query: { id: '5b1ad5d8a4c54e1dbb2a4a0b6e1f0c11' } }"
```

The function did not load the order, check its version, validate the result, or save it. It
decided. That division is what everything else builds on: you write decisions and
declarations, and the runtime does what surrounds them. The reasons are in
[Product–Platform Separation](../../model/foundations/1.separation.md).
