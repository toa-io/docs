# The OAuth Server

Other programs sometimes need to act for one of your users: a desktop client, an automation, an AI
assistant calling the application's tools over MCP. The gateway can act as an OAuth 2.1
authorization server for them. The user consents on a page your application serves, and the client
receives a token of that user's identity, optionally limited to some scopes and to one entry point.

The gateway serves everything except the consent page. That page needs a person, so it is yours to
build; most of this article is about it.

## Turning it on

```yaml
# context.toa.yaml
exposition:
  authorities:
    store: api.store.example.com
  oauth:
    authorize: https://store.example.com/oauth/authorize
```

Without `oauth` no authorization server exists. With it:

| Key | Meaning | Default |
| --- | --- | --- |
| `authorize` | Required. The absolute URL of the consent page. | |
| `resources` | Paths advertised as protected resources, for example `['/.mcp']`. | none |
| `scopes` | Scopes advertised as what a client may ask for. | none |
| `registration` | `open` lets clients register themselves; `closed` does not advertise it. | `closed` |

The issuer is `https://` followed by the authority's host. An authorization server needs TLS in
front of the gateway.

## What a client does

Nothing here is yours to implement, but it helps to know the sequence the client follows, since
the consent page is one step of it.

1. The client calls a protected entry, such as `/.mcp`, without a token and is refused:

   ```http
   401 Unauthorized
   www-authenticate: Bearer resource_metadata="https://api.store.example.com/.well-known/oauth-protected-resource/.mcp", scope="store:orders"
   ```

2. It reads the document that header names, then the authorization server's metadata.
3. It identifies itself, by registering or by a published metadata document.
4. It opens your consent page in the user's browser.
5. Your page redirects back to the client with a code.
6. The client exchanges the code for an access token and repeats step 1 with
   `authorization: Bearer <token>`.

Once `oauth` is annotated, every `401` of the gateway carries the `www-authenticate` challenge.

## Discovery

The documents are served to anyone, at the paths the specifications fix.

```http
GET /.well-known/oauth-authorization-server HTTP/1.1
host: api.store.example.com
accept: application/yaml
```

```yaml
issuer: https://api.store.example.com
authorization_endpoint: https://store.example.com/oauth/authorize
token_endpoint: https://api.store.example.com/identity/grants/
registration_endpoint: https://api.store.example.com/identity/clients/
response_types_supported: [code]
grant_types_supported: [authorization_code]
code_challenge_methods_supported: [S256]
token_endpoint_auth_methods_supported: [none]
client_id_metadata_document_supported: true
authorization_response_iss_parameter_supported: true
scopes_supported: [store:orders]
```

`registration_endpoint` appears only with `registration: open`, and `scopes_supported` only with
`scopes`. The same document is served at `/.well-known/openid-configuration`.

Each path in `resources` has a protected resource document, read at the well-known path followed
by the resource's own:

```http
GET /.well-known/oauth-protected-resource/.mcp HTTP/1.1
host: api.store.example.com
accept: application/yaml
```

```yaml
resource: https://api.store.example.com/.mcp
authorization_servers: [https://api.store.example.com]
bearer_methods_supported: [header]
scopes_supported: [store:orders]
```

`/.well-known/oauth-protected-resource` without a suffix describes the origin as a whole.

A host that is not a declared authority has no documents: these paths answer `404` there.

## Clients

Only public clients are supported: a client proves itself with PKCE, not with a secret. There are
two ways for a client to be known.

### Published metadata

A client whose `client_id` is an `https` URL publishes what it is at that URL. The gateway reads
the document from there, but only from origins you trust:

```yaml
# context.toa.yaml
configuration:
  identity.clients:
    trust:
      - https://claude.ai
```

With an empty list, which is the default, no such document is read and such a client is unknown.

### Registration

With `registration: open`, a client registers itself:

```http
POST /identity/clients/ HTTP/1.1
host: api.store.example.com
content-type: application/json

{"client_name": "Claude", "redirect_uris": ["https://claude.ai/api/mcp/auth_callback"]}
```

```http
201 Created
cache-control: no-store

{
  "client_id": "c8f3a1e4d8c9b2f6a0e5d7c3b1a9f8e2",
  "client_name": "Claude",
  "redirect_uris": ["https://claude.ai/api/mcp/auth_callback"],
  "grant_types": ["authorization_code"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none"
}
```

Accepted properties are `client_name`, `client_uri`, `logo_uri`, `redirect_uris` (1 to 8,
required), `scope`, `grant_types`, `response_types` and `token_endpoint_auth_method`.

- The `client_id` is derived from the metadata: the same registration sent twice is the same
  client. A registration cannot be changed; different metadata is a different client.
- A redirect URI must be `https`, or `http` on a loopback address. Anything else is `400` with
  `error: invalid_redirect_uri`.
- `token_endpoint_auth_method` other than `none` is `400` with `error: invalid_client_metadata`.
- A registration nothing has used is dropped after `identity.clients.ttl`.

`registration: closed` only stops advertising the endpoint. Decide between trusting named origins
and opening registration by who you expect: known products publish metadata; arbitrary tools
register.

## The consent page

The client opens the URL in `authorize` in the user's browser, with the request in the query:

```
https://store.example.com/oauth/authorize
  ?response_type=code
  &client_id=https%3A%2F%2Fclaude.ai%2Foauth%2Fclaude-code-client-metadata
  &redirect_uri=http%3A%2F%2Flocalhost%3A3118%2Fcallback
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256
  &state=af0ifjsldkj
  &resource=https%3A%2F%2Fapi.store.example.com%2F.mcp
  &scope=store:orders
```

The page is part of your web client. It does four things.

### 1. Sign the user in

By whatever means the application already offers. The page ends up holding the user's own `Token`
and knows their identity id.

### 2. Show who is asking

```http
GET /identity/clients/https%3A%2F%2Fclaude.ai%2Foauth%2Fclaude-code-client-metadata/ HTTP/1.1
host: api.store.example.com
authorization: Token eyJhbGciOiJkaXIi...
accept: application/yaml
```

```yaml
client_id: https://claude.ai/oauth/claude-code-client-metadata
client_name: Claude Code
client_uri: https://claude.ai
logo_uri: https://claude.ai/logo.png
redirect_uris: [http://localhost/callback, http://127.0.0.1/callback]
```

The `client_id` goes into the path URL-encoded. Any authenticated identity may read a client. An
unknown client is `422` with the code `UNKNOWN_CLIENT`; show an error and do not redirect.

Display `client_name`, the scopes asked for, and **the host of `redirect_uri`**. A redirect to
`localhost` could be any program on the user's machine, so the user should see where the code is
going.

### 3. On assent, ask for a code

```http
POST /identity/grants/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: api.store.example.com
authorization: Token eyJhbGciOiJkaXIi...
content-type: application/json

{
  "client": "https://claude.ai/oauth/claude-code-client-metadata",
  "redirect": "http://localhost:3118/callback",
  "challenge": "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM",
  "method": "S256",
  "scope": ["store:orders"],
  "resource": ["https://api.store.example.com/.mcp"]
}
```

```http
201 Created
cache-control: no-store

{"code": "SplxlOBeZQQYbYS6WxSbIA", "expires_in": 60}
```

The path holds the id of the consenting identity, which must be the one the page is signed in as.
The body passes on what arrived in the query:

| Property | From the query | |
| --- | --- | --- |
| `client` | `client_id` | Required. |
| `redirect` | `redirect_uri` | Required. |
| `challenge` | `code_challenge` | Required. |
| `method` | `code_challenge_method` | Required; must be `S256`. |
| `scope` | `scope`, split on spaces into a list | Optional. |
| `resource` | `resource`, as a list | Optional. |

A refusal is `400` with `error` and `error_description`:

| `error` | When |
| --- | --- |
| `invalid_client` | The client is unknown. |
| `invalid_request` | The redirect is not one this client may receive a code at, or the method is not `S256`. |

On such a refusal the page **must not redirect** to the `redirect_uri`: it has just been told the
address is not the client's. It shows the error itself.

Redirect URIs are compared exactly with those of the client, except on a loopback address, where
the port is ignored.

### 4. Send the user back

On assent, redirect to the client's `redirect_uri` with the code, the client's `state` untouched,
and the issuer:

```
http://localhost:3118/callback
  ?code=SplxlOBeZQQYbYS6WxSbIA
  &state=af0ifjsldkj
  &iss=https%3A%2F%2Fapi.store.example.com
```

`iss` is required: the metadata promises it, and a client rejects a response without it. Its value
is the `issuer` of `/.well-known/oauth-authorization-server`, which the page may fetch.

When the user declines, redirect all the same, saying so:

```
http://localhost:3118/callback?error=access_denied&state=af0ifjsldkj&iss=https%3A%2F%2Fapi.store.example.com
```

A single-page application does either with `location.assign`.

**Consent is asked every time.** Grants are recorded and can be listed, but the gateway does not
skip the page for a client the user allowed before, and neither should yours without thought.

## The token endpoint

The client redeems the code. This is the client's request, shown for completeness:

```http
POST /identity/grants/ HTTP/1.1
host: api.store.example.com
content-type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk&redirect_uri=http%3A%2F%2Flocalhost%3A3118%2Fcallback&client_id=https%3A%2F%2Fclaude.ai%2Foauth%2Fclaude-code-client-metadata
```

```http
200 OK
cache-control: no-store

{"access_token": "eyJhbGciOiJkaXIi...", "token_type": "Bearer", "expires_in": 2592000}
```

- `code_verifier` is required; the code was issued against its `S256` hash.
- A code is redeemed once. It is spent by the attempt whether or not the verifier matches, so a
  failed exchange means starting over from the consent page.
- A wrong verifier, a different `redirect_uri`, a used or expired code: all are `400` with
  `error: invalid_grant`, with no hint which.
- A scope the consenting identity does not hold is `400` with `error: invalid_scope`.

## Access tokens

An access token is a token of the identity that consented. It is presented as
`authorization: Bearer …` and passes the same [access directives](6.access.md) as that identity
would. Like a [custom token](3.tokens.md#custom-tokens) it is never refreshed.

### Scopes

Without `scope`, the token carries the roles its identity holds. With `scope`, it carries those
scopes **in place of** the roles. Each must be covered by a role of the identity (see
[Roles](7.roles.md#hierarchy)).

The `scopes` list of the annotation is what you advertise, not a filter: a scope outside the list
is still granted when the identity's roles cover it.

### Audience

When the client asked for a `resource` and the user allowed it, the token is bound to that entry
and admitted only there. A token bound to `https://api.store.example.com/.mcp` works at `/.mcp`
and is answered `401` at `/store/orders/…`, at `/.rpc`, and at `/identity/…`.

This does not hide data: an operation exposed as an MCP tool returns the same thing it returns
over HTTP. What it withholds is everything the entry does not publish: the rest of the HTTP tree
and identity management.

An entry is a host and a path. A token bound to another host is refused on this one.

## Grants

What a user allowed is recorded, one grant per identity per client. Build a "connected apps" page
from:

```http
GET /identity/grants/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: api.store.example.com
authorization: Token eyJhbGciOiJkaXIi...
accept: application/yaml
```

```yaml
- id: 3f2e1d0c9b8a4f7e6d5c4b3a2f1e0d9c
  client: c8f3a1e4d8c9b2f6a0e5d7c3b1a9f8e2
  scope: [store:orders]
  resource: [https://api.store.example.com/.mcp]
  CREATED: 1759696400000
```

and let the user take one back:

```http
DELETE /identity/grants/2428c31ecb6e4a51a24ef52f0c4181b9/3f2e1d0c9b8a4f7e6d5c4b3a2f1e0d9c/ HTTP/1.1
host: api.store.example.com
authorization: Token eyJhbGciOiJkaXIi...
```

```http
204 No Content
```

Revoking a grant disables its access token within `identity.tokens.cache.ttl`
(see [Tokens](3.tokens.md#listing-and-revoking)). Both routes are open to the identity alone.

## MCP

MCP itself, the tools it publishes and its annotation are covered in
[MCP Tools](../gateway/15.tools.md). What connects it to this article:

- Advertise the endpoint as a protected resource with `resources: ['/.mcp']`. An MCP client then
  finds the authorization server from the `401` it receives, and the token it obtains is bound to
  `/.mcp`.
- Where MCP is served on a host of its own, that host is a protected resource without being
  listed: its document is at `/.well-known/oauth-protected-resource` of that host, and names the
  authority's issuer as the authorization server.
- Each tool is authorized as the route it is, against the consenting identity (or the granted
  scopes). A route that is `auth:anonymous` is callable as a tool whatever the client presents.
- Tools that should be usable through MCP by a signed-in user need a directive that admits that
  user, typically [`auth:id`](6.access.md#id) with the identity passed as a tool argument. A client
  learns its identity from a tool that [echoes it](1.identities.md#the-account-of-the-caller).

## Limits

| Setting | Meaning | Default |
| --- | --- | --- |
| `identity.grants.lifetime` | Seconds a code may be redeemed within; at most 600. | `60` |
| `identity.grants.token` | Seconds an access token is valid; `0` is until revoked. | `2592000` |
| `identity.clients.trust` | Origins whose client metadata documents are read. | `[]` |
| `identity.clients.lifetime` | Seconds a fetched metadata document is kept before it is read again. | `3600` |
| `identity.clients.ttl` | Seconds an unused registration is kept. | `2592000` |
| `identity.clients.size` | Bytes of a metadata document that are read. | `16384` |
| `identity.clients.timeout` | Milliseconds a metadata document has to arrive. | `3000` |

The registration endpoint accepts 10 requests an hour per client address, and the token endpoint
60 a minute. Both count by the [client address](8.authorities.md#the-client-address), so they
limit nothing until `exposition.ip` is set.
