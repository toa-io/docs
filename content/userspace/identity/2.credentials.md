# Credentials

A request proves its identity with the `authorization` header. This article lists the schemes the
gateway understands, then covers the first of them, a username and a password, and the resource
that lists everything an identity can sign in with.

## Schemes

```http
authorization: <Scheme> <credentials>
```

| Scheme | Credentials | Covered in |
| --- | --- | --- |
| `Basic` | `base64(username:password)` | this article |
| `Token` | a token the gateway issued | [Tokens](3.tokens.md) |
| `Bearer` | an OpenID Connect `id_token` of a trusted provider, or a token the gateway issued | [Federation](4.federation.md), [OAuth](9.oauth.md) |
| `Code` | an authorization code of a trusted provider | [Federation](4.federation.md#authorization-code-flow) |
| `OTP` | `base64(username:code)` | [OTP and Passkeys](5.passwordless.md) |

The scheme name is not case-sensitive. Passkeys have no scheme: a passkey signs in through
[a request of its own](5.passwordless.md#signing-in-with-a-passkey).

`Token` is the primary scheme. A request authenticated by any other one is answered with a token in
the `authorization` response header, and the client is expected to continue with it. **A client
must not store a password**: it sends it once and keeps the token.

Every scheme fails the same way. Credentials that are malformed, unknown, wrong or expired leave
the request without an identity, and a route that needs one answers `401 Unauthorized`. A scheme
the gateway does not know, or a header without a space between scheme and credentials, is `401` as
well.

## A username and a password

`POST /identity/basic/` creates an identity with Basic credentials. It takes no credentials itself.

```http
POST /identity/basic/ HTTP/1.1
host: store.example.com
content-type: application/yaml
accept: application/yaml

username: bob
password: secret#1234
```

```http
201 Created

id: 2428c31ecb6e4a51a24ef52f0c4181b9
```

The reply carries no token, because the request carried no credentials. The client signs in next:

```http
GET /identity/ HTTP/1.1
host: store.example.com
authorization: Basic Ym9iOnNlY3JldCMxMjM0
```

A password may contain colons.

This route creates an identity and nothing else. When signing up must also create an account, use
[inception](1.identities.md#inception-an-identity-born-with-an-entity) on the application's own
route instead, and the Basic credentials of that request are stored the same way.

| Reply | When |
| --- | --- |
| `201 Created` | The identity is created. |
| `409 Conflict` | The username is taken in this authority. |
| `422`, code `INVALID_USERNAME` | The username breaks the constraints. |
| `422`, code `INVALID_PASSWORD` | The password breaks the constraints. |

A `422` body is the error:

```yaml
code: INVALID_PASSWORD
message: Password is not meeting the requirements
```

### Is a username free

```http
GET /identity/basic/usernames/Ym9i/ HTTP/1.1
host: store.example.com
```

The last segment is the username, Base64 URL encoded. The reply is `204 No Content` when the
username is taken and `404 Not Found` when it is free. No credentials are needed.

## Changing the username or password

```http
PATCH /identity/basic/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Basic Ym9iOnNlY3JldCMxMjM0
content-type: application/yaml

password: new-secret
```

```http
200 OK
```

The body holds `username`, `password` or both.

- **The request must be authenticated with `Basic`**, that is, with the current password. A token
  is answered `403` with the text `Basic authentication scheme is required to access this
  resource`.
- The identity must be the one in the path, or hold the role `system:identity:basic`. Anyone else
  is answered `403`.
- A value that breaks the constraints is answered `422`.
- Changing the credentials revokes the tokens of the identity. See
  [Tokens](3.tokens.md#revocation) for when that takes effect.

## Adding a password to an identity

An identity that signed in some other way, or a
[transient](1.identities.md#transient-identities) one, adds Basic credentials with `POST` to its
own path:

```http
POST /identity/basic/332017649c814649b25ee466c1fe4534/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
content-type: application/yaml

username: alice
password: secret#1234
```

```http
201 Created
```

Any credentials of that identity will do. An identity has at most one username and password per
authority: a second `POST` is answered `422` with the code `EXISTS`.

## Removing the password

```http
DELETE /identity/basic/332017649c814649b25ee466c1fe4534/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
```

```http
204 No Content
```

New Basic credentials can be added afterwards.

## Constraints

Usernames and passwords are checked against lists of regular expressions. A value must match every
expression in its list.

```yaml
# context.toa.yaml
configuration:
  identity.basic:
    username:
      - ^\S{3,64}$
    password:
      - ^.{12,64}$
      - \d
```

The defaults are `^.{1,128}$` for a username and `^.{8,32}$` for a password.

## Hashing

Passwords are stored hashed with bcrypt. Two settings control it:

```yaml
# context.toa.yaml
configuration:
  identity.basic:
    rounds: 10
    pepper: $IDENTITY_BASIC_PEPPER
```

| Key | Meaning | Default |
| --- | --- | --- |
| `rounds` | Salt rounds, at least 1. | `10` |
| `pepper` | A secret mixed into every hash. | none |

`pepper` is a secret: write it as a `$NAME` reference and deploy the value separately, as
[Configuration](../services/2.configuration.md#secrets) describes. Set it before the first user
signs up: stored hashes are made with it.

## The principal

A new deployment has no identities, so nobody can grant the first role. `principal` names the
credentials whose identity is given the `system` role the moment it is created:

```yaml
# context.toa.yaml
configuration:
  identity.basic:
    principal:
      authority: store
      username: root
```

Create the credentials in that authority with `POST /identity/basic/` or with `POST /identity/`,
and that identity can manage everything. The same username in another authority is an ordinary
one. The principal's username cannot be changed afterwards: the attempt is answered `422` with the
code `PRINCIPAL_LOCKED`. [Roles](7.roles.md#the-first-role) continues from here.

## Listing credentials

An account page needs to show what the user can sign in with. One request answers it:

```http
GET /identity/credentials/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
accept: application/yaml
```

```yaml
basic:
  username: bob
federation:
  - id: 09200d0bcc2448c5863e3f50ae18af84
    iss: https://accounts.google.com
    CREATED: 1754899200000
passkeys:
  - id: 54ed430804324e81b39756ea4708b546
    aid: adce0002-35bc-c60a-648b-0b25f1f05503
    synced: true
    label: Personal iPhone
    CREATED: 1754899200000
```

Only the identity itself may read it. `basic` is `null` when there is no password; `federation`
and `passkeys` are always arrays. Nothing secret is returned.

- `federation[].iss` is the provider. Map issuers to names and logos in the client.
- `passkeys[].aid` is the authenticator's AAGUID, which a client can look up in a catalog of
  authenticators to show a name and an icon. `synced` says the passkey is backed up and likely
  available on more than one device.
- Each `id` is what the `DELETE` routes of [federation](4.federation.md#federated-credentials) and
  [passkeys](5.passwordless.md#managing-passkeys) take.

Tokens and one-time passwords are not listed: they are not stored credentials.

## Failed attempts

Rejected credentials can be counted per client address, whatever the scheme, so that passwords are
not guessed at leisure. It is off until the Context asks for it:

```yaml
# context.toa.yaml
exposition:
  ip: cf-connecting-ip
  bouncer:
    attempts: 20
    interval: 60
```

An address may fail `attempts` times at once and earns them back at `attempts` per `interval`
seconds. A request carrying credentials from an address with nothing left is answered:

```http
429 Too Many Requests
retry-after: 30
```

- `attempts` defaults to `20` and `interval` to `60`; `bouncer: {}` takes both.
- `bouncer` requires `ip`, which names the header the client address is read from. See
  [Authorities and the Edge](8.authorities.md#the-client-address).
- A request without credentials is never counted, and neither is one whose address is unknown.
