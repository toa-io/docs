# Roles and Bans

A role is a value assigned to an identity. Routes require roles with
[`auth:role`](6.access.md#role). Role names form a hierarchy, roles are granted and revoked
through the gateway, and the first one is declared in the Context.

## Hierarchy

A role is a string of alphanumeric segments separated by colons, at most 32 characters per segment:

```
store
store:orders
store:orders:refunds
```

The colons form a hierarchy. `store:orders:refunds` lies within `store:orders`, which lies within
`store`. What a route requires is called a *scope* and has the same form.

**A role covers its own scope and every scope within it.** An identity must hold the required role
or a more general one:

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /refunds:
    auth:role: store:orders:refunds
    GET: enumerate
```

| The identity holds | `store:orders:refunds` is |
| --- | --- |
| `store:orders:refunds` | covered |
| `store:orders` | covered |
| `store` | covered |
| `store:orders:refunds:eu` | not covered |
| `store:catalog` | not covered |

Design role names from general to specific, so that one grant near the root gives a whole area.
Nothing has to be registered: a role exists by being granted, and a scope by being required.

The root scope `system` is reserved for the gateway's own resources. The scopes it uses are listed
[below](#system-scopes).

### Scopes with route variables

A scope can include a route variable, which gives roles a per-resource meaning:

```yaml
# components/store.catalog/manifest.toa.yaml
exposition:
  /:vendor:
    auth:role: store:vendors:{vendor}:manager
    PUT: transit
```

Grant `store:vendors:acme:manager` to the manager of one vendor, `store:vendors:acme` to its
owner, and `store:vendors` to staff who manage all of them. Variable values used this way must be
valid role segments.

## Reading roles

An identity's roles come with the identity:

```http
GET /identity/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
accept: application/yaml
```

```yaml
id: 2428c31ecb6e4a51a24ef52f0c4181b9
roles:
  - store:orders
```

A client uses them to decide what to show. The roles of any identity are read at:

```http
GET /identity/roles/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
accept: application/yaml
```

```yaml
- store:orders
```

This is open to the identity itself and to holders of `system:identity:roles`.

## Granting

```http
POST /identity/roles/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token <a token of an identity with system:identity:roles>
content-type: application/yaml
accept: application/yaml

role: store:orders
```

```http
201 Created

id: 9c4702490ff84f2a9e1b1da2ab64bdd4
grantor: 72cf9b0ab0ac4ab2b8036e4e940ddcae
```

The path names the identity that receives the role. `grantor` is the identity that granted it,
recorded with the role.

An identity with `system:identity:roles` may grant any role to anyone.

| Reply | When |
| --- | --- |
| `201 Created` | The role is granted. |
| `400 Bad Request` | The path is not an identity id, or the role is not a valid role name. |
| `401` / `403` | The caller has no identity, or neither of the roles that allow granting. |
| `422`, code `INACCESSIBLE_SCOPE` | The caller may delegate, but not this role. |

### Delegation

Granting everything is too much for most people who need to grant something. An identity with the
role `system:identity:roles:delegation` may grant **roles that its own roles cover**, and no
others.

A moderator holding `store:moderation` and `system:identity:roles:delegation` can give an
assistant `store:moderation` or `store:moderation:photos`. Asked to grant `store:finance`, the
gateway answers `422` with `INACCESSIBLE_SCOPE`.

The right to delegate is not itself delegable: roles within `system:identity:roles` cannot be
granted this way, whatever the delegating identity holds.

## Revoking

```http
DELETE /identity/roles/2428c31ecb6e4a51a24ef52f0c4181b9/store:orders/ HTTP/1.1
host: store.example.com
authorization: Token <a token of an identity with system:identity:roles>
```

```http
204 No Content
```

The last segment is the role. Revoking requires `system:identity:roles`; delegation does not
include taking back.

## When a change takes effect

A token carries the roles its identity had when it was issued.

- A client using a `Token` sees a grant or a revocation when its token is next
  [refreshed](3.tokens.md#refreshing): within `identity.tokens.refresh`, 10 minutes by default. It
  costs the client nothing; the new token arrives on its next request after that.
- A request authenticated with any other scheme (a password, a provider's token) reads the current
  roles.
- [Custom tokens](3.tokens.md#custom-tokens) are never refreshed. **Revoking any role of an identity
  revokes all its custom tokens**; issue them again and they carry the roles that are left. A
  grant does not reach an existing custom token either: issue a new one.

So after granting a role to a signed-in user, expect up to `refresh` seconds before a route
guarded by it opens for them. If a client must see it at once, have it sign in again.

## The first role

Granting requires a role, so a new deployment needs one identity that has a role by declaration.
That is the *principal*, named in the configuration of the credentials it signs in with:

```yaml
# context.toa.yaml
configuration:
  identity.basic:
    principal:
      authority: store
      username: root
```

```http
POST /identity/ HTTP/1.1
host: store.example.com
authorization: Basic cm9vdDpzZWNyZXQjMTIzNA==
```

```http
201 Created
authorization: Token eyJhbGciOiJkaXIi...
```

The identity created with those credentials in that authority is granted `system`, and the token
in this reply already holds it. `system` covers every `system:…` scope, so the principal can grant
roles, ban, and issue tokens for anyone. From there, grant narrower roles to the people who need
them and keep the principal's credentials out of daily use.

A provider's subject can be the principal instead of a username; see
[Federation](4.federation.md#the-principal). When the principal is created with
`POST /identity/basic/`, which returns no token, the role is granted a moment later, before the
principal has had time to sign in.

`system` does not open the application's own routes: `store:orders` is not within `system`. Grant
the principal what it needs, or declare an administrative role on the tree.

## System scopes

The gateway's resources require these scopes. Each is also open to the identity it concerns where
the table says so.

| Scope | Allows | Also open to |
| --- | --- | --- |
| `system:identity:roles` | Granting any role, revoking, reading anyone's roles. | The identity itself, for reading. |
| `system:identity:roles:delegation` | Granting roles the holder's own roles cover. | |
| `system:identity:basic` | Changing or removing anyone's Basic credentials. | The identity itself. |
| `system:identity:tokens` | Issuing a [custom token](3.tokens.md#acting-for-another-identity) for any identity. | The identity itself. |
| `system:identity:keys` | Listing and revoking anyone's custom token keys. | The identity itself. |
| `system:identity:otp` | Issuing a [one-time password](5.passwordless.md#a-code-for-yourself) for any identity. | The identity itself. |
| `system:identity:bans` | Banning and unbanning. | |

Routes that require a `system` scope are marked `system` in resource descriptions, so that tools
listing an application's resources can leave them out.

## Bans

A banned identity cannot authenticate with any of its credentials.

```http
PUT /identity/bans/e8e4f9c2a68d419b861403d71fabc915/ HTTP/1.1
host: store.example.com
authorization: Token <a token of an identity with system:identity:bans>
content-type: application/yaml

banned: true
comment: Chargeback fraud
```

```http
204 No Content
```

`comment` is optional. The identity that issued the ban is recorded with it.

What follows:

- Requests with the identity's password, provider token, OTP or passkey are answered `401` at
  once.
- A `Token` it already holds keeps working until its next refresh, at most
  `identity.tokens.refresh` seconds, and is then answered `401`.
- Its [custom tokens](3.tokens.md#listing-and-revoking) are revoked, and stop working within
  `identity.tokens.cache.ttl`.
- Credentials cannot be created for a banned id by inception.

Lifting the ban is the same request with `banned: false`:

```http
PUT /identity/bans/e8e4f9c2a68d419b861403d71fabc915/ HTTP/1.1
host: store.example.com
authorization: Token <a token of an identity with system:identity:bans>
content-type: application/yaml

banned: false
```

The identity signs in again and receives a new token. Its custom tokens are not restored; it
issues new ones.

A ban concerns the identity, not the application's entity that shares its id. If the shop must also
stop a banned customer's pending orders, that is an operation of its own, called by whoever issues
the ban.
