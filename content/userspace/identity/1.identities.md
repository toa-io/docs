# Identities

An identity is the identifier of whoever sends a request, and nothing more; the
[model](../../model/edge/2.identity.md) explains why. This article shows how an identity comes to
exist, how a client learns its own, and how it is tied to an entity of the application.

The gateway brings everything needed: the components that store credentials, issue tokens and hold
roles run inside it under the `identity` namespace, and their resources are served under
`/identity/`. You do not write them, you configure them.

## The one thing to configure

Tokens are encrypted, so the gateway needs a key before it can authenticate anyone:

```yaml
# context.toa.yaml
configuration:
  identity.tokens:
    keys:
      - id: 2026q4
        key: $IDENTITY_TOKENS_KEY
```

Generate the value with `toa key` and deploy it as a [secret](../running/9.secrets.md).
[Tokens](3.tokens.md#keys) covers the key list in full. Every other setting of the identity
components has a default.

## Asking who you are

`GET /identity/` answers the identity the request's credentials resolve to. It exists in every
application, with nothing declared.

```http
GET /identity/ HTTP/1.1
host: store.example.com
authorization: Basic ZGV2ZWxvcGVyOnNlY3JldA==
accept: application/yaml
```

```http
200 OK
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...
cache-control: no-store

id: efe3a65ebbee47ed95a73edd911ea328
roles:
  - developer
```

Two things come back: the identity, and a token in the `authorization` response header. The client
keeps the token and sends it with every later request instead of the password:

```http
GET /identity/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...
```

This is what signing in amounts to. Authentication does not depend on the URL: credentials may be
sent with any request, and whichever request carries them is answered with a token. `GET
/identity/` is simply the usual first request, because the client needs the `id`.

There are no sessions and no cookies. Signing out is the client deleting its token.

## Transient identities

A request to `GET /identity/` without credentials creates an identity on the spot:

```http
GET /identity/ HTTP/1.1
host: store.example.com
accept: application/yaml
```

```http
201 Created
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...

id: 332017649c814649b25ee466c1fe4534
roles: []
```

Such an identity is *transient*: it exists only as the token the reply carries. Nothing is stored,
and when the client loses the token the identity is gone. Use it for a visitor who has not signed up
yet: a guest's cart can be kept under `/store/carts/:customer/` and reached with the guest's token.

A transient identity becomes a lasting one when credentials are added to it, for example
[a password](2.credentials.md#adding-a-password-to-an-identity) or
[a passkey](5.passwordless.md#passkeys). The `id` does not change, so whatever the guest owned stays
theirs.

## Inception: an identity born with an entity

An application has its own notion of a user. In the shop it is `store.accounts`. The simplest link
between an account and an identity is that they share an `id`, and `auth:incept` creates them that
way.

```yaml
# components/store.accounts/manifest.toa.yaml
exposition:
  /:
    POST:
      auth:incept: id
      io:output: [id]
      endpoint: transit
```

The value names the property of the operation's output that holds the new entity's id. The request
carries credentials nobody owns yet:

```http
POST /store/accounts/ HTTP/1.1
host: store.example.com
authorization: Basic Ym9iOnBhc3MxMjM0
content-type: application/yaml
accept: application/yaml

name: Bob
```

```http
201 Created
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...

id: 2428c31ecb6e4a51a24ef52f0c4181b9
```

The account is created, an identity with the same `id` is created, and the Basic credentials of the
request now belong to it. The token in the reply is that identity's.

What to know about it:

- **The route is open to requests that carry no identity yet.** `auth:incept` grants access when the
  request has no credentials, or credentials that are well-formed and owned by nobody. It needs no
  `auth:anonymous` beside it.
- **Without credentials, the identity is transient.** The account is created and the reply carries a
  token for an identity with the account's `id`. The client adds credentials later. This is how a
  sign-up form that asks only for a name works.
- Credentials may be `Basic` or `Bearer` (a token of an external provider, see
  [Federation](4.federation.md)). No other scheme can incept: such a request is answered `401`.
- If the output has no such property, for instance because the operation returned an error, nothing
  is incepted and the operation's reply is sent as it is.

### What the client sees when it fails

| Request | Reply |
| --- | --- |
| Credentials that already belong to an identity | `403 Forbidden` |
| A known username with a wrong password, or a token that cannot be read | `401 Unauthorized` |
| Basic credentials that are not `base64(username:password)` | `422`, code `INVALID_CREDENTIALS` |
| A username or password that breaks the [constraints](2.credentials.md#constraints) | `422`, code `INVALID_USERNAME` or `INVALID_PASSWORD` |
| An identity that is [banned](7.roles.md#bans) | `401 Unauthorized` |

The first two are refused before the operation is called. The others are found after it ran, so the
entity exists by then: the operation is not undone.

### An identity without an entity

`auth:incept` with a `null` value creates an identity that no entity is tied to. The gateway
declares one such route itself:

```http
POST /identity/ HTTP/1.1
host: store.example.com
authorization: Basic Ym9iOnBhc3MxMjM0
accept: application/yaml
```

```http
201 Created
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...

id: 7f1c5d0be0a54b2c9d2f4ec1a6b8e9aa
roles: []
```

## Assertion: sign in or sign up in one request

`auth:assert: true` makes a route create the identity when the credentials are new, and use the
existing one when they are not.

```yaml
# components/store.accounts/manifest.toa.yaml
exposition:
  /echo:
    GET:
      auth:assert: true
      auth:anyone: true
      io:output: [id, balance]
      endpoint: echo
```

```http
GET /store/accounts/echo/ HTTP/1.1
host: store.example.com
authorization: Basic bmV3OnBhJCR3MHJkIQ==
```

A request with known credentials is answered `200`. A request with new ones is answered `201`, with
the identity created under a fresh id, and a token in both cases.

- `auth:assert` does not grant access. Something else on the route must: here `auth:anyone`.
- A request without credentials is answered `401`.
- The scheme must be one that supports inception: `Basic` or `Bearer`.
- A wrong password for a known username is `401`, as everywhere.

## The account of the caller

With shared ids, "the caller's account" is the account whose id is the identity. There are two ways
to reach it.

**By route.** Put the id in the path and guard it with `auth:id`:

```yaml
# components/store.accounts/manifest.toa.yaml
exposition:
  /:id:
    auth:id: id
    GET: observe
```

`GET /store/accounts/2428c31ecb6e4a51a24ef52f0c4181b9/` is open to that identity alone. The client
learned the id from `GET /identity/` or from the reply of the inception. See
[Access](6.access.md#id).

**By an operation that is told who calls.** `auth:delegate` puts the identity into the operation's
input:

```yaml
# components/store.accounts/manifest.toa.yaml
operations:
  echo:
    type: computation
    input:
      type: object
      properties:
        identity:
          type: object
          properties:
            id: { type: string }
            roles: { type: array, items: { type: string } }
          required: [id, roles]

exposition:
  /echo:
    GET:
      auth:assert: true
      auth:delegate: identity
      io:output: [id, balance, roles]
      cache:control: no-store
      endpoint: echo
```

```javascript
// components/store.accounts/operations/echo.js
export async function computation ({ identity }, context) {
  const account = await context.local.observe({ query: { id: identity.id } })

  if (account instanceof Error)
    return account

  return { ...account, roles: identity.roles }
}
```

One request answers "who am I" with the application's own data. The reply differs per caller at
the same URL, so tell caches not to store it. [Access](6.access.md#delegate) describes
`auth:delegate` and when not to use it.

## Identities and authorities

Credentials belong to an [authority](8.authorities.md), the name of the domain a request arrived
at. The same username under two authorities is two identities, and a token issued under one is
refused under the other. An application served on one domain can ignore this.

## Where an identity ends

An identity exists as long as it has credentials. The components that store credentials do not
coordinate: removing the last password, federated credential or passkey is allowed, and leaves an
identity nobody can sign in to. If your application needs accounts to stay recoverable, the client
must refuse to remove the last credential;
[`GET /identity/credentials/:identity/`](2.credentials.md#listing-credentials) tells it what is
left.
