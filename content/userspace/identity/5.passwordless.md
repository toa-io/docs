# OTP and Passkeys

Two ways to sign in without a password: a one-time code delivered to the user, and a passkey held
by the user's device. Both end like every other scheme, with a token in the response.

## One-time passwords

A one-time password (OTP) is a 6-digit code tied to a *username*, valid once and for a short time.
The username is any string the application chooses: an email address, a phone number, an id. The
gateway issues and verifies codes; **delivering the code to the user is the application's job.**

### Issuing a code

Codes are issued by calling the `identity.otp.issue` operation from an operation of your own. Add
an operation to `store.accounts` that issues a code for an email address and sends it:

```yaml
# components/store.accounts/manifest.toa.yaml
operations:
  otp:
    type: effect
    input:
      type: object
      properties:
        authority: { type: string }
        email: { type: string, format: email }
      required: [authority, email]

exposition:
  /otp:
    POST:
      anonymous: true
      map:authority: authority
      io:input: [email]
      io:output: false
      endpoint: otp
```

```javascript
// components/store.accounts/operations/otp.js
export async function effect ({ authority, email }, context) {
  const otp = await context.remote.identity.otp.issue({
    input: { authority, username: email }
  })

  if (otp instanceof Error)
    return otp

  return await context.remote.store.notifications.send({
    input: { to: email, subject: 'Your code', text: `Your code is ${otp.code}` }
  })
}
```

`store.notifications` is the shop's component that sends email. `map:authority` supplies the
[authority](8.authorities.md) the request arrived at; a code is valid only there.

The input of `identity.otp.issue`:

| Property | Meaning |
| --- | --- |
| `authority` | Required. The authority the code is valid in. |
| `username` | Required. 1 to 256 characters. |
| `identity` | An identity id to bind the username to. See [below](#binding-a-username-to-an-identity). |
| `lifetime` | Seconds this code is valid, 1 to 3600. Defaults to the configured `lifetime`. |

The output is `{ code }`, a string of six digits.

The route is anonymous and sends mail, so limit how often it can be called;
[Input and Output](../gateway/6.io.md#throttling) describes throttling.

### Signing in with a code

The client sends the username and the code the user typed as `base64(username:code)` under the
`OTP` scheme:

```http
GET /identity/ HTTP/1.1
host: store.example.com
authorization: OTP Ym9iQGV4YW1wbGUuY29tOjEyMzQ1Ng==
accept: application/yaml
```

```http
200 OK
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...

id: 6f3d2c1b0a9e4f8d7c6b5a4e3d2c1b0a
```

- A code works **once**. The second request with it is `401`.
- A username resolves to the same identity every time. The first successful sign-in of a username
  nobody has seen creates the identity.
- An expired or wrong code is `401`.

### Binding a username to an identity

Passing `identity` to `issue` makes the username a way into that identity. The first use is
typically "confirm your email": a signed-in user asks for a code to an address, and once a code
has been issued this way, signing in with that address resolves to their identity.

```yaml
# components/store.accounts/manifest.toa.yaml
exposition:
  /:id:
    /otp:
      POST:
        auth:id: id
        map:authority: authority
        map:segments:
          identity: id
        io:input: [email]
        io:output: false
        endpoint: otp
```

```javascript
// components/store.accounts/operations/otp.js
export async function effect ({ authority, email, identity }, context) {
  const otp = await context.remote.identity.otp.issue({
    input: { authority, username: email, identity }
  })

  // …deliver otp.code as before
}
```

Declare `identity` as an optional string in the operation's input, and one operation serves both
routes.

### A code for yourself

An identity can issue a code for itself over HTTP, with no application code:

```http
POST /identity/otp/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
accept: application/yaml
```

```http
201 Created

code: '493817'
```

The username of such a code is the identity's id, so it is redeemed as
`OTP base64(<identity id>:<code>)` and resolves to that identity. It moves a signed-in session to
another device: one device shows the code, the other signs in with it.

The request must come from the identity itself or from one with the role `system:identity:otp`,
which may issue a code for anyone.

### Limits

```yaml
# context.toa.yaml
configuration:
  identity.otp:
    lifetime: 300 # seconds a code is valid; 1 to 3600
    attempts: 5   # failed attempts allowed per username within `lifetime`
```

The values shown are the defaults. After `attempts` wrong codes for one username, every code for
it is refused, the right one included, until `lifetime` has passed since the first failure. A
successful sign-in resets the count.

All refusals are `401` for the client. The log names the reason: `EXPIRED` for a code that is
wrong, used or expired, `TOO_MANY_ATTEMPTS`, `INVALID_CREDENTIALS` for credentials that are not
`base64(username:code)`.

## Passkeys

A passkey is a WebAuthn credential: a key pair whose private half never leaves the user's
authenticator. The browser API does the cryptography; the gateway issues challenges, verifies the
answers and stores public keys.

Each ceremony is two requests: ask for a *challenge*, then send what the authenticator produced.
The client sits between them, calling `navigator.credentials.create()` or
`navigator.credentials.get()`.

**The relying party is the client.** A passkey belongs to the web origin it was registered on, and
is usable only from that origin. The gateway reads the origin from the request's `origin` header,
which a browser sends by itself.

### Adding a passkey to an identity

Ask for a creation challenge for the identity. **Send no credentials with challenge requests.**

```http
POST /identity/passkeys/challenges/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
content-type: application/yaml
accept: application/yaml

type: creation
```

```http
201 Created

identity: 2428c31ecb6e4a51a24ef52f0c4181b9
challenge: 5Yb0mHcFqv3s0xN6a8sU0c1B6Jm9Zl2kq7R4tW8yE1o
timeout: 60000
pubKeyCredParams:
  - type: public-key
    alg: -7
  - type: public-key
    alg: -257
authenticatorSelection:
  residentKey: required
  requireResidentKey: true
excludeCredentials: []
```

These are the options for `navigator.credentials.create()`, except `rp` and `user`, which the
client adds: its own name and id as the relying party, and the user's name with `identity` as the
user id. `excludeCredentials` lists the passkeys the identity already has.

Send the result, serialized as JSON, with a label for the user to recognize the passkey by:

```http
POST /identity/passkeys/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
origin: https://store.example.com
authorization: Token eyJhbGciOiJkaXIi...
content-type: application/json
accept: application/yaml

{
  "label": "Personal iPhone",
  "id": "Xk3…",
  "type": "public-key",
  "response": {
    "attestationObject": "o2NmbXRk…",
    "clientDataJSON": "eyJ0eXBlIjoi…",
    "authenticatorData": "SZYN5YgO…",
    "publicKey": "MFkwEwYH…",
    "publicKeyAlgorithm": -7,
    "transports": ["internal", "hybrid"]
  },
  "authenticatorAttachment": "platform",
  "clientExtensionResults": {}
}
```

```http
201 Created

id: 54ed430804324e81b39756ea4708b546
aid: adce0002-35bc-c60a-648b-0b25f1f05503
synced: true
label: Personal iPhone
CREATED: 1754899200000
```

The body is what `PublicKeyCredential.toJSON()` returns, plus `label` (required, 1 to 64
characters). This request is authenticated: only the identity itself may add a passkey.

### Signing up with a passkey

A new user has no identity to put in the path. Ask for a creation challenge without one:

```http
POST /identity/passkeys/challenges/ HTTP/1.1
host: store.example.com
content-type: application/yaml
accept: application/yaml

type: creation
```

```http
201 Created
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...

identity: 8a7b6c5d4e3f4a2b9c1d0e9f8a7b6c5d
challenge: 3nD0y…
timeout: 60000
…
```

The reply creates a [transient identity](1.identities.md#transient-identities): `identity` is its
id and the `authorization` header carries its token. The client runs
`navigator.credentials.create()` and sends the result to
`POST /identity/passkeys/8a7b6c5d4e3f4a2b9c1d0e9f8a7b6c5d/` with that token, as above. Once the
passkey is stored, the identity is a lasting one.

To create an account together with it, the application declares a route of its own that calls
`identity.passkeys.create` and carries
[`auth:id`](6.access.md#id), or creates the account first by
[inception without credentials](1.identities.md#inception-an-identity-born-with-an-entity) and
adds the passkey to the identity that reply returns.

### Signing in with a passkey

Ask for a request challenge:

```http
POST /identity/passkeys/challenges/ HTTP/1.1
host: store.example.com
content-type: application/yaml
accept: application/yaml

type: request
```

```http
201 Created

challenge: Qm9v…
timeout: 60000
allowCredentials: []
```

Pass it to `navigator.credentials.get()`; the user picks a passkey. Send the result, again without
credentials:

```http
POST /identity/passkeys/ HTTP/1.1
host: store.example.com
origin: https://store.example.com
content-type: application/json
accept: application/yaml

{
  "id": "Xk3…",
  "type": "public-key",
  "response": {
    "authenticatorData": "SZYN5YgO…",
    "clientDataJSON": "eyJ0eXBlIjoi…",
    "signature": "MEUCIQ…",
    "userHandle": "MjQyOGMz…"
  },
  "clientExtensionResults": {}
}
```

```http
201 Created
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...

identity: 2428c31ecb6e4a51a24ef52f0c4181b9
```

The token in the header is the identity's; continue with it.

To narrow the choice to the passkeys of a known identity, ask for the challenge at
`POST /identity/passkeys/challenges/:identity/` with `type: request`; `allowCredentials` then
lists them.

### Managing passkeys

```http
GET /identity/passkeys/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
accept: application/yaml
```

```yaml
- id: 54ed430804324e81b39756ea4708b546
  aid: adce0002-35bc-c60a-648b-0b25f1f05503
  synced: true
  label: Personal iPhone
  CREATED: 1754899200000
```

```http
DELETE /identity/passkeys/2428c31ecb6e4a51a24ef52f0c4181b9/54ed430804324e81b39756ea4708b546/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
```

```http
204 No Content
```

Both require credentials of the identity. `aid` and `synced` are explained under
[listing credentials](2.credentials.md#listing-credentials).

### Settings

```yaml
# context.toa.yaml
configuration:
  identity.passkeys:
    algorithms: [-7, -257]
    timeout: 60000
    residence: required
    verification: preferred
```

| Key | Meaning | Default |
| --- | --- | --- |
| `algorithms` | Accepted COSE algorithm ids, offered as `pubKeyCredParams`. | `[-7, -257]` |
| `timeout` | Milliseconds the user has to complete a ceremony. A challenge is forgotten shortly after. | `60000` |
| `residence` | `residentKey` of the authenticator selection: `required`, `preferred` or `discouraged`. | `required` |
| `verification` | `userVerification`: `required`, `preferred` or `discouraged`. With `required`, an answer without user verification is refused. | none |

### What the client sees

A challenge can be answered once and only within its time. Refusals of the second request come as
`422` with a code:

| Code | Reason |
| --- | --- |
| `FAILED` | The answer did not verify: an unknown or expired challenge, another origin, a bad signature. |
| `INVALID` | The answer verified as not valid. |
| `MISS` | Signing in with a passkey nobody registered in this authority. |

A challenge request that carries credentials is answered `403`, and so is a sign-in request that
does.
