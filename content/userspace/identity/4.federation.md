# Federation

Federation lets a user sign in with an account they already have at an OpenID Connect provider:
Google, Apple, a corporate directory, a CI system. The gateway verifies the provider's token and
resolves it to an identity of the application. You list the providers you trust; there is nothing
to implement.

## Trusting a provider

No provider is trusted until the Context names it:

```yaml
# context.toa.yaml
configuration:
  identity.federation:
    trust:
      - iss: https://accounts.google.com
        aud: 1045282659797-example.apps.googleusercontent.com
```

`iss` is the issuer, exactly as it appears in the provider's tokens. `aud` is the audience the
token must have been issued for: the client id the provider gave your application. A token of
another issuer, or of this issuer for another audience, is refused.

The provider's metadata and signing keys are read from
`<iss>/.well-known/openid-configuration`, so the gateway must be able to reach it.

## Signing in with an `id_token`

The client obtains an `id_token` from the provider, in whatever way the provider's SDK offers, and
sends it as `Bearer`:

```http
GET /identity/ HTTP/1.1
host: store.example.com
authorization: Bearer eyJhbGciOiJSUzI1NiIsImtpZCI6...
accept: application/yaml
```

```http
200 OK
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...

id: 9c1f0a6d5b7e4f3a8d2c1b0a9e8f7d6c
roles: []
```

The client keeps the `Token` and drops the `id_token`, as with any other scheme (see
[Tokens](3.tokens.md#receiving-a-token)).

A person is recognized by the pair of `iss` and `sub` claims. The same pair always resolves to the
same identity, whatever else changes in the token.

### New users

By default, the first valid token of a subject nobody has seen **creates an identity**. No sign-up
step is needed: `GET /identity/` with a new Google account answers `200` and a fresh `id`.

That identity has no account in the application yet. Two ways to deal with it:

- Let the client create the account afterwards on a route guarded by
  [`auth:id`](6.access.md#id), using the `id` it was given.
- Turn implicit creation off, and create the identity together with the account.

```yaml
# context.toa.yaml
configuration:
  identity.federation:
    trust:
      - iss: https://accounts.google.com
        aud: 1045282659797-example.apps.googleusercontent.com
    assert: false
```

With `assert: false`, a valid token of an unknown subject authenticates nobody: it is `401`
wherever an identity is required. The identity is created by
[inception](1.identities.md#inception-an-identity-born-with-an-entity):

```yaml
# components/store.accounts/manifest.toa.yaml
exposition:
  /:
    POST:
      auth:incept: id
      io:output: [id]
      endpoint: transit
```

```http
POST /store/accounts/ HTTP/1.1
host: store.example.com
authorization: Bearer eyJhbGciOiJSUzI1NiIsImtpZCI6...
content-type: application/yaml

name: Bill Smith
```

```http
201 Created
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...

id: 4344518184ad44228baffce7a44fd0b1
```

The account and the identity share the id, and the provider's subject is bound to it. A second
`POST` with the same token is answered `403`: those credentials have an identity already.

[`auth:assert`](1.identities.md#assertion-sign-in-or-sign-up-in-one-request) works with `Bearer`
too, when one route should serve both new and returning users.

### Several audiences

`aud` may be a list, when several clients of yours (a web app, an iOS app) have client ids of their
own, or when a provider issues tokens per caller:

```yaml
trust:
  - iss: https://token.actions.githubusercontent.com
    aud:
      - https://github.com/acme
      - https://github.com/acme-labs
```

A token is accepted when its audience is one of them.

## Authorization code flow

Some providers hand the browser a *code* instead of a token, to be exchanged by a server that
holds a client secret. The gateway does the exchange.

Enable it per provider by adding the secret:

```yaml
# context.toa.yaml
configuration:
  identity.federation:
    trust:
      - iss: https://accounts.google.com
        aud: 1045282659797-example.apps.googleusercontent.com
        secret: $GOOGLE_CLIENT_SECRET
```

or, for a provider that wants a signed client assertion instead of a secret (Apple does), the
signing key:

```yaml
      - iss: https://appleid.apple.com
        aud: com.example.store.web
        signature:
          iss: 3L7XKJ5X9Q        # the issuer of the assertion: your team id
          kid: 8YH4ZB2K7M        # the id of the key
          key: $APPLE_PRIVATE_KEY # PKCS8 PEM, the contents of the .p8 file
```

`secret` and `signature.key` are secrets: `$NAME` references, deployed separately. Where `aud` is a
list, the first value is used as the client id of the exchange.

The client redirects the user to the provider, receives the code on its redirect URI, and sends:

```http
GET /identity/ HTTP/1.1
host: store.example.com
authorization: Code eyJjb2RlIjoiNC8wQWJDLi4uIiwiaXNzIjoiaHR0cHM6Ly9hY2NvdW50cy5nb29nbGUuY29tIiwiZm9yIjoiaHR0cHM6Ly9zdG9yZS5leGFtcGxlLmNvbS9jYWxsYmFjay8ifQ==
```

The credentials are Base64 of a JSON object:

```json
{
  "code": "4/0AbC...",
  "iss": "https://accounts.google.com",
  "for": "https://store.example.com/callback/"
}
```

| Property | Meaning |
| --- | --- |
| `code` | The authorization code the provider returned. |
| `iss` | The issuer, as in `trust`. |
| `for` | The redirect URI the code was issued for. |

The reply is the same as for an `id_token`: the identity and a `Token`. A code is single-use, so
send it once and continue with the token.

## Federated credentials

An identity can have several providers attached, and several subjects of one provider. The
resources under `/identity/federation/:identity/` manage them; each requires credentials of that
identity.

### Attaching a provider to an existing identity

A user who signed up with a password adds Google as a second way in:

```http
POST /identity/federation/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
content-type: application/yaml
accept: application/yaml

scheme: bearer
credentials: eyJhbGciOiJSUzI1NiIsImtpZCI6...
```

```http
201 Created

id: 09200d0bcc2448c5863e3f50ae18af84
iss: https://accounts.google.com
CREATED: 1754899200000
```

`scheme` is `bearer` with an `id_token` as `credentials`, or `code` with the Base64 value described
above. From now on that provider's token resolves to this identity.

Attaching credentials the identity already has returns the existing one. Credentials that belong
to another identity are refused with `422` and the code `EXISTS`.

### Listing

```http
GET /identity/federation/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
accept: application/yaml
```

```yaml
- id: 09200d0bcc2448c5863e3f50ae18af84
  iss: https://accounts.google.com
  CREATED: 1754899200000
```

The subject is not returned. The `id` is the credential's own, not the identity's.

### Removing

```http
DELETE /identity/federation/2428c31ecb6e4a51a24ef52f0c4181b9/09200d0bcc2448c5863e3f50ae18af84/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
```

```http
204 No Content
```

Nothing stops the removal of the last credential; see
[where an identity ends](1.identities.md#where-an-identity-ends).

## Using the claims

A token of a provider carries more than `sub`: an email, a name, a repository. While the request is
authenticated with `Bearer`, those claims are available in two places.

**As input.** [`map:claims`](../gateway/7.mapping.md#token-claims) copies claims into the
operation's input; keys are input properties, values are claim names:

```yaml
# components/store.accounts/manifest.toa.yaml
exposition:
  /:
    POST:
      auth:incept: id
      map:claims:
        email: email
        verified: email_verified
      io:output: [id]
      endpoint: transit
```

A claim the token does not have leaves the property unset, and so does a request that is not
authenticated with a provider's `Bearer` token. That includes every later request made with the
gateway's `Token`, so read claims on the request that presents the `id_token`.

**As an access rule.** [`auth:claims`](6.access.md#claims) admits a request by the values of `iss`,
`sub` and `aud`, without any stored identity mattering. This is how a CI job is let in by the
repository its token names.

## The principal

As with [Basic credentials](2.credentials.md#the-principal), one subject can be named to receive
the `system` role when its identity is created:

```yaml
# context.toa.yaml
configuration:
  identity.federation:
    principal:
      authority: store
      iss: https://accounts.google.com
      sub: '104218230498234917283'
```

The same subject in another authority is ordinary.

## Configuration reference

All keys of `identity.federation`:

| Key | Meaning | Default |
| --- | --- | --- |
| `trust` | Trusted providers, see below. | `[]` |
| `assert` | Create an identity for valid credentials nobody owns. | `true` |
| `principal` | `authority`, `iss` and `sub` of the subject granted `system`. | none |

Each entry of `trust`:

| Key | Meaning |
| --- | --- |
| `iss` | Required. The issuer URI. |
| `aud` | Required. The accepted audience, or a list of them. |
| `secret` | Client secret; enables the authorization code flow. |
| `signature` | `iss`, `kid`, `key` (PKCS8 PEM) of a signed client assertion; enables the code flow. |

## What the client sees

Every rejection is the same to the client: the request has no identity, and a route that needs one
answers `401`. The reason is written to the gateway's log as a code:

| Code | Reason |
| --- | --- |
| `TRUST` | The issuer is not in `trust`. |
| `TOKEN` | The token is malformed, expired, badly signed, or for another audience. |
| `ISS`, `SUB` | The token has no `iss` or `sub`. |
| `NOT_FOUND` | Valid token, unknown subject, and `assert` is `false`. |
| `CODE_NOT_ENABLED` | A code was sent for a provider without `secret` or `signature`. |
| `CODE_SCHEMA` | The `Code` credentials are not the JSON described above. |
| `CONFIG`, `RESPONSE`, `NO_TOKEN` | The provider's metadata or its answer to the exchange was unusable. |

The same codes are returned as `422` by `POST /identity/federation/:identity/`, where the client
asked for the credentials to be attached and can be told why they were not.
