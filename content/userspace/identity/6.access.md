# Access

Who may call what is declared on the resource tree with directives of the `auth` family. Operations
never check permissions; the [model](../../model/edge/2.identity.md#authorization) explains why.
This article goes through every directive. How directives are written and inherited in general is in
[The Resource Tree](../gateway/2.routes.md#directives-are-inherited).

## Closed by default

A route with no `auth` directive admits nobody:

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:
    GET: enumerate
```

```http
GET /store/orders/ HTTP/1.1
host: store.example.com
```

```http
401 Unauthorized
```

Access is always something a route states.

## How a request is decided

Every `auth` directive that applies to a method is an alternative: **the request is admitted as
soon as one of them grants.** Directives declared on a node apply to its methods and to everything
nested under it, so alternatives accumulate down the tree.

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:customer:
    auth:id: customer          # the customer themselves…
    auth:role: store:support   # …or anyone in support
    GET: enumerate
    POST:
      auth:role: store:partner # …or, for POST only, a partner
      endpoint: create
```

When nothing grants, the reply depends on whether the request has an identity:

| The request | Reply |
| --- | --- |
| Has no credentials, or credentials that were rejected | `401 Unauthorized` |
| Has an identity that no directive admits | `403 Forbidden` |

Two consequences:

- **Nesting cannot narrow.** A directive on a nested node adds an alternative to those above it; it
  does not replace them. To require several conditions at once, use [`rule`](#rule). To start afresh
  on a subtree, declare it as a sibling route or mark the node `isolated: true`, as
  [Avoiding inheritance](../gateway/2.routes.md#avoiding-inheritance) describes.
- A directive may be written without the family prefix: `anonymous: true` is `auth:anonymous:
  true`. The examples here use the full name.

## `anonymous`

Admits a request that carries **no credentials**.

```yaml
# components/store.catalog/manifest.toa.yaml
exposition:
  /:
    auth:anonymous: true
    GET: enumerate
```

A request that does carry valid credentials is refused with `403`. This is deliberate: a response
to a request with credentials cannot be shared by caches, and a public resource should be
cacheable. A client must not send its token to anonymous routes. Resource descriptions mark such
methods `anonymous` so that a client can tell.

The rule does not apply to calls made through `/.rpc` and `/.mcp`: an anonymous route is reachable
there whatever the request presented.

## `anyone`

Admits any request with **valid credentials**, whoever it is.

```yaml
# components/store.pictures/manifest.toa.yaml
exposition:
  /:
    auth:anyone: true
    POST: upload
```

A resource open to both the public and signed-in users declares both:

```yaml
/:
  auth:anonymous: true
  auth:anyone: true
  GET: enumerate
```

## `id`

Admits the identity whose id equals a route variable. The value is the variable's name.

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:customer:
    auth:id: customer
    GET: enumerate
    POST: create
```

```http
GET /store/orders/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
```

The request is admitted when the token's identity is `2428c31ecb6e4a51a24ef52f0c4181b9`, and
answered `403` for any other identity.

This is how "people reach what is theirs" is expressed: put the owner in the path. It works because
an account and its identity
[share an id](1.identities.md#inception-an-identity-born-with-an-entity). Nested routes inherit
it, so `/:customer/:order/` is the customer's too.

## `role`

Admits an identity that holds a role covering the named scope.

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:
    auth:role: store:orders
    GET: enumerate
```

A list admits a holder of any of them:

```yaml
auth:role: [store:orders, store:support]
```

A scope may be built from route variables, written in braces:

```yaml
# components/store.catalog/manifest.toa.yaml
exposition:
  /:vendor:
    auth:role: store:vendors:{vendor}:manager
    PUT: transit
```

`PUT /store/catalog/acme/` requires a role covering `store:vendors:acme:manager`. A variable the
route does not have is a mistake in the declaration and answers `500`.

What "covers" means, and how roles are granted, is the subject of [Roles](7.roles.md).

## `rule`

Admits when **all** the directives inside it grant. It is how conditions are combined.

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:customer/:order:
    /refund:
      POST:
        auth:rule:
          id: customer
          role: store:verified
        endpoint: refund
```

Only the customer themselves, and only with the role, may ask for a refund. Inside a rule the
directives are named without the prefix.

A rule is itself one alternative among the others on the route. Remember inheritance when you rely
on one: if `/:customer` above carries `auth:id: customer`, that directive admits the customer on
its own and the rule narrows nothing. Declare the route where it does not inherit the wider grant.

## `claims`

Admits a request authenticated with a `Bearer` token of an
[external provider](4.federation.md) whose claims have the given values. `iss`, `sub` and `aud`
can be matched; at least one is required.

```yaml
# components/store.catalog/manifest.toa.yaml
exposition:
  /imports:
    POST:
      auth:claims:
        iss: https://token.actions.githubusercontent.com
        aud: https://github.com/acme
      endpoint: import
```

A value is compared exactly. Where the token's `aud` is a list, one matching entry is enough.
Three forms of value are computed from the request instead:

| Value | Matches |
| --- | --- |
| `/:name` | The value of the route variable `name`. |
| `:authority` | The [authority](8.authorities.md) of the request. |
| `:domain` | For `iss` only: an issuer on the same parent domain as the request's host. The issuer `https://accounts.example.com` matches requests to `shop.example.com` and `a.shop.example.com`, not to `shop.other.com`. |

```yaml
/vendors/:vendor:
  auth:claims:
    iss: https://id.example.com
    sub: /:vendor
```

The provider must be [trusted](4.federation.md#trusting-a-provider), or the token is rejected
before the directive is consulted. The directive applies only to the request that presents the
provider's token; requests made with the gateway's `Token` carry no claims.

## `scheme`

Refuses every authentication scheme but the named one. It grants nothing; pair it with a directive
that does.

```yaml
# components/store.accounts/manifest.toa.yaml
exposition:
  /:id:
    /close:
      POST:
        auth:scheme: basic
        auth:id: id
        endpoint: close
```

A request authenticated any other way is answered:

```http
403 Forbidden

Basic authentication scheme is required to access this resource
```

Use it where an action must be confirmed with the password itself, not with a token that may have
been lying on a device for weeks. The gateway's own password change route does.

## `input`

Restricts who may send particular properties of the request body. It grants nothing; it is checked
in addition to whatever admits the request.

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:customer/:order:
    PATCH:
      auth:id: customer
      auth:role: store:support
      auth:input:
        - prop: status
          role: store:support
        - prop: [items, total]
          id: customer
      endpoint: assign
```

Each entry names a property, or a list of them, and the directives required to send it. When the
body contains a named property and one of the entry's directives does not grant, the reply is:

```http
403 Forbidden

Input property is not authorized
```

Here a customer can change the items of their order but not its status. A body that does not
contain the property is unaffected. Bodies that are not objects are not checked.

## `delegate`

Admits any request with an identity, and puts that identity into the request body under the named
property.

```yaml
# components/store.orders/manifest.toa.yaml
operations:
  approve:
    type: transition
    input:
      type: object
      properties:
        approver:
          type: object
          properties:
            id: { type: string }
            roles: { type: array, items: { type: string } }
          required: [id]

exposition:
  /:order:
    /approval:
      PUT:
        auth:rule:
          role: store:managers
          delegate: approver
        endpoint: approve
```

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, order) {
  if (order.status !== 'pending')
    return new Error('NOT_PENDING')

  order.status = 'approved'
  order.approver = input.approver.id
}
```

The embedded value is an object that holds the identity's `id` and `roles`.

- **`delegate` alone admits every authenticated caller.** To record the caller *and* require a
  role, put both in a `rule`, as above. Written side by side they would be alternatives, and the
  role would not be required.
- The value comes from the gateway, not from the client. Whatever the client sent under that
  property is overwritten, and the property is left out of the input that resource descriptions
  show. An [`io:input`](../gateway/6.io.md#input) restriction applies to what the client sent, so
  the property does not need to be listed there.
- A missing body becomes an object holding the property. A body that is not an object is `400`.

It is meant for recording who did something: an approver, an author, an audit trail, and for
[echoing the caller's own entity](1.identities.md#the-account-of-the-caller). **Do not use it to
make decisions about access inside an operation.** Those belong on the route.

## `incept`, `assert` and `echo`

Three directives of the family create or return identities rather than guard resources:

- [`auth:incept`](1.identities.md#inception-an-identity-born-with-an-entity) admits a request
  without an identity and creates one from the reply.
- [`auth:assert`](1.identities.md#assertion-sign-in-or-sign-up-in-one-request) creates an identity
  for new credentials; it grants nothing.
- `auth:echo` answers the request with the caller's identity, creating a transient one when there
  are no credentials. It is what [`GET /identity/`](1.identities.md#asking-who-you-are) is made of,
  and an application has no reason to declare it again.

## Restrictions that come with the credential

A route's directives are not the only check. A credential may carry limits of its own, applied
after a directive grants:

- A [custom token](3.tokens.md#permissions) with `permissions` is refused with `403` outside the
  paths and methods it lists.
- A custom token with [`scopes`](3.tokens.md#scopes) holds those roles in place of its owner's.
- An [OAuth access token](9.oauth.md#audience) bound to a resource is refused with `401` anywhere
  else.

## Where directives are declared

A component declares access on its own resources in its manifest, as in every example above. The
Context can declare directives on the tree as well, under `exposition: /:`, and they are inherited
by the component branches below:

```yaml
# context.toa.yaml
exposition:
  /:
    auth:role: store:admin
```

Here an administrator may reach every resource of the application, whatever the components
declare for everyone else.

The gateway's own resources under `/identity/` are isolated: nothing declared above them applies.
`auth:anonymous: true` at the root does not open role management.

## What a caller is shown

Resource descriptions follow access. `OPTIONS` on a resource, the discovery document and the tool
list of MCP (see [Discovery](../gateway/16.discovery.md) and [MCP Tools](../gateway/15.tools.md))
include only the methods the asking identity may reach, and `OPTIONS` answers `403` where it may
reach none. A description also says what guards a method:

| Mark | Meaning | Set by |
| --- | --- | --- |
| `anonymous` | Send no credentials here. | `anonymous` |
| `authenticated` | Any identity. | `anyone`, `delegate`, `claims` |
| `private` | The identity the route names. | `id` |
| `protected` | A role. | `role` |
| `system` | A role within the `system` scope. | `role` |

Directives that depend on a route variable (`id`, a `role` with braces, `claims`) cannot be decided
without a request, so such methods are shown to every authenticated caller and hidden from callers
without an identity.

## Summary

| Directive | Value | Grants when |
| --- | --- | --- |
| `auth:anonymous` | `true` | The request has no credentials. |
| `auth:anyone` | `true` | The request has an identity. |
| `auth:id` | route variable name | The identity equals the variable. |
| `auth:role` | scope or list of scopes | A role of the identity covers one of them. |
| `auth:rule` | map of directives | Every directive in it grants. |
| `auth:claims` | `iss`, `sub`, `aud` | The provider's token carries those claims. |
| `auth:delegate` | input property name | The request has an identity; embeds it. |
| `auth:incept` | output property name or `null` | The request has no identity yet; creates one. |
| `auth:echo` | none | Always; answers with the identity. |
| `auth:scheme` | scheme name | Never; refuses other schemes with `403`. |
| `auth:input` | list of `prop` with directives | Never; refuses unauthorized properties with `403`. |
| `auth:assert` | `true` | Never; creates the identity for new credentials. |
