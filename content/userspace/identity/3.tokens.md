# Tokens

Whatever a client signs in with, it continues with a token the gateway issued. This article covers
how tokens are handed out and replaced, how long they live, the keys behind them, and *custom
tokens*: long-lived, restricted tokens for scripts and integrations.

## Receiving a token

A request authenticated by any scheme other than `Token` is answered with a token:

```http
GET /identity/ HTTP/1.1
host: store.example.com
authorization: Basic Ym9iOnNlY3JldCMxMjM0
```

```http
200 OK
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...
cache-control: no-store
```

The token arrives in the `authorization` **response** header, in the form the client sends back:

```http
GET /store/orders/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...
```

A token is opaque to the client: it is encrypted, and nothing in it is meant to be read.

The rule for a client is one line: **whenever a response carries an `authorization` header, discard
the token you hold and use the new one.** A browser client reads the header because the gateway
exposes it to cross-origin pages.

A response that carries a token is always `cache-control: no-store`, whatever the route declares.

## Refreshing

A token has two periods:

```yaml
# context.toa.yaml
configuration:
  identity.tokens:
    lifetime: 2592000 # seconds; 30 days
    refresh: 600      # seconds; 10 minutes
```

The values shown are the defaults.

- For `refresh` seconds after it was issued, a token is taken as it is: nothing is looked up.
- After that it is *obsolete* but still valid. The next request that presents it is served, and its
  response carries a fresh token.
- After `lifetime` it is refused, and the request has no identity (`401` where one is needed).

So a client that makes a request at least once every `lifetime` stays signed in indefinitely, and
one that stays away longer signs in again.

`refresh` is also how long a change takes to reach a signed-in client. A token carries the roles
the identity had when it was issued. A role granted or revoked, a changed password, a ban: each
takes effect when the token is next refreshed, at most `refresh` seconds later. A smaller value
tightens that window and costs a lookup more often.

## Keys

Tokens are encrypted with a symmetric key that you provide. It is the only identity setting
without a default.

```yaml
# context.toa.yaml
configuration:
  identity.tokens:
    keys:
      - id: 2026q3
        key: $IDENTITY_TOKENS_KEY_2026Q3
```

Generate a key:

```shell
toa key
```

Each entry has an `id` of your choice and a `key`, which is a secret: write a `$NAME` reference and
deploy the value separately ([Configuration](../services/2.configuration.md#secrets) shows how).

The **first** entry encrypts new tokens. Every entry decrypts: a token names the `id` of the key it
was made with. This is what makes rotation possible.

### Rotating a key

1. Add the new key **after** the current one and deploy. Every instance now knows both.

   ```yaml
   keys:
     - id: 2026q3
       key: $IDENTITY_TOKENS_KEY_2026Q3
     - id: 2026q4
       key: $IDENTITY_TOKENS_KEY_2026Q4
   ```

2. Move the new key to the first position and deploy. New tokens use it; old ones still decrypt.

   ```yaml
   keys:
     - id: 2026q4
       key: $IDENTITY_TOKENS_KEY_2026Q4
     - id: 2026q3
       key: $IDENTITY_TOKENS_KEY_2026Q3
   ```

3. Remove the old key only after the last token made with it has expired: `lifetime` after step 2,
   30 days by default. `refresh` is not a safe window, because an idle client still holds an old
   token.

Removing a key signs out everyone whose token was made with it. Never change the `id` of a key in
use.

### Legacy keys

An entry may carry `format: paseto`. Such a key only reads tokens issued by older versions of the
runtime; it never issues. A token read with it is replaced at once. Keep the entry until those
tokens have expired, then delete it. At least one entry without `format: paseto` is required.
`toa key --format paseto` generates such a key, and is needed only to maintain one.

## Revocation

There is no list of issued tokens, so a single token cannot be revoked. All tokens of an identity
are revoked together when:

- its [Basic credentials](2.credentials.md#changing-the-username-or-password) are changed, or
- the identity is [banned](7.roles.md#bans).

Revocation is noticed when a token is refreshed, so a revoked token keeps working for up to
`refresh` seconds and is then answered `401`.

To sign a user out everywhere, change their password or ban them. To sign out one device, the
device deletes its token.

## Custom tokens

A script, a CI job or a partner integration needs a credential that is not a person's password and
does not change under it. An identity issues one for itself:

```http
POST /identity/tokens/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
content-type: application/yaml
accept: application/yaml

label: Nightly export
lifetime: 3600
```

```http
201 Created

kid: 5b0c2f3d1a8e4c7f9d6b2a1e0f3c4d5e
exp: 1759700000000
token: eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...
```

`token` is sent as `authorization: Token …` like any other. `kid` identifies the key it was issued
under, which is what revokes it; `exp` is when it expires, in milliseconds.

A custom token differs from an ordinary one:

- **It is never refreshed.** Responses carry no replacement; it works unchanged until it expires.
- It is encrypted with a key of its own, not with `identity.tokens.keys`, so key rotation does not
  touch it.
- It can be restricted, as below.

### Options

| Property | Meaning |
| --- | --- |
| `label` | Required. A name of 1 to 64 characters, shown when keys are listed. |
| `lifetime` | Seconds the token is valid. Defaults to the configured `lifetime`. `0` never expires; avoid it in production. |
| `scopes` | Roles the token acts with, **in place of** the identity's own. |
| `permissions` | Paths and methods the token may be used at. |

### Scopes

```yaml
label: Catalog reader
lifetime: 86400
scopes: [store:catalog:read]
```

The token behaves as an identity whose only role is `store:catalog:read`. Each scope must be one
a role of the identity covers (see [Roles](7.roles.md#hierarchy)); otherwise no token is issued and
the reply is `422` with the code `INACCESSIBLE_SCOPE`. A token cannot hold more than its owner.

### Permissions

```yaml
label: Order export
lifetime: 86400
permissions:
  /store/orders/2428c31ecb6e4a51a24ef52f0c4181b9/: [GET]
  /store/pictures/**: ['*']
```

Keys are glob patterns matched against the request path, without the query string. Values are the
methods allowed there; `*` is any method. A request outside the permissions is answered `403`,
even where the identity itself would be admitted.

`scopes` and `permissions` only narrow. The token still passes the route's own
[access directives](6.access.md) as its identity.

### Acting for another identity

An identity that holds the role `system:identity:tokens` may issue a token for any identity, by
putting that identity's id in the path:

```http
POST /identity/tokens/e8e4f9c2a68d419b861403d71fabc915/ HTTP/1.1
host: store.example.com
authorization: Token <a token of an identity with system:identity:tokens>
content-type: application/yaml

label: Support session
lifetime: 600
```

The token that comes back resolves to `e8e4f9c2a68d419b861403d71fabc915`. This is how a support
tool acts as a customer. Keep the lifetime short and the role rare.

### Listing and revoking

Each custom token has a key, and the key is what you manage.

```http
GET /identity/keys/2428c31ecb6e4a51a24ef52f0c4181b9/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
accept: application/yaml
```

```yaml
- id: 5b0c2f3d1a8e4c7f9d6b2a1e0f3c4d5e
  label: Nightly export
  expires: 1759700000000
  CREATED: 1759696400000
```

Newest first. A revoked key also carries `revokedAt`. The secret itself is never returned.

```http
DELETE /identity/keys/2428c31ecb6e4a51a24ef52f0c4181b9/5b0c2f3d1a8e4c7f9d6b2a1e0f3c4d5e/ HTTP/1.1
host: store.example.com
authorization: Token eyJhbGciOiJkaXIi...
```

```http
204 No Content
```

Both requests need the identity itself or the role `system:identity:keys`.

The keys of an identity are also revoked automatically, and every custom token with them, when the
identity is banned, when its Basic credentials are changed, and when **any** of its roles is
revoked. After a role is revoked, issue the tokens again; they will carry the roles that are left.

A revoked or deleted key stops working within `cache.ttl`:

```yaml
# context.toa.yaml
configuration:
  identity.tokens:
    cache:
      max: 1024   # keys remembered per process
      ttl: 600000 # milliseconds; 10 minutes
```

The values shown are the defaults. Give both when you change either.

## Tokens as `Bearer`

A token the gateway issued is also accepted under the `Bearer` scheme:

```http
authorization: Bearer eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIi...
```

This is how [OAuth clients](9.oauth.md) present theirs. A client of your own should use `Token`.

## Configuration reference

All keys of `identity.tokens`:

| Key | Meaning | Default |
| --- | --- | --- |
| `keys` | Encryption keys, first one issues. Each: `id`, `key` (secret), optional `format` (`jwe` or `paseto`). | required |
| `lifetime` | Seconds a token is valid. | `2592000` |
| `refresh` | Seconds before a token is replaced on use. | `600` |
| `cache.max` | Custom token keys remembered per process. | `1024` |
| `cache.ttl` | Milliseconds a custom token key is remembered. | `600000` |

## What the client sees

| Situation | Reply |
| --- | --- |
| A token that cannot be decrypted, or whose key is no longer configured | `401` |
| A token past its `lifetime` | `401` |
| A token issued under another [authority](8.authorities.md) | `401` |
| A revoked token, after `refresh`; a revoked custom token, after `cache.ttl` | `401` |
| A custom token used outside its `permissions` | `403` |
| A custom token whose `scopes` do not cover the route's role | `403` |
