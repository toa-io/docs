# Mirroring a Provider's Object

The shop sells a membership: a monthly payment that gives free delivery. The membership lives at
the payment provider. It is created there, renewed there every month, cancelled there — by the
shop, or by the customer on the provider's own page — and it lapses there when a card fails. The
shop needs to know, for every order, whether the customer is a member right now, without asking
the provider each time.

So the shop keeps a copy and updates it from the provider's notifications. The naive way is to
apply what each notification carries: "renewed until June 1" sets `expires`, "cancelled" sets
`cancels`. It fails without any component being down:

- **Notifications arrive in any order.** The customer cancels and changes their mind within a
  minute. "Resumed" arrives first, "cancelled" second, and the shop's copy says cancelled for a
  membership that is alive.
- **There is often nothing to order them by.** Many providers stamp notifications in whole
  seconds and give the object no version.
- **A notification can be missed**, and from then on the copy is wrong until the next one happens
  to carry the same field.

## A notification is a signal to read again

Do not apply what a notification says. Take one thing from it — *which* object changed — and read
that object from the provider. Whatever order the signals come in, the last read is the current
truth.

```text
provider ── POST ──> store.webhooks.ingest ── call ──┐
the customer returns from the payment page ── call ──┼──> store.memberships.signal
the shop itself changed it at the provider ── call ──┘        │ call, by the derived id
                                                              v
                             store.memberships.merge ── call ──> store.payments.membership
                                 ~ store.memberships.sync        (reads the provider)
                                 v
                             store.accounts.entitle
```

### The mirror

```yaml
# components/store.memberships/manifest.toa.yaml
name: memberships
namespace: store

entity:
  associated: true
  properties:
    membership: { type: string }   # the provider's id
    customer: { type: string }
    plan: { type: string }
    expires: { type: integer }     # when the paid period ends, ms
    cancels: { type: integer }     # when a requested cancellation takes effect, ms
    timestamp: { type: integer }   # when it was read from the provider, ms
  required: [membership, customer, plan, expires, timestamp]

operations:
  signal:
    type: effect
    errors: &refusals [UNKNOWN_MEMBERSHIP, NO_CUSTOMER, UNAVAILABLE]
    input: &signal
      type: object
      properties:
        membership: { type: string }
      required: [membership]
  merge:
    concurrency: retry
    query: true
    errors: *refusals
    input: *signal
```

```typescript
// components/store.memberships/operations/signal.ts
import type { Context, SignalInput } from '../types/index.d.ts'
import { key } from '../lib/key.ts'

export async function effect (input: SignalInput, context: Context) {
  return await context.local.merge({ query: { id: key(input.membership) }, input })
}
```

```typescript
// components/store.memberships/operations/merge.ts
import type { Context, MergeInput, State } from '../types/index.d.ts'

export async function transition (input: MergeInput, entry: State, context: Context) {
  const read = await context.remote.store.payments.membership({
    input: { membership: input.membership }
  })

  if (read instanceof Error) return read

  const customer = entry.customer ?? read.metadata?.customer

  if (customer === undefined) return new Error('NO_CUSTOMER')

  entry.membership = read.id
  entry.customer = customer // set by the first read, never moved to another customer
  entry.plan = read.plan
  entry.expires = read.period_end * 1000
  entry.timestamp = context.now()

  if (typeof read.cancel_at === 'number') entry.cancels = read.cancel_at * 1000
  else delete entry.cancels
}
```

The entity is [associated](../logic/1.state.md#an-object-identified-by-something-else) and its id
is derived from the provider's, with the same `key` function as in
[Receiving Webhooks](13.webhooks.md#one-record-per-payment): every signal about one membership
reaches one object, and the first one creates it. An entity may instead declare
[an `id` of the provider's shape](../logic/1.state.md#identifiers-of-another-shape) and use the
provider's id as it is.

The mirror is "the membership as the provider held it at `timestamp`". `merge` only sets values,
so running it twice ends the same. `store.payments.membership` is one more operation of the
[gateway](12.gateways.md), declared with `errors: [UNKNOWN_MEMBERSHIP, UNAVAILABLE]`.

### Who signals

**The webhook**, before it answers the provider:

```typescript
// components/store.webhooks/operations/ingest.ts — after the notification is decoded
if (notification.type.startsWith('membership.')) {
  const signalled = await context.remote.store.memberships.signal({
    input: { membership: notification.data.id }
  })

  if (signalled instanceof Error && signalled.code === 'UNAVAILABLE') return signalled

  entry.membership = notification.data
}
```

`ingest` declares `errors: [DECODE, UNAVAILABLE]`, and the entity gains `membership`. If the
provider cannot be read at this moment, the notification is refused with `UNAVAILABLE`, the
provider gets `422`, and it sends the notification again later — which is exactly what a failed
read needs. Any other refusal (`NO_CUSTOMER`, `UNKNOWN_MEMBERSHIP`) would be the same next time,
so the notification is stored and answered with a success.

**The customer's return** from the payment page. The browser comes back with the id of the
checkout; the shop asks the gateway for the checkout, checks that it is the caller's, and signals
the membership it created. The customer sees the membership at once instead of waiting for the
webhook. The same route for a top-up is shown in
[Taking a Payment, End to End](16.payments.md).

**The shop's own change.** When the customer cancels in the shop, the shop changes the membership
at the provider and reads it back in the same breath:

```typescript
// components/store.memberships/operations/cancel.ts
import type { CancelInput, Context } from '../types/index.d.ts'

export async function effect (input: CancelInput, context: Context) {
  const [current] = await context.local.enumerate({
    query: { criteria: `customer==${input.customer}`, sort: ['expires:desc'], limit: 1 }
  })

  if (current === undefined) return new Error('NO_MEMBERSHIP')

  const cancelled = await context.remote.store.payments.cancel({
    input: { membership: current.membership }
  })

  if (cancelled instanceof Error) return cancelled

  await context.local.signal({ input: { membership: current.membership } })
}
```

`cancel` declares `errors: [NO_MEMBERSHIP, UNKNOWN_MEMBERSHIP, UNAVAILABLE]`, and
`store.payments.cancel` is one more operation of the gateway. If the last read fails, nothing is
lost: the provider's notification about the cancellation follows, and signals again.

### Telling the rest of the shop

`store.accounts` keeps what it needs of the membership, so that an order is decided from the
account alone. The mirror announces a change only when something the account holds changed:

```typescript
// components/store.memberships/events/sync.ts
import type { Event } from '@toa.io/core/types'
import type { Entity } from '../types/index.d.ts'

const HELD = ['plan', 'expires', 'cancels'] as const

export function condition (event: Event<Entity>) {
  return HELD.some((property) => event.origin?.[property] !== event.state[property])
}
```

An event file named `sync` replaces the [inherited one](../logic/7.events.md#inherited-events). A
read that found nothing new moves `timestamp` and publishes nothing.

```yaml
# components/store.accounts/manifest.toa.yaml
operations:
  entitle:
    concurrency: retry
    query: true
    errors: [OBSOLETE]
    input:
      type: object
      properties:
        plan: { type: string }
        expires: { type: integer }
        cancels: { type: integer }
        timestamp: { type: integer }
      required: [plan, expires, timestamp]

receivers:
  store.memberships.sync: entitle
```

```typescript
// components/store.accounts/receivers/store.memberships.sync.ts
import type { Entity as Membership } from '@components/store.memberships'
import type { EntitleInput } from '../types/index.d.ts'

export function request (membership: Membership) {
  const input: EntitleInput = {
    plan: membership.plan,
    expires: membership.expires,
    timestamp: membership.timestamp
  }

  if (membership.cancels !== undefined) input.cancels = membership.cancels

  return { query: { id: membership.customer }, input }
}
```

```typescript
// components/store.accounts/operations/entitle.ts
import type { EntitleInput, State } from '../types/index.d.ts'

export async function transition (input: EntitleInput, entry: State) {
  if (entry.membership !== undefined && input.timestamp < entry.membership.timestamp)
    return new Error('OBSOLETE')

  entry.membership = input
}
```

The shop's own events can arrive out of order too. Here there *is* something to order them by:
`timestamp`, the moment the provider was read. An older read is refused, and a refusal in a
receiver simply ends that event. Keeping copies in step is the subject of
[Ask the Owner, or Keep a Copy](8.ownership.md), and ordering of
[Messages Out of Order](6.order.md).

Whether the customer is a member is then one comparison, wherever it is needed:

```typescript
const member = account.membership !== undefined && account.membership.expires > context.now()
```

Nothing has to run when a membership lapses. The date passes, and the comparison turns false
([Work on the Clock](11.time.md)).

## Why read again instead of applying the notification

Applying needs an order, and the outside world rarely gives one you can trust. Reading needs
none.

**When something that lives elsewhere changes, treat every message about it as "look again", and
copy what you find. Apply the content of a message only if its sender gives every state of the
object a number that only grows.**

The cost is one request to the provider per notification. If the provider does number the states
of an object, carrying that number and refusing older ones is cheaper;
[Messages Out of Order](6.order.md) shows that form.

The call from `ingest` to `signal`, rather than an event, follows from who can try again. If the
read fails inside a receiver, the shop would have to repeat it itself, and the provider — the
only party that knows something changed — has already been told all is well. Done by a call
before the reply, a failed read is handed back to the provider, which repeats the notification
for days.

## What can still go wrong

**Two signals for one membership at once.** Both `merge` runs read the provider and try to write
the same object. One wins. `concurrency: retry` runs the other again from the start, so it reads
the provider *again* and writes what is true after the first
([Two Writers at Once](5.concurrency.md)). Running again is harmless here because the call inside
`merge` only reads; a transition that changes something elsewhere and may run again needs more
care.

**The same signal twice.** The provider is read twice and the same values are set twice. If
nothing the account holds changed, no `sync` follows.

**Signals out of order.** There is no order to respect: each one reads the present.

**The provider is down.** From the webhook: refused, and repeated by the provider. From the
customer's return or the shop's own change: the caller is told `UNAVAILABLE`, and the webhook
about the same change follows anyway.

**A notification never arrives.** The copy stays as it was read last. For a membership that is
bounded: `expires` passes, the shop stops treating the customer as a member, and the next signal
of any kind — a renewal, a return to the shop — reads the truth. Where staleness must be bounded
more tightly, a [pulse](../logic/13.schedules.md) that signals every membership whose `expires`
is near or just past does it.

**`sync` reaches the account late, or twice, or after a newer one.** Late: the account is behind
for a moment. Twice: `entitle` sets the same values. After a newer one: `OBSOLETE`.

**The mirror is not the cash register.** Reading a membership grants nothing. Money a membership
brings in arrives as paid invoices, and each is recorded once under the provider's id of the
invoice, exactly like a top-up in [Receiving Webhooks](13.webhooks.md). Keep "what state is it
in" and "what was paid" on separate paths.

## Rules of thumb

- One object per provider object, `associated`, under an id derived from the provider's.
- A message about it carries one useful thing: its id. Read the rest.
- Read and write in one transition with `concurrency: retry`; only set values.
- Record when you read, and let copies refuse anything older.
- Publish to the rest of the application only when something they keep has changed.
- Signal by a call where the sender can retry and you cannot; refuse only for "ask again later".
- After changing the object at the provider yourself, signal at once and let the webhook cover a
  failure.
- An expiry is a date to compare with, not an event to wait for.
