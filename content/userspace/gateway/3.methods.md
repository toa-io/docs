# Methods and Calls

A method of the tree maps an HTTP method on a route to one operation. For every request the
gateway builds one call — an `input` and a `query`, as described in
[Requests](../components/4.requests.md) — and turns the reply into a response.

## Declaring a method

The short form names the operation:

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:
    io:output: true
    GET: enumerate
    POST: create
```

The long form is an object. It is needed as soon as the method has a query declaration or
directives of its own:

```yaml
exposition:
  /:id:
    PUT:
      endpoint: approve
      io:output: [id, status]
```

| Key | Meaning |
| --- | --- |
| `endpoint` | The operation to call. |
| `query` | What a request may select, see [Queries](4.queries.md). |
| `family:name` | Directives of this method. |

In a component's manifest `endpoint` is the name of one of its own operations; an operation that
does not exist is refused when the manifest is read. In the Context an endpoint is written in
full: `store.orders.approve`.

A method may also be served by a directive alone, without an operation — a stored file, a
[realtime](13.realtime.md) stream, a [stub](17.running.md#stubs). Such methods have no `endpoint`;
they are described with their directives.

## Which operation for which method

HTTP methods carry meaning that clients, caches and crawlers act on. Map each to the kind of
operation that means the same:

| Method | Operation | Use |
| --- | --- | --- |
| `GET` | Observation, computation | Read one entity, a list, or a computed value. |
| `POST` | Transition without a query, effect | Create an entity; do something. |
| `PUT` | Transition with a query, effect | Change the entity the path selects. |
| `PATCH` | Assignment, effect | Set some properties of the entity the path selects. |
| `DELETE` | Transition | Remove the entity the path selects. |

`HEAD` is served by the method declared for `GET`: it answers the same headers and no body.
`LOCK` and `UNLOCK` may be declared like any other method where an application has a use for
them. `OPTIONS` is not declared: it [describes the resource](16.discovery.md). A method the route
does not declare is `405 Method Not Allowed`; one the gateway does not know at all is
`501 Not Implemented`.

Operation types are explained in [Operations](../components/2.operations.md).

## The body becomes the input

The request body, decoded from the format `content-type` names, is the call's `input`.

```yaml
exposition:
  /:
    io:output: [id]
    POST: create
```

```http
POST /store/orders/ HTTP/1.1
content-type: application/json

{"customer": "b70a7dbca6b14a2eaac8a9eb4b2ff4db", "items": [{"product": "kettle", "quantity": 1}], "total": 4200}
```

The input is validated against the operation's input schema. A body that does not fit is
refused before the operation runs:

```http
HTTP/1.1 400 Bad Request

"must have required property 'customer'"
```

A route can accept less than the operation does, see [`io:input`](6.io.md#input), and can fill
input properties from the request itself — headers, the language, the host — see
[Mapping the Request](7.mapping.md).

## Route variables

For every method except `POST`, route variables select state. They go to the query:

- a variable named `id` becomes `query.id`;
- any other variable becomes a condition `name==value` of `query.criteria`.

```yaml
exposition:
  /of/:customer/:id:
    io:output: true
    GET: observe
```

`GET /store/orders/of/b70a…f4db/4c47…d6f4/` observes the order `4c47…d6f4`, provided its
`customer` is `b70a…f4db`. If it is another customer's order, nothing matches and the answer is
`404`.

For `POST` there is no state to select yet, so route variables go to the input:

```yaml
exposition:
  /of/:customer:
    io:output: [id]
    POST: create
```

```http
POST /store/orders/of/b70a7dbca6b14a2eaac8a9eb4b2ff4db/ HTTP/1.1
content-type: application/yaml

items:
  - product: kettle
    quantity: 1
total: 4200
```

The operation receives `customer` in its input, taken from the path. **A route variable
overrides an input property of the same name**, so a client cannot create an order for a
customer other than the one in the path.

An operation that takes no query at all — a computation, an effect — receives route variables
in its input too. To hand a variable to the input of any method explicitly, or to keep one out of
the criteria, use [`map:segments`](7.mapping.md#route-variables).

## The query string

What a client may put after `?` is decided by the method's `query` declaration. With none, a
method that maps a queryable operation accepts the standard parameters within default bounds:

```http
GET /store/orders/?criteria=status==pending&sort=total:desc&limit=20 HTTP/1.1
```

A parameter the method does not take is refused:

```http
HTTP/1.1 400 Bad Request

"Query must NOT have additional properties"
```

[Queries](4.queries.md) covers the parameters, their bounds, and how a route fixes or opens
each of them.

## `GET` does not write

`GET` and `HEAD` are safe methods: a browser prefetches them, a crawler follows them, a cache
replays them. The gateway holds them to that. A call made for a `GET` is read-only, and so is
every call made below it: if it reaches an operation that may change state, the request fails
with `500`.

```yaml
exposition:
  /:id:
    io:output: true
    GET: cancel        # a transition: every request is answered 500
```

The rule covers the whole chain. A `GET` mapped to an observation that calls a transition of
another component fails the same way; see [Call chains](../../model/reliability/6.chains.md).

Where a safe method really has to write — a confirmation link in an email — say so with
`io:readonly`:

```yaml
exposition:
  /confirmations/:id:
    GET:
      endpoint: confirm
      io:readonly: false
```

The value states what holds for the call whatever the method: `false` lets a `GET` write, `true`
makes a `POST` read-only. Like any directive it can be written on a node for every method under
it. `HEAD` follows its `GET`.

Use `io:readonly: false` as an exception. A `GET` that writes is still treated as safe by
everything between the client and the gateway.

An effect or an unmanaged operation counts as one that may change state, even when it only
computes. Behind a `GET` such an operation needs `io:readonly: false` as well.

## What comes back

The reply of the operation decides the status.

| Reply | Response |
| --- | --- |
| Output, to `GET`, `PUT`, `PATCH`, `DELETE` | `200 OK` with the output as the body |
| Output, to `POST` | `201 Created` with the output as the body |
| Output the route does not let through | `204 No Content`; `201` with no body to a `POST` |
| Nothing: `null`, or no entity matched | `404 Not Found` |
| A returned error | `422 Unprocessable Entity` with the error as the body |
| A stream | A multipart response, see [Streams and Flow](9.streams.md) |

A returned error is the refusal the operation declares in `errors:`
([Errors](../components/3.errors.md)). Its code is the body the client reads:

```javascript
// components/store.orders/operations/approve.js
export async function transition (input, order, context) {
  if (order.status !== 'pending') return new Error('NOT_PENDING')

  // ...
}
```

```http
PUT /store/orders/4c4759e6f9c74da989d64511df42d6f4/ HTTP/1.1
accept: application/yaml
```

```http
HTTP/1.1 422 Unprocessable Entity
content-type: application/yaml

code: NOT_PENDING
```

An exception — a bug, an unreachable dependency — is `500` with an empty body. The full list of
statuses, and what failures of the request itself look like, is in
[Requests and Responses](5.protocol.md#statuses).

An operation that needs to choose the status itself, for a protocol that demands it, declares
[`io:status`](6.io.md#status).

## Retrying safely

A client that did not receive an answer cannot tell whether its request was carried out. For a
method whose operation declares [`once`](../reliability/3.idempotency.md#declaring-it), the client
can repeat the request under an `idempotency-key` header and be answered with what the first attempt
answered:

```http
POST /store/orders/ HTTP/1.1
idempotency-key: 3f1c8a2e-5b7d-4c1e-9a55-0d6f1e2b7c33
content-type: application/yaml

customer: b70a7dbca6b14a2eaac8a9eb4b2ff4db
total: 4200
```

The key is the client's to generate and to repeat only for a retry of the same request. It is
scoped by who is calling, by the method and by the path, so the same key on two routes is two
calls, and one client's key never meets another's. The body is not part of it: a retry with a
different body is answered with the first answer.

A key sent to a method whose operation does not declare `once` is accepted and has no effect. On a
route that nobody is authenticated on, all clients share one scope of keys; give a state-changing
route an [access rule](../identity/6.access.md).

What `once` is, and how to declare it, is in
[Idempotency](../../model/reliability/3.idempotency.md).

## Changing only if unchanged

A `PUT` or `PATCH` can be made conditional on the version of the entity the client last read,
with the `if-match` header. This is covered with caching, in
[Versions and conditional writes](8.caching.md#versions-and-conditional-writes).
