# Running the Gateway

The gateway is a service the runtime provides. An application does not write it, but it does
decide where it runs, which hosts it answers on, and a handful of options of its deployment.
All of them live under `exposition` in the Context. This article also covers the tools for
developing against the gateway: stubs, delays and faults.

## Locally

Running the whole application in one process starts the gateway with it:

```shell
$ toa mono components/*
```

`mono` starts the service of every extension the components use, so a component with an
`exposition` section brings the gateway up. It listens on port `8000`:

```shell
$ curl -i http://localhost:8000/store/orders/
```

To run a composition with the gateway beside it, name the service:

```shell
$ toa compose components/* --service exposition
```

`--service` is exact: nothing else is started. Or run the gateway as a process of its own, next
to compositions started separately:

```shell
$ toa serve exposition
```

In every case the environment is prepared first, as described in
[Running](../start/3.running.md).

A local Context usually answers on `localhost` and shows exceptions:

```yaml
# context.toa.yaml
exposition:
  authorities:
    shop@local: localhost:8000
    shop@production: api.store.example
  debug@local: true
```

A key suffixed with `@<environment>` applies in that environment only; see
[Environments](../../model/running/1.environments.md).

### Ports

| Port | Serves |
| --- | --- |
| `8000` | The application's traffic. |
| `8004` | The gateway's readiness probe. |

## Authorities

`authorities` is the only required option. It maps an identifier to each host the application
is served on:

```yaml
exposition:
  authorities:
    shop: api.store.example
    outlet: api.outlet.example
```

- The hosts are what the gateway's ingress is created for in a deployment.
- The identifier is what [`map:authority`](7.mapping.md#the-host) hands to operations, and what
  identities and credentials are bound to. **Renaming an identifier invalidates the credentials
  issued under it.** Changing the host behind an identifier does not.
- A request for a host that is not listed is still served; its authority is the host name
  itself.

Give each environment its own host under the same identifier, as in the example above, so that
the identifier — and everything bound to it — stays stable across environments.

## In a deployment

By default the gateway is deployed on its own, with a `Service` and an `Ingress` for the
authorities' hosts. Deployment as a whole is described in
[Deployment](../../model/running/4.deployment.md); these options shape the gateway's part.

```yaml
# context.toa.yaml
exposition:
  authorities:
    shop: api.store.example
  class: nginx
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: 64m
  resources:
    cpu: [200m, 2000m]
    memory: [200Mi, 1Gi]
```

| Option | Meaning |
| --- | --- |
| `class` | The ingress class. |
| `annotations` | Annotations of the `Ingress`. |
| `service.annotations` | Annotations of the `Service`. |
| `resources` | CPU and memory of the gateway's pods: for each, the request and the limit. `~` deploys without any. |
| `protocol` | `h1` (the default) or `h2c`, see [HTTP/2](#http2). |

Whatever stands in front of the gateway has its own limits. An ingress that caps request bodies
below the `limit` of an [upload route](11.files.md#size-limit), or times out idle connections
sooner than a [realtime stream](13.realtime.md) sends heartbeats (every 16 seconds), will cut
requests the gateway would have served. Set those through `annotations`.

### In a composition

The gateway can run inside a composition's pods, instead of in pods of its own:

```yaml
# context.toa.yaml
compositions:
  - name: edge
    components:
      - store.orders
      - store.accounts
    services:
      - exposition
```

Its `Service` and `Ingress` stay the same and now select that composition's pods. Compositions
are described in [Compositions](../../model/running/2.compositions.md).

### Readiness

The gateway answers `GET /.ready` on port `8004`:

- `200` once it is connected, has discovered the routes of the running components, and is
  listening;
- `503` with `retry-after` before that.

The probe is on a port of its own, and the traffic port answers `404` for `/.ready`. In a
deployment the probe is configured for you. Under a process manager, the gateway also sends the
`ready` message that PM2's `wait_ready` waits for.

### Stopping and halting

When the gateway stops, it finishes the requests in flight. Open streams are ended with `FIN`,
so their readers reconnect to another replica.

While a deployment is [halted](../../model/running/6.halt.md), the gateway keeps its port and
answers every request `503` with `cache-control: no-store`, so that clients are told by the
application instead of meeting a refused connection.

### HTTP/2

The gateway serves HTTP/1.1. `protocol: h2c` makes it serve cleartext HTTP/2 instead:

```yaml
exposition:
  protocol: h2c
  service:
    annotations:
      projectcontour.io/upstream-protocol.h2c: '8000'
```

- The ingress controller must proxy cleartext HTTP/2 upstream, and usually needs an annotation
  to do so. Contour, Traefik and Envoy-based controllers can; ingress-nginx cannot.
- A gateway serving `h2c` answers nothing else on that port. A controller that speaks HTTP/1.1
  upstream reaches nothing.
- Under `h2c`, a request refused before its body was read — too large, not authorized — is
  answered and then cancelled. The client gets the reply, and its upload stops. A client that
  streams a body has to handle the cancelled stream: in Node it is
  `ERR_STREAM_PREMATURE_CLOSE` on the stream it passed.

## Client address

Behind a load balancer every connection comes from the balancer, so the gateway cannot take the
client's address from the connection — and it never does. The Context names the header in which
the edge writes it:

```yaml
exposition:
  ip: cf-connecting-ip
```

Name the header your edge **overwrites**: `CF-Connecting-IP`, `X-Real-IP`, `X-Forwarded-For`,
depending on the infrastructure. A client can send any of these itself, so only a header the
edge sets is trustworthy. Where the header holds a list, the last value — the one the edge
appended — is used.

The address is what [`io:throttle`](6.io.md#keys) keys on with `ip`, and what failed authentications
are metered by (`bouncer`, see [Credentials](../identity/2.credentials.md#failed-attempts)).

Without `ip`, or for a request without the header, a request has no address: a throttle keyed
on `ip` lets it through, and says so in the log.

## Censor

A request can be refused by the value of a header, before anything else looks at it:

```yaml
exposition:
  censor:
    header: cf-ipcountry
    values: [XX, YY]
```

A request whose `header` holds one of `values` is answered
`451 Unavailable For Legal Reasons` with an empty body, whatever its path. It is refused before
it is routed or authenticated, and calls nothing.

- The header's name matches in any case. A value matches exactly: `xx` is not `XX`.
- A request without the header, or with another value, is served.
- The reply carries CORS headers and preflights are answered, so a page can read the status and
  tell its user.
- The header is taken as it arrives. It is meaningful only if an edge in front of the gateway
  writes it; a client that reaches the gateway around that edge sends what it likes.

## Seeing what answered

Every reply carries an `exposition` header naming the gateway's build, the Context and the
environment. When several environments or versions are in play, it tells which one a reply came
from.

`debug: true` puts the text of exceptions into `500` replies; see
[Errors](5.protocol.md#seeing-exceptions-while-developing). Keep it to non-production
environments: `debug@local: true`.

## Development directives

The `dev` family helps to build a client before, or without, the operations behind it.

### Stubs

`dev:stub` answers a method with a fixed body. No operation is called, so a route can exist
before its component does:

```yaml
# context.toa.yaml
exposition:
  /:
    /recommendations:
      anonymous: true
      io:output: true
      GET:
        dev:stub:
          - product: kettle
            score: 0.93
          - product: teapot
            score: 0.71
```

```http
GET /recommendations/ HTTP/1.1
accept: application/json
```

```http
HTTP/1.1 200 OK
content-type: application/json

[{"product":"kettle","score":0.93},{"product":"teapot","score":0.71}]
```

The route's access rules and content negotiation apply as to a real reply. A stub of `null`
answers `404`, as an operation that found nothing does.

### Delays

`dev:sleep` lets a client ask for a slow answer, to see how its interface behaves while it
waits. The value is the longest delay the route allows, in milliseconds:

```yaml
# context.toa.yaml
exposition:
  /:
    dev:sleep@local: 10000
```

A request then names the delay it wants in the `sleep` header, as a JSON array of the minimum
and the maximum in milliseconds; the actual delay is random between them:

```http
GET /store/orders/ HTTP/1.1
sleep: [500, 1500]
```

A request without the header is not delayed. A range beyond the route's maximum is
`400 Invalid sleep duration`. Declared on the Context's `/`, as above, it is available on every
route of the application, in the local environment only.

### Faults

`dev:faulty` makes a route fail at random, to see how a client copes. The value is the
probability, greater than 0 and at most 1, with which a request is answered
`503 Service Unavailable`:

```yaml
exposition:
  /:
    dev:faulty@local: 0.2
```

`dev:throw` makes a method throw an exception with the given message, which answers `500`:

```yaml
      GET:
        dev:throw: Not built yet
```

**Keep `dev` directives out of production.** Suffix them with a development environment, as in
the examples, or remove them before deploying.

## Other endpoints of the gateway

Besides the application's routes, the gateway serves a few paths of its own.

| Path | Serves | Turned on by |
| --- | --- | --- |
| `/.discovery` | The tree and its page, see [Discovery](16.discovery.md). | always on |
| `/.rpc` | [JSON-RPC](14.procedures.md). | `exposition.rpc` |
| `/.mcp` | [MCP](15.tools.md). | `exposition.mcp` |
| `/realtime/:id/` | An identity's [own stream](13.realtime.md#an-identitys-own-stream). | always on |
| `/.ready` on port `8004` | The readiness probe. | always on |

Identity endpoints under `/identity/`, and the OAuth endpoints, are described in
[Identity Reference](../identity/10.reference.md#resources).

## Reference

Every key of `exposition` in the Context:

| Key | Type | Meaning |
| --- | --- | --- |
| `authorities` | `{ identifier: host }` | Hosts the application is served on. Required. |
| `/` | resource tree | Routes and directives of the Context, see [Exposing a Component](1.exposing.md#routes-declared-in-the-context). |
| `debug` | boolean | Put exception text into `500` replies. Default `false`. |
| `class` | string | Ingress class. |
| `annotations` | `{ name: value }` | Ingress annotations. |
| `service.annotations` | `{ name: value }` | Service annotations. |
| `resources` | `{ cpu: [a, b], memory: [a, b] }` or `~` | Resources of the gateway's pods. |
| `protocol` | `h1` or `h2c` | HTTP version served. Default `h1`. |
| `ip` | header name | Where the client address is read from. |
| `censor` | `{ header, values }` | Requests answered `451`. |
| `rpc` | `{ batch }` | Serve JSON-RPC, see [JSON-RPC](14.procedures.md). |
| `mcp` | `{ name, … }` | Serve MCP, see [MCP Tools](15.tools.md#reference). |
| `bouncer` | `{ attempts, interval }` | Meter failed authentications per address; requires `ip`. See [Credentials](../identity/2.credentials.md#failed-attempts). |
| `oauth` | `{ authorize, … }` | The OAuth authorization server. See [The OAuth Server](../identity/9.oauth.md). |
