# Mapping the Request

By default an operation exposed over HTTP receives the body as its input and the path as its
query. A request carries more than that: headers, a language, the host it was sent to, the
claims of a token. The `map` directives put those into input properties, so an operation gets
them as plain arguments and stays ignorant of HTTP. The `require` directives state what a
request must carry.

## The rules of mapping

```yaml
# components/store.catalog/manifest.toa.yaml
exposition:
  /:
    io:output: true
    GET:
      endpoint: browse
      map:headers:
        currency: x-currency
```

`browse` receives `input.currency` holding the value of the `x-currency` header.

- The operation's input must be an object.
- **A mapped property overwrites one the client sent.** Whatever is mapped is the route's to
  fill, not the caller's.
- A mapped property is not subject to [`io:input`](6.io.md#input). A route may forbid every body
  property and still fill some itself.
- In the answer to [`OPTIONS`](16.discovery.md#asking-a-resource) a mapped property is taken out
  of the input schema, because a client has nowhere to send it.

## Headers

`map:headers` maps input properties to request headers. Keys are input properties, values are
header names:

```yaml
map:headers:
  currency: x-currency
  agent: user-agent
```

A header sent several times arrives as one comma-separated value. A header that is absent leaves
the property unset; make the header mandatory with [`require:header`](#requiring-headers), or the
property optional in the operation's input.

Each mapped header is added to the reply's `vary` and to the headers a browser on another origin
may send ([CORS](5.protocol.md#browsers-on-other-origins)).

## Route variables

Route variables normally go to the query (or, for `POST`, to the input) on their own, see
[Methods and Calls](3.methods.md#route-variables). `map:segments` puts a variable into the input
under a name of your choice. Keys are input properties, values are variable names:

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:id/items/:product:
    io:output: true
    PUT:
      endpoint: amend
      map:segments:
        product: product
```

`PUT /store/orders/4c47…d6f4/items/kettle/` calls `amend` on the order `4c47…d6f4` with
`input.product` set to `kettle`.

A variable that is mapped this way is still used for criteria and still seen by other
directives. Prefix its name with `~` to take it out of both:

```yaml
      map:segments:
        product: ~product
```

Use `~` when the variable is an argument and not a property of the entity. Without it,
`product==kettle` would be added to the criteria, and an order has no such property.

The rest of a path matched by `**` is mapped under the name `'**'`:

```yaml
# components/store.pages/manifest.toa.yaml
exposition:
  /**:
    io:output: true
    GET:
      endpoint: render
      map:segments:
        path: '**'
```

`GET /store/pages/help/shipping/` calls `render` with `input.path` set to `help/shipping`.

## Language

`map:languages` lists the languages the application supports, and `map:language` puts the one
that best matches the request's `accept-language` into an input property:

```yaml
# components/store.catalog/manifest.toa.yaml
exposition:
  /:
    map:languages: [en, fr]
    io:output: true
    GET:
      endpoint: browse
      map:language: language
```

```http
GET /store/catalog/ HTTP/1.1
accept-language: fr-CA, fr;q=0.9, en;q=0.5
```

```http
HTTP/1.1 200 OK
content-language: fr
vary: origin, accept-language, accept
```

`browse` receives `input.language` set to `fr`. If none of the supported languages matches, the
first of the list is used. The reply carries `content-language` and varies on `accept-language`.

The list is usually the same for the whole application. Declare it once, in the Context, with
its shortcut:

```yaml
# context.toa.yaml
exposition:
  /:
    languages: [en, fr]
```

## The host

An application may be served on several hosts. The Context gives each one an identifier, an
*authority*:

```yaml
# context.toa.yaml
exposition:
  authorities:
    shop: api.store.example
    outlet: api.outlet.example
```

`map:authority` puts the identifier of the host a request was sent to into an input property:

```yaml
# components/store.catalog/manifest.toa.yaml
exposition:
  /:
    io:output: true
    GET:
      endpoint: browse
      map:authority: storefront
```

A request to `api.outlet.example` calls `browse` with `input.storefront` set to `outlet`. This
is how one deployment serves several storefronts with different catalogues.

A host that is not among the authorities is passed as it is, lowercased:
`api.unknown.example`. A `host` that is not a host name (with an optional port) is answered
`400`.

Authorities matter beyond mapping. An identity and its credentials belong to one authority, so
renaming an identifier invalidates them; see
[Authorities and the Edge](../identity/8.authorities.md#identities-belong-to-an-authority). Hosts
are given per environment in [Running the Gateway](17.running.md#authorities).

## Token claims

`map:claims` maps the claims of the request's `Bearer` token to input properties. Keys are input
properties, values are claim names:

```yaml
# components/store.accounts/manifest.toa.yaml
exposition:
  /:
    POST:
      endpoint: open
      map:claims:
        email: email
        verified: email_verified
```

If the request is not authenticated with a `Bearer` token, or the token has no such claim, the
property is not set. Which tokens are accepted is described in
[Credentials](../identity/2.credentials.md#schemes).

## The raw body

`map:buffer` hands the body to the operation as it was sent, unparsed. The value is the input
property that receives it:

```yaml
# components/store.payments/manifest.toa.yaml
exposition:
  /callbacks:
    POST:
      endpoint: accept
      map:buffer: body
      map:headers:
        signature: x-signature
```

```javascript
// components/store.payments/operations/accept.js
export async function effect ({ body, signature }, context) {
  if (!verify(body, signature)) return new Error('BAD_SIGNATURE')

  const event = JSON.parse(body)

  // ...
}
```

This is what a webhook needs: a signature is computed over the exact bytes, which parsing and
re-encoding would not preserve.

- The body arrives as a UTF-8 string.
- It is not parsed, so the request may carry any `content-type`.
- The route receives no parsed body: the input holds the buffer and whatever else is mapped.
- A route with `map:buffer` is served over HTTP only. It is not available as a
  [procedure](14.procedures.md).

## The body as a stream

`map:stream` hands the body to the operation as a stream, for content that has to flow through
an operation without being held in memory. It is described in
[Streams and Flow](9.streams.md#streamed-request-bodies). A route cannot declare both
`map:stream` and `map:buffer`.

## The process

`map:instance` names the route variable that carries the process a stateful operation is called
on. It is described in [Streams and Flow](9.streams.md#stateful-operations).

## Requiring headers

`require:header` refuses a request that lacks a header. `require:headers` takes a list:

```yaml
# components/store.orders/manifest.toa.yaml
exposition:
  /:id:
    require:header: if-match
    io:output: [id, status]
    PUT: approve
```

```http
PUT /store/orders/4c4759e6f9c74da989d64511df42d6f4/ HTTP/1.1
accept: text/plain
```

```http
HTTP/1.1 400 Bad Request

Header required: if-match
```

Requiring `if-match` makes every write to the route conditional on the version the client read,
so no client can overwrite a change it has not seen; see
[Versions and conditional writes](8.caching.md#versions-and-conditional-writes).

```yaml
require:headers: [if-match, x-currency]
```

Like every directive, a requirement on a node applies to all methods under it.

## Summary

| Directive | Value | Fills the property with |
| --- | --- | --- |
| `map:headers` | `{ property: header }` | The header's value. |
| `map:segments` | `{ property: variable }` | The route variable; `~variable` also removes it from criteria. |
| `map:languages` | list of language codes | Nothing: declares the supported languages. |
| `map:language` | property | The best supported language for `accept-language`. |
| `map:authority` | property | The identifier of the host. |
| `map:claims` | `{ property: claim }` | The claim of the `Bearer` token. |
| `map:buffer` | property | The unparsed body, as a string. |
| `map:stream` | property, or an object | The body as a stream. |
| `map:instance` | variable | Nothing: names the process to call. |
| `require:header` | header | Nothing: refuses a request without it. |
| `require:headers` | list of headers | Nothing: refuses a request that lacks one of them. |
