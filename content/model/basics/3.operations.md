# Operations

An operation has a type, a scope of state it works on, and rules it keeps so that the runtime
can execute it on the application's behalf. Three of the types manage entity state, as
[The Component](../foundations/3.component.md) shows; two more do not.

## Types

![The phases of a transition, an observation and an assignment](https://res.cloudinary.com/dl5z4zgth/image/upload/v1791358562/operation-phases_azcl08.png)

An operation's type states its relationship to state and to the world outside the component.

| Type | Phases | Purpose |
| --- | --- | --- |
| Transition | Retrieve → Run → Commit | Reads and changes current state. |
| Observation | Retrieve → Run | Reads state. |
| Assignment | Run → Commit | Describes a change without reading state. |
| Computation | Run | Derives a result; touches no state and has no side effects. |
| Effect | Run, optionally after Retrieve | Acts beyond the component's own state. |

### Computation

A computation is logic without state. It receives input, may use the context, and returns a
result:

```typescript
export async function computation (input: Input, context: Context) {
  return input.total * context.configuration.rate
}
```

A component made only of computations declares no entity at all. It is still a component: it has
a logical address, a contract, and a place in a composition.

### Effect

An effect is an operation whose purpose is something other than changing its own entity:
sending a message, calling an external system, orchestrating calls to other components.

```typescript
export async function effect (input: Input, context: Context) {
  const order = await context.remote.orders.observe({ query: { id: input.order } })

  await context.remote.billing.charge({ input: { order: order.id, total: order.total } })
  await context.remote.inventory.reserve({ input: { order: order.id } })
}
```

Declaring such logic as an effect is a statement of intent. The runtime cannot make an effect
safe to repeat or undo what it did outside the component, so it treats effects with the caution
their type announces. In a component that stores state, an effect can be called for a particular
entity; the runtime then supplies that entity's state, creating the entity if it does not exist
yet.

## Scope

The *scope* is the shape of state an operation is handed in its Retrieve phase.

| Scope | The operation receives |
| --- | --- |
| `entry` | One entity object. |
| `entries` | A set of entity objects. |
| `stream` | A stream of entity objects, read as the storage finds them. |
| `changeset` | An empty changeset to fill (assignments). |
| `none` | No state. |

The query of a call selects *which* state; the scope determines *how much* of it the operation
is prepared to work with. An observation over `entries` lists orders; a transition over `entry`
changes one.

A transition over `entries` changes several entities as one unit. The set is committed whole or
not at all: if any member changed since it was read, nothing is written.

Such a set is always bounded. The call names its members by `ids` or caps what its criteria
select with a `limit`, and the transition commits exactly the entities it was handed: a `limit`
of two changes two. A change to everything the criteria match is therefore a series of calls,
each over a bounded set, repeated until one comes back short:

```typescript
await context.local.expire({
  query: { criteria: 'status==pending;deadline<1700000000000', limit: 256 }
})
```

A transition that changes what its criteria read — here, the status — finds fewer entities each
time. A `limit` without `sort` takes any of the matching entities, not the same ones twice.

## Safety

Operations are either *safe* or *unsafe*, by whether they are allowed to change anything.

| Type | Safety |
| --- | --- |
| Observation | Safe |
| Computation | Safe |
| Transition | Unsafe |
| Assignment | Unsafe |
| Effect | Unsafe |

Safety is a property of the type, not of a particular call: a transition is unsafe even when a
given call of it changes nothing. This lets the runtime reason about calls before making them.
A request that is only supposed to read can be refused the moment it reaches an unsafe
operation; see [Call Chains](../reliability/6.chains.md).

## Genuine operations

The runtime can retrieve state, retry on conflict, run replicas, and move a component across
process boundaries only if operations behave predictably. An operation's implementation is
expected to be:

1. **Stateless.** It keeps nothing between calls. Running one instance many times gives the same
   results as running many instances once each.
2. **Deterministic.** The same input and state produce the same result.
3. **Autonomous.** It does not assume anything about where it runs, such as direct network
   access.
4. **Pure.** Its only effects are the state it changes and what it does through the context.
5. **Non-exceptional.** It does not use exceptions for control flow; a refusal is a returned
   error.

These are the terms of the trade described in
[Product–Platform Separation](../foundations/1.separation.md). Each rule corresponds to
something the runtime does in the operation's place: statelessness permits replicas,
determinism permits retries, autonomy permits relocation, purity makes every interaction visible
to the runtime, and returned errors let it distinguish a decision from a failure.

## Leaving the model

Two declarations step outside these rules deliberately.

An *unmanaged* operation receives the storage's own client instead of entity state. It exists
for reads the query model cannot express. Everything the runtime provides around state —
versioning, concurrency control, events — depends on writes passing through it, so an unmanaged
operation is meant to read and never to write.

An operation declared `stateful` is tied to one process and is called on that process by name.
It trades the guarantees of an ordinary call for the ability to reach something a particular
process holds.

Both are part of the model as acknowledged exceptions: the manifest says where they are, so the
rest of the application can still be reasoned about by the rules.
